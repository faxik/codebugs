## prescription (ВЫБРАННАЯ ФОРМА — решение (3), не гипотеза)

Карта дала гипотезу «`order_by`-параметр И/ИЛИ отдельный глагол `recent`» и прямо назвала
её «hypothesis, not a mandate». Preflight выбрал:

> **ОТДЕЛЬНЫЙ ГЛАГОЛ `recent`. Параметра `order_by` НЕ добавляем. `query_findings` НЕ
> трогаем вообще.**

Пять доводов, каждый опирается на добытый факт, а не на вкус:

1. **Ловушка 1 обходится СТРУКТУРНО, а не тестами.** Предупреждение «PARAMETER ORDER IS
   LOAD-BEARING» относится к построенному запросу `query_findings`: плейсхолдеры CASE
   стоят текстуально между WHERE и LIMIT/OFFSET. Добавить туда `updated_at >= ?` — значит
   вклиниться ровно в эту опасность, где ошибка портит ТОЛЬКО отфильтрованные запросы.
   Отдельная функция строит свой запрос, в котором CASE нет вообще: опасность не
   «покрыта тестом», её НЕ СУЩЕСТВУЕТ.
2. **Ловушка 2 обходится СТРУКТУРНО.** Нет параметра `order_by` → нет произвольного имени
   колонки → CB-20/CB-22 не переоткрываются. Причём preflight добыл довод, которого в
   карте нет: `is_sql_identifier` — SAFE SUBSET формы, а не список реальных колонок
   (`NULL` его проходит). То есть форма A потребовала бы `is_sql_identifier` **плюс**
   собственный аллоулист колонок — два механизма там, где нужен ноль.
3. **П.3 приёмки («поведение без нового параметра не меняется») выполняется СВОЙСТВОМ
   ДИФФА.** `query_findings` не изменена ни на байт — значит несущий под LIMIT порядок
   «severity, затем created_at» (CB-20) не может сдвинуться, и это видно ревьюеру из
   диффа, а не из зелёного прогона.
4. **Обязательная оговорка попадает в правильный СКОУП.** У отдельного глагола описание
   покрывает ВСЮ поверхность. На `query` та же оговорка относилась бы только к случаю
   «передан один конкретный параметр» — оговорка в чужом скоупе внутри и без того
   огромного докстринга.
5. **Детерминизм берётся у уже существующего прецедента**: `ORDER BY updated_at DESC,
   rowid DESC` — буквально форма из `_match_fingerprint:728`, новых прецедентов не
   вводим.

**Цена формы, названная вслух** (не бесплатно): в `findings.py` появляется вторая
читающая SELECT-дорожка по `findings`. Это легально — таблицей владеет тот же модуль
(правило «ни один модуль не лезет в чужие таблицы» не нарушено), и `similarity.py`
прецедентно читает findings ТОЛЬКО через публичный аксессор. Дублирование ограничено:
новая дорожка не повторяет ни один из 14 фильтров `query_findings`.

### Что именно построить

**Доменная функция** `recent_findings(conn, *, since, status=None, limit=100, offset=0)`:
- `WHERE updated_at >= ?`, плюс `status = ?` когда фильтр активен;
- `ORDER BY updated_at DESC, rowid DESC` — литерал, не параметр, не f-строка от ввода;
- возвращает тот же контракт-шейп, что `query_findings` (`findings` + `total` + эхо
  фильтров) — сверься с реальным возвратом `query_findings` и повтори его, не изобретай;
- `since` **обязателен**. Валидируй ДО любого запроса: непустая строка, разбираемая как
  `YYYY-MM-DD` или полный ISO-таймстемп. Мусор (`"yesterday"`, `0`, `[]`, `None`) →
  `ValueError` с внятным текстом. Это прямая обязанность по CB-82: «нет фильтра» —
  правило ЗАПРОСНОЙ стороны, а здесь фильтр обязательный, поэтому падать надо, а не
  молча возвращать всё или ничего;
- `status` — необязательный, и именно здесь работает CB-25: активность фильтра решает
  `types.is_vocabulary_filter_active`, НЕ truthiness и НЕ `!= ""`; активное значение
  прогоняется через `resolve_finding_status` (обе стороны словаря, CB-19).

**MCP-инструмент `recent`** внутри `register_tools` — без доменного префикса, как вся
поверхность findings (`add`, `query`, `stats`, `categories_normalize`); прецедент
`categories_normalize` — недавнее добавление в этот же файл, тоже без префикса, и
дробить семейство одним префиксным членом значит усложнить будущее общее переименование.

**CLI-глагол `recent`** в `register_cli` + `_cmd_recent` + строка в `commands.update({…})`.
Порядок `except json.JSONDecodeError` ПЕРЕД `except ValueError` обязателен (правило
раздела Error handling: `_cmd_query` несёт этот же порядок и комментарий, объясняющий его).

### Формулировка оговорки (обязательна дословно по смыслу, в MCP-докстринге И в CLI help)

Описание обязано сказать, ЧТО ПОЛЕ ЗНАЧИТ, а не что хочет прочитать вызывающий:

- `updated_at` — время ПОСЛЕДНЕЙ ЗАПИСИ, не момент закрытия;
- любая правка двигает его: смена статуса, ретег, meta-патч, ре-триаж severity **и
  `append_note`**;
- `_bump_row` двигает его на ДЕДУПЛИЦИРОВАННОМ НАБЛЮДЕНИИ без смены статуса;
- поэтому `recent(since=…, status="fixed")` = «карты, которые СЕЙЧАС fixed и которых
  касались с этой даты», а НЕ «карты, закрытые с этой даты»;
- ошибка односторонняя: ложные срабатывания возможны, пропуски — нет (закрытие всегда
  пишет `updated_at`).

## acceptance (тест, обязанный упасть при мутации)

Все четыре пункта куратора плюс два теста, пиннующие оговорку как ПОВЕДЕНИЕ.

1. **Один вызов MCP и один вызов CLI.** Тест дёргает MCP-инструмент через ту же
   механику, что используют соседние тесты findings, и CLI — через `cli.main` in-process
   (как это делают существующие CLI-тесты в файле).
2. **Порядок ДЕТЕРМИНИРОВАН.** Тест-мутант: несколько карт с ОДИНАКОВЫМ целосекундным
   `updated_at`. Утверждение — точная последовательность id, повторяемая между прогонами.
   Такой тест обязан упасть, если убрать `, rowid DESC`.
3. **Поведение `query` без изменений.** Проверяй ШАБЛОНОМ SQL через `RecordingConnection`
   (`tests/test_findings.py:23`) — `sql.count(...)`/наличие `ORDER BY` — а не только
   поведением: правило репо «assert against the SQL template, not the executed statement».
   Плюс существующий `TestSeverityOrdering` должен остаться зелёным нетронутым.
4. **ОТФИЛЬТРОВАННЫЙ случай покрыт обязательно** — ловушка 1 портит только его.
   Даже при выбранной форме (query не трогаем) тест на `recent(since=…, status="fixed")`
   с реальным набором строк обязателен: он ловит перепутанный порядок биндов в НОВОМ
   построенном запросе. Тест только на `recent(since=…)` без статуса — вакуозен по этой
   оси и не принимается как единственный.
5. **Оговорка как поведение, а не как проза** — два теста:
   - карта, ПЕРЕ-НАБЛЮДЁННАЯ через дедуп (живая, статус не менялся), НЕ всплывает в
     `recent(since=…, status="fixed")`;
   - карта, ЗАКРЫТАЯ давно и получившая `append_note` сегодня, ВСПЛЫВАЕТ в
     `recent(since=сегодня, status="fixed")`. Это и есть исполняемая формулировка
     «последнее касание ≠ момент закрытия»; назови это в докстринге теста.
6. **Плохой `since` отвергается**: `""`, `"yesterday"`, `0`, `[]`, `None` → `ValueError`,
   и CLI печатает одну внятную строку в stderr с кодом 1, а не трейсбек.
7. **Golden регенерирован** указанной командой; `test_schema_matches_golden` и
   `test_golden_is_already_normalized` зелёные.

**Мутационная проба (§13 п.2) — ТОЛЬКО во ВРЕМЕННОМ worktree.**
`git worktree add <tmp> <sha>` → внести мутацию → прогнать → `git worktree remove --force`.
Никогда в рабочем дереве: в Т-15 проба в общем дереве совпала с параллельным коммитером
и мутант едва не попал в коммит. Минимум две мутации, обе обязаны дать КРАСНОЕ:
(М1) убрать `, rowid DESC` из ORDER BY → падает тест детерминизма;
(М2) заменить `>=` на `>` ИЛИ снять валидацию `since` → падает соответствующий тест.
