## 1. Механика: чем именно это делается

`git blame --reverse -p [-C] -L <a>,<b> <reported_at_commit>..HEAD -- <path>`

Формат porcelain при `--reverse` инвертирован относительно обычного blame:
`<sha> <строка_в_ПОСЛЕДНЕЙ_ревизии> <строка_в_ИСХОДНОЙ_ревизии>`. Строка **жива**, если
её `<sha>` равен HEAD; иначе `<sha>` — последний коммит, где она ещё существовала, то есть
строка удалена. Записи `filename` в том же выводе несут **путь в последней ревизии**, и он
может отличаться от записанного — именно этим и ловится переезд.

Git 2.53.0. `reported_at_commit` уже заморожен в строке (CB-53), то есть входные данные
для этого механизма в трекере **уже есть** и ничего добавлять к записи не требуется.

## 4. Стоимость — и ответ на вопрос «вне лока или под бюджетом»

| операция | codebugs | autosorter |
|---|---|---|
| `git blame --reverse` (РАЗРЕШЕНИЕ) | медиана **10.7 ms**, p90 25.8, max 53 | медиана **21.5 ms**, p90 42.7, max 95 |
| `git show <commit>:<path>` (ЗАХВАТ текста) | медиана **0.95 ms**, p90 1.45, max 1.78 | — |
| чтение файла с диска (сырое) | 0.008 ms | — |
| `git rev-parse HEAD` (уже платится сегодня) | 0.67 ms | — |
| контентный якорь v4 (разрешение) | медиана 2.14 ms | медиана 2.21 ms |

**Ответ, которого требовал куратор, и он структурный, а не про бюджет:**
**reverse blame — операция ЧТЕНИЯ, она физически не находится под write-lock.** Захват под
локом не делает трейса вообще: ему нужны `reported_at_commit` (уже захватывается сегодня),
путь, пролёт (разбор в памяти) и — по решению владельца — текст. **Маржинальная цена якоря
под локом = один `git show` ≈ 0.95 ms** против 8–16 ms, которые лок уже держит на
резолвере similarity. Разрешение (11–23 ms) живёт в отдельном вербе и лока не касается.

Дедупликация разрешения по паре (commit, file) даёт лишь **16% / 6%** экономии (31 пара на
37 карточек; 307 на 325), то есть батч-разрешение почти не экономит: `anchor_resolve` над N
карточками стоит примерно N × 11–23 ms. Это подтверждает, что разрешение обязано быть
ОТДЕЛЬНЫМ вербом и не может жить внутри `get`/`query`.

## 5. САМОЕ ВАЖНОЕ: blame ошибается, и это обосновывает хранение текста

| | codebugs | autosorter |
|---|---|---|
| строк, доживших до HEAD | 58 | 479 |
| текст на выведенной строке **совпал** | 58 (**100.00%**) | 478 (**99.79%**) |
| **разошёлся** | 0 | **1 (0.21%)** |

Единственное расхождение локализовано: **CB-3055**, `src/autosorter/watcher/service.py`,
старая строка 503 → blame выдал строку 168 HEAD; blame считает, что там
`for root_str, loader in self._asignore_loaders.items():`, а в файле на строке 168 стоит
`self._ignore_rules.reset()`.

**Следствие для дизайна, и оно несущее:** номер строки от `blame --reverse` **нельзя
отдавать не проверив**. В 0.21% случаев он уверенно неверен — а уверенно неверный ответ
хуже отказа. Значит разрешение обязано СВЕРИТЬ содержимое выведенной строки с сохранённым
текстом и при расхождении отвечать отказом, а не координатой.

**И это же — настоящее обоснование решения владельца хранить текст.** Владелец сказал «для
reverse blame, видимо, нужен текст». Замер уточняет, ЗАЧЕМ: текст нужен не чтобы НАЙТИ код
(находит git), а чтобы **ПРОВЕРИТЬ ответ git'а**. Без сохранённого текста проверять не с чем,
и 0.21% уверенно неверных координат уходят потребителю как правда.

## 6. Контролируемый опыт: rename + сдвиг + split (проверка заявления владельца дословно)

Владелец: «Так даже split/rename и т.п. можно отследить!» Проверено в одноразовом репо
(`/tmp/bt7rn`), где над якорем последовательно сделаны ТРИ операции: переименование файла
`a.py`→`b.py`; вставка трёх строк выше якоря (сдвиг номеров); **вынос функции в отдельный
файл** `split_out.py`.

Якорь — строки 4–7 файла `a.py` в базовом коммите. Результат `git blame --reverse -C`:

```
def target_function():        -> split_out.py строка 3
    x = compute_the_thing()   -> split_out.py строка 4
    y = x * 2                 -> split_out.py строка 5
    return y                  -> split_out.py строка 6
```

Файл на HEAD подтверждает: `target_function` действительно на строке 3 `split_out.py`.
**Заявление владельца подтверждено буквально.** Контентный якорь v4 на этом же случае
отвечает `lost`: он ищет в ЗАПИСАННОМ файле `a.py`, которого на HEAD уже нет.

**И неожиданное — комбинация флагов не монотонна:**

| флаги | куда разрешился якорь |
|---|---|
| голый | `b.py` (переезд файла отслежен, split — нет) |
| `-M` | `b.py` |
| **`-C`** | **`split_out.py`** ✔ |
| `-M -C` | `b.py` ✘ |

**`-C` в одиночку ловит split, а `-M -C` вместе — теряет.** Мои первые корпусные прогоны шли
на `-M -C`, то есть на конфигурации, которая splits пропускает. Матрица флагов перемерена
на живом корпусе codebugs (37 карточек): голый 26/37, `-M` 27/37, `-C` 27/37, `-M -C` 27/37,
`-C -C` 27/37, и **ноль карточек переехали в другой файл ни при одном флаге** — то есть на
этой истории случай split просто не встречается, и выбор флага стоит ноль.

Честная пара утверждений: способность реальна и продемонстрирована опытом; её измеренная
частота на историях обоих трекеров — **нулевая**. Поэтому `-C` выбирается как бесплатная
страховка, а не как измеренная выгода.

## 7. Комплементарность: нужен ли контентный якорь v4 как фолбэк

Оба канала прогнаны на ОДНОЙ популяции.

| | codebugs (37) | autosorter (250) |
|---|---|---|
| ядро (reverse blame) разрешило | 27 (73.0%) | 177 (70.8%) |
| фолбэк (контентный хеш v4) разрешил | 10 (27.0%) | 126 (50.4%) |
| **хотя бы один** | 27 (73.0%) | **187 (74.8%)** |
| **ТОЛЬКО фолбэк** | **0** | **10 (4.0%)** |
| только ядро | 17 | 61 |
| согласие по строке, где ответили оба | 10 / 10 | **116 / 116** |

**Выводы, и первый — против моей же v4.**
1. Ядро строго сильнее фолбэка: 73% против 27% и 71% против 50%.
2. **Там, где ответили оба, они согласны по номеру строки в 126 случаях из 126.** Два
   независимых механизма, ноль расхождений — это сильное свидетельство, что оба правы.
3. **Фолбэк добавляет 0 карточек на codebugs и 10 из 250 (4.0%) на autosorter.** Это те
   случаи, где ядро сказало «все строки удалены», а текст всё же нашёлся в текущем файле —
   код был удалён и заново добавлен, и git не связал эти события.
4. Значит контентный якорь **не избыточен, но и не равноправен**: он вторичный канал ценой
   4 процентных пункта на большом корпусе, и его настоящая область — популяция, которую эти
   два корпуса не содержат вовсе: **нет git, shallow-клон, файл вне истории, незакоммиченная
   правка, другая VCS** (её владелец назвал явно).

## 8. Честный отказ: где ядро не работает вообще

Проверено исполнением на `--depth 1` клоне (`/tmp/bt7shallow`): `.git/shallow` присутствует,
глубина истории 1, и `git blame --reverse <старый>..HEAD` падает громко —

`.git/shallow`, недостижимость коммита и ненулевой код возврата blame дают три независимых
признака. Это путь `unknown(<причина>)`, а не молчаливый неверный ответ.

## 9. Побочное, но снимающее целый раздел рисков v4

Если захват берёт текст **из хранилища объектов git** (`git show <commit>:<path>`), а не с
диска, то неверсионируемые файлы недостижимы ПО ПОСТРОЕНИЮ. Проверено:

```
git show HEAD:.git/config          -> fatal: path '.git/config' exists on disk, but not in '<tree>'
git show HEAD:.env                 -> fatal: path '.env' does not exist in '<tree>'
git show HEAD:../../etc/passwd     -> fatal: '../../etc/passwd' is outside repository
git show HEAD:/etc/passwd          -> fatal: path '/etc/passwd' exists on disk, but not in '<tree>'
git show HEAD:.codebugs/findings.db-> fatal: path '.codebugs/findings.db' exists on disk, but not in '<tree>'
```

А захват v4 читал бы их с диска: `.git/config` — обычный файл 546 байт внутри корня,
проходящий все предикаты v4; `.codebugs/findings.db` — **1 495 040 байт базы самого
трекера**. То есть v4 могла занормализовать и сохранить в карточку фрагмент собственной
базы находок.

**Следствие:** containment, `realpath` полного пути, `S_ISREG`, отказ FIFO/устройствам —
весь раздел §7.2 v4 — при захвате через git не нужен: границу держит сам git, а не наш код.
Владелец принял канал чтения как цену; пере-центровка на git отдаёт бóльшую часть этой цены
обратно бесплатно.

## 10. Честные пределы этого замера

1. **Потолок прогона**: autosorter прогонялся до 400 разрешений (312 попали в предикат) и
   250 для комплементарности, не весь корпус. Предикаты при этом считаны по ВСЕМУ корпусу.
2. **Один прогон на точку, одна машина, тёплый кэш.** Опираться следует на порядок
   (0.95 ms против 11–23 ms), а не на третью цифру.
3. **Пролёт якоря искусственно ограничен пятью строками** (`b = min(b, a+4)`) — это верхняя
   планка v4; при другой планке доли выживания изменятся.
4. **Оба трекера — репозитории с полной историей и одним владельцем.** Популяция «нет
   git / shallow / другая VCS», ради которой и держится фолбэк, здесь **не представлена
   вовсе**, поэтому её вклад измерить нечем — он аргументируется, а не измеряется.
5. **`no_parsable_span` (62 и 1594) — ограничитель, общий для обоих каналов** и не
   устраняемый выбором механизма: это карточки, которые не говорят, где смотреть.
6. Сверка по содержимому сравнивает `.strip()`-формы, то есть слепа к изменению отступа.
