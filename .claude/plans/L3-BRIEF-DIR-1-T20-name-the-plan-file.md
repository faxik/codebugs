## §1. Замысел — то, против чего будут принимать

**Н3 дословно: конвенция, нарушенная четырежды после принятия, — не правило.**

Канон **К-3** гласит: параллельные сессии добавляют файлы на `main` **поимённо, никогда
каталогом**. Он принят потому, что `git add .claude/plans/` одной сессии затянул **чужой
untracked-файл другого направления** в чужой коммит с чужим сообщением. Содержимое уцелело,
испорчен **провенанс**: артефакт одного направления числится за другим и за не относящейся к нему
работой.

После принятия канона нарушение повторилось — куратор считает это **рецидивом №4** в семье. Отсюда
решение: **перевести конвенцию в механику.** Это дословно урок CB-50, записанный в `CLAUDE.md`
в первом же абзаце раздела Workflow: *«a convention that exists only as a pattern in the log is not
a rule»* и *«prose cannot enforce prose»*.

Приёмка будет читать дифф **против этого предложения**, а не против формы в §2.

## §2. Задание-гипотеза — и ты вправе предложить лучшую

**Гипотеза куратора:** pre-commit-хук на `main` **отказывает коммиту, который стейджит
`.claude/plans/`-файл, чьё имя не названо в сообщении коммита.**

Логика: автор, осознанно коммитящий свой план, назовёт его без труда; автор, случайно загребший
чужой файл каталогом, его не назовёт, потому что не знает о нём.

**Куратор явно записал, что форма — гипотеза, и преflight вправе предложить лучшую.** Если по коду
и по механике git ты увидишь механизм, который ловит тот же замысел дешевле или надёжнее, —
предложи его В ВОЗВРАТЕ с обоснованием, и не приземляй молча ни одну из версий. Замысел (§1) не
обсуждается; форма — обсуждается.

## §3. Ловушки, которые я вижу заранее — разбери каждую в preflight

Это не требования, это места, где гипотеза может оказаться дефектной. **Найдёшь ещё — назови.**

1. **Подстрочное совпадение — не «названо».** Наивная проверка «имя файла встречается в тексте
   сообщения» проходит по сообщению `docs: правки в .claude/plans/`, то есть **ровно по той форме,
   которую хук должен ловить**. Сравнивать надо с базовым именем файла как с токеном, а не
   подстрокой. Это ровно класс «гейт, который не может сработать», которым `CLAUDE.md` размечен
   насквозь.
2. **Хук обязан ОТКАЗЫВАТЬ, когда не смог посмотреть.** Пустое сообщение, сообщение из файла
   (`-F`), `--amend`, коммит без `-m` через редактор — если хук в каком-то из этих состояний
   читает пустоту и молча пропускает, он становится «guard clean because it could not look».
   Это главный враг направления (Н1). **Fail closed, и посчитай, что осмотрел** — точно так же,
   как `pre-commit-hook.sh` уже делает для `MERGE_HEAD` (см. `CLAUDE.md`, абзац
   «`MERGE_HEAD` is read fail-closed»).
3. **Не-ASCII имена.** `git diff --cached --name-only` по умолчанию C-квотит такие пути. В этом
   репозитории это **уже случалось дважды** — один раз дало ложный отказ плановой заметки, другой
   раз заставило `_guard_conflict_markers` молча ПРИНЯТЬ конфликт-маркер. Оба читателя чинились
   через `-c core.quotePath=false`. Не наступи третий раз.
4. **Скоуп: только `main`, только `.claude/plans/`.** На ветках хук не должен мешать вообще — там
   поимённость не нужна, потому что чужих untracked-файлов там не бывает. Существующий
   pre-commit-хук уже отказывает на `main` всему, кроме `.claude/plans/*.md`; твоя проверка —
   ДОПОЛНИТЕЛЬНАЯ к ней и живёт в том же файле.
5. **Один уровень, не поддерево.** Действующее правило — `.claude/plans/*.md` ровно один уровень.
   Мой собственный юнит на этой неделе получил корректный отказ на
   `.claude/plans/exposure-scripts/matrix.py`. Не расширь скоуп попутно.
6. **`--no-verify` остаётся escape hatch и это НЕ дефект.** Так записано в `CLAUDE.md`: хук
   существует, чтобы остановить случайность, а оператор, набравший флаг, заявил намерение.
7. **Хук не может ссылаться на `tools/`.** Он запускается из `.git/hooks/` симлинком и обязан
   работать, когда `tools/` нет в дереве. Поэтому библиотеку `_guards.sh` он **не** подключает —
   посмотри, как это уже сделано, и не сломай.
8. **`install-hooks.sh` и порядок в нём.** Если добавляется что-то к арму — помни зафиксированный
   в `CLAUDE.md` урок: `merge.ff=false` ставится **раньше** всего, что может упасть, иначе
   установщик способен пропустить единственный механизм, который не заменяется хуком.

## §4. Что обязано быть в тестах

`tests/test_worktree_harness.py` — дом для этого. Два класса проверок, и **второй обязателен**:

- **Поведенческие**: состояние, которое хук обязан ОТКАЗАТЬ, и состояние, которое обязан
  ПРОПУСТИТЬ. Как минимум: имя названо → пропуск; имя не названо → отказ; два файла, назван один →
  отказ; пустое сообщение → отказ; не-ASCII имя названо → **пропуск** (ложный отказ здесь так же
  плох, как пропуск).
- **Структурная**: что хук действительно ВЫЗЫВАЕТСЯ. В этом репозитории дважды удаляли вызовы
  гуардов, и весь сьют оставался зелёным, потому что скрипт никто не исполнял. Каждый гуард
  покрыт юнит-тестом, а композиция — нет; это записано в `CLAUDE.md` как отдельный урок.

**Мутационная проба обязательна и ставится В ТОЧКУ дефекта.** И — **канон К-5, принят сегодня:
мутационная проба выполняется во ВРЕМЕННОМ worktree, никогда в рабочем.** Инцидент Т-15: в окно
между мутацией и откатом чужой коммит мог подхватить мутанта.

**Из возврата Т-19, стоило отдельного разбора:** прогоняй с `PYTHONDONTWRITEBYTECODE=1`, чисти
`__pycache__` и **подтверждай, что мутант применён** (`grep -c` по внесённой строке). Первый
прогон исполнителя Т-19 дал ложное «1 passed» из-за устаревшего `.pyc`; симптом читается как
эквивалентный мутант, а был инструментальным. Без подтверждения применения «мутант выжил» и
«мутант не применён» **неразличимы**.

## §6. Харнес и каноны

```
tools/worktree-setup.sh feature/t20-name-the-plan-file
# работа в .worktrees/feature-t20-name-the-plan-file
uv run --extra dev ruff check src/ tests/
uv run --extra dev python -m pytest tests/ -q      # --extra dev не опционален
tools/worktree-finish.sh feature-t20-name-the-plan-file 'msg' --merge-msg '…'
```

- **К-1. На `main` ты не коммитишь НИКОГДА.** Факт своей приёмки пишешь в этот бриф **на ветке**,
  ДО `worktree-finish.sh`, чтобы итерация осталась одним мерджем.
- **К-3.** Файлы добавляешь **поимённо** — да, ты чинишь именно это, и правило действует на тебя.
- **К-4.** Ветка начинается с красных тестов (TDD) → **`--merge-msg` ОБЯЗАТЕЛЕН**, иначе субъект
  мерджа возьмёт первый коммит первопарентной линии, то есть «red tests».
- **К-5.** Мутационная проба — во временном worktree, никогда в рабочем.
- Цитируй **грепаемое содержание, а не номера строк** — номера не переживают форвард-мердж.

**Ты будешь править `CLAUDE.md`** (таблица «что механически энфорсится» и раздел Workflow —
там появится новая строка). Это **точка сериализации с DIR-2**: перед касанием проверь
`claims_list` и живые ветки, и не мержь параллельно с ними.

## §7. Кросс-модельное ревью

```
timeout 420 codex exec --sandbox read-only '…' < /dev/null
```
Никогда в фоне без границы; дифф **текстом** в промпте; **явно назови бюджет верификации**
(«можно прогнать вот эту команду и прочитать вот эти файлы; обход дерева запрещён») — это
работает лучше глухого запрета, проверено дважды сегодня. Имя модели из каскадных документов
**не бери**, фолбэк на дефолтную разрешён явно. **После двух таймаутов вправе отказаться от
кросс-модельной половины, назвав это вслух в возврате** — молчаливый пропуск не принимается.
