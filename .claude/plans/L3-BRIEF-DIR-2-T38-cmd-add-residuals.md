## 1. Задание — две карточки, один хендлер, РАЗНЫЕ механизмы

**CB-132 (medium, `error_handling`).** `--meta` с не-JSON или не-объектом вылетает СЫРЫМ
traceback'ом: `json.loads(args.meta)` без арма над ним. `codebugs add … --meta 'не json'`
даёт `json.JSONDecodeError`, `--meta '[1,2]'` — `TypeError: cannot convert dictionary update
sequence element #0`. CLAUDE.md называет этот класс прямо: «хендлер, который не ловит
ничего, нарушает правило ровно так же, как ловящий в неверном порядке» (урок CB-19/CB-79).
Направление фикса: арм `json.JSONDecodeError` с текстом, называющим негодное значение, плюс
явный отказ, когда распарсенный payload не объект.
**Ограничение, которое легко нарушить:** порядок армов `json.JSONDecodeError` ПЕРЕД
`ValueError` — действующий контракт, пиненный `tests/test_findings.py::TestRetriageCliContract`.
Не потревожь его.

**CB-133 (low, `silent_default`).** `-l ""` по-прежнему молча отбрасывается: засев meta
идёт через `if value:` по `_ADD_META_FLAGS`, то есть по TRUTHINESS. Явно набранная пустая
строка не приземляется, конфликтом не считается, вызов рапортует успех. **Это НЕ регрессия**
(до Т-24 было `if args.lines:` — то же самое), это инстанс уже дважды ратифицированного
класса: CB-25 («нет фильтра» = None и пустая строка, никогда truthiness) для чтения и
**CB-82** («на пути ЗАПИСИ None — единственное „не передано“») для записи. Флаг CLI — путь
записи, значит применяется CB-82.
**Суб-решение, которое ты обязан принять и НАЗВАТЬ:** `-l ""` должен отказывать или
сохранять пустую строку? CB-82-консистентный ответ — отказывать. Если код покажет иное —
доложи, не исполняй молча.

**Предпосылки (спот-чекни; расхождение = СТОП и доклад):** грепаемые якоря —
`_ADD_META_FLAGS` и охраняющий его `if value:`; `meta.update(json_meta)` внутри `_cmd_add`.
Т-24 уже перенёс разбор `--meta` ДО `db.connect()`, поэтому соединение на этом пути больше
не течёт — то есть CB-132 сегодня «не хуже», и юнит правит ФОРМУ ОТКАЗА, а не утечку.

## 7. Слот эскалаций менеджера (3) → держателю (2)

**НЕ ПУСТО — три пункта.**

**Э-1. Расширение буквы ради смысла: `--meta ""` тоже начал отказывать, хотя не назван ни в
одной карте.** `--meta` охранялся ВТОРОЙ truthiness-проверкой в том же блоке —
`json_meta = json.loads(args.meta) if args.meta else {}` — то есть явно набранный `--meta ""`
молча исчезал и вызов рапортовал успех: ровно класс CB-133, на соседнем флаге того же
хендлера. Оставить его значило приземлить фикс, который двумя строками выше нарушает
собственное обоснование (CB-82: на пути записи `None` — единственное «не передано»), то есть
секционно-локальное применение списка правок, порождающее новый дефект при закрытии старого.
Считаю это сохранением СМЫСЛА ратифицированного класса, а не расширением интента, поэтому
исполнил и называю вслух, а не спрашиваю. Прецедент формы взят из `bench.py`: там `csv_data=""`
— это «переданный ПУСТОЙ документ», а не отсутствующий аргумент (грепаемо: комментарий
`A payload is "supplied" when it is not None`). Видимо пользователю → строка в CHANGELOG.
**Если держатель считает это выходом за скоуп — откат стоит одного предиката и одного теста
(`test_an_empty_meta_refuses`).**

**Э-2. Предпосылка §6 брифа не подтвердилась: клеймов харнес НЕ взял.** Бриф предписывает
`tools/worktree-setup.sh fix/t38-cmd-add-residuals` со словами «имя несёт обе карты через

несёт. CB-132 и CB-133 не были заклеймлены ни на минуту. Ущерба нет (юнит одиночный,

### Что сделано, по картам

**CB-132 — форма отказа для негодного `--meta`.** Арм навешен на РАЗБОР И ТОЛЬКО НА НЕГО:
греп-якорь `except json.JSONDecodeError as e:` внутри `_cmd_add`, непосредственно вокруг
`json_meta = json.loads(args.meta)`. Плюс отдельный отказ по ФОРМЕ распарсенного значения —
якорь `if not isinstance(json_meta, dict):` с текстом
`--meta must be a JSON object (a mapping), not `. Два разных механизма, потому что дефекта два:
`--meta 'не json'` умирал в `json.JSONDecodeError`, а `--meta '[1,2]'` — валидный JSON неверной
ФОРМЫ — в `TypeError` из `meta.update` ниже; арм разбора второй случай не видит по построению.
Прежний охранник `if isinstance(json_meta, dict):` вокруг проверки конфликта CB-129 снят: он
существовал именно для того, чтобы не делать SUBSTRING-тест `key in json_meta` по строке, а
теперь не-объект отказан ВЫШЕ, так что охранять нечего.

**Узость арма — не деталь, а несущее свойство, и она пиненa тестом.** Ниже в том же хендлере
живёт `except json.JSONDecodeError:` с комментарием `MUST stay ahead of the ValueError arm` —
это ПРЕД-записный разбор `_bump_row`'ом СОХРАНЁННОЙ meta найденной строки, то есть порча
данных, а не негодный ввод, и она обязана продолжать вылетать громко. Один широкий `try`
превратил бы её в аккуратную однострочную «ошибку ввода» для состояния, которого вызывающий не
набирал — ложь класса CB-15/CB-16. Пиненo тестом
`test_a_bump_over_corrupt_stored_meta_still_crashes`, близнецом
`TestRetriageCliContract::test_a_committed_write_is_never_reported_as_bad_input`. Порядок
`json.JSONDecodeError` ПЕРЕД `ValueError` не потревожен: оба новых отказа делают `sys.exit`, а
не `raise`, поэтому в цепочку армов вообще не попадают.

**CB-133 — суб-решение, которое требовалось назвать: `-l ""` ОТКАЗЫВАЕТ, не сохраняет пустую
строку.** Основание добыто из кода, а не из брифа: `src/codebugs/bench.py`, функция
`_require_text` — грепаемо по её докстрингу `on a write path \`None\` is the ONLY "not supplied"`
и по телу `raise ValueError(f"{name} must not be empty{suffix}")`. Это уже приземлённая,
ратифицированная реализация CB-82 в этом же репозитории, и она на переданной пустой строке
именно ОТКАЗЫВАЕТ — не подставляет умолчание и не сохраняет `""`. Код не показал иного, так что
докладывать расхождение не пришлось: CB-82-консистентный ответ брифа и поведение кода совпали.
Дополнительный довод по существу: сохранить `{"lines": ""}` значит положить на строку
бессмысленный ключ, а молча выбросить — это ровно тот success-shaped discard, который юнит
закрывает. Реализация: `if value is None: continue` (отсутствие) отделено от `if not value:`
(переданная пустота) — греп-якорь `was given an empty value, which is not `.
