# Задание: короткий вид выдачи у `query` и `recent` (из autosorter CB-4650)

Составлено 23.09.2026 сессией autosorter-6d по прямой просьбе владельца. Адресат — куратор
codebugs: он решает, какому направлению отдать работу и под каким номером. Карточку в
СОБСТВЕННОМ трекере codebugs завести при постановке задачи; в трекере autosorter она уже
есть — CB-4650, и в её заметках записана перекрёстная проверка Codex.

## 1. Что сломано и почему это важно

Инструмент MCP `query` (и его сосед `recent`) всегда возвращает карточки ЦЕЛИКОМ: полное
описание, всё поле `meta` с кольцом наблюдений, сводку привязки к коду. Уже при нескольких
десятках карточек ответ не помещается в окно агента. Тогда среда сохраняет его в файл
`tool-results/mcp-codebugs-query-*.txt`, а агент следующим шагом пишет самодельный
`jq` или Python, чтобы собрать из этого файла короткую таблицу.

**Замер (окно: только транскрипты проекта autosorter за 14 дней до 23.09.2026; другие
проекты не смотрелись):**

| Что | Число |
|---|---|
| Ответов `query`, сохранённых в файл из-за размера | 195 |
| Медианный размер такого ответа | 104 КБ (каждый десятый — больше 379 КБ) |
| Медианный вес одной карточки в ответе | около 4,5 КБ |
| Доля полного описания в весе карточек | 51 % |
| Доля поля `meta` | 38 % |
| Доля сводки привязки `anchor` | 4 % |
| Вес той же карточки в виде строки из шести полей с описанием до 200 знаков | около 354 байт — в 13 раз меньше |
| Самодельных разборов таких файлов за то же окно | 584 |

Почти все 584 разбора собирают одну и ту же таблицу «номер, важность, статус, начало
описания». То есть агенты каждый раз вручную восстанавливают то, что командная строка
codebugs уже умеет печатать.

**Почему это важно, и кто так решил.** Это оценка сессии autosorter-6d по объёму: сбоев от
этого не случалось, цена — лишний контекст и ручной код на каждом просмотре списка
карточек. Число 195 взято из реальной работы, а не из рассуждения.

## 2. Что уже есть (проверено чтением кода 23.09)

- `src/codebugs/findings.py:5000` — MCP-инструмент `query`: фильтры, `group_by`, `limit`,
  `offset`, `resolve_anchors`, выбора вида выдачи нет. Ветка `status="deferred"`
  (`:5111`–`:5165`) может вернуться раньше, чем дойдёт до `query_findings`, а при
  непустом результате дописывает каждой строке `blocker_count` (`:5186`–`:5188`).
- `src/codebugs/findings.py:5192` — MCP-инструмент `recent`, та же форма строк.
- `src/codebugs/findings.py:5641`–`:5678` — командная строка `codebugs query` уже печатает
  ровно нужную проекцию: `id`, `severity`, `category`, `file`, `status`, `description`,
  а при `--resolve-anchors` ещё столбец `loc` через `_anchor_cell` (`:5566`).
- В репозитории есть снимок схем инструментов и `tests/test_exposure_matrix.py`. Новый
  параметр их затронет; обновлять осознанно, не глушить. Подробно эти файлы при
  составлении задания НЕ читались.

## 3. Что сделать

Добавить `query` и `recent` параметр **`view`** с закрытым набором значений `"full"` и
`"summary"`. Это ФИКСИРОВАННЫЙ вид, а не произвольный выбор полей: Codex отговорил от
`fields=[...]`, потому что произвольная схема ответа хуже проверяется и её реже используют.

Строка в виде `"summary"`:
- поля `id`, `severity`, `category`, `file`, `status` — как есть;
- `description`, обрезанное до 200 знаков (знаков, а не байт: описания часто по-русски);
- флаг `description_truncated: true|false`, чтобы обрезка была видна, а не молчалива;
- `blocker_count`, если строка пришла из ветки `deferred`;
- при `resolve_anchors=true` — короткое состояние привязки той же строкой, что даёт
  `_anchor_cell`, без полной сводки;
- поля `meta` нет.

Ключи самой выдачи (`grouped`, `total`, `limit`, `offset`) сохраняются в обоих видах.
Ответы с `group_by` вид не меняет. Неизвестное значение `view` — отказ с понятным текстом,
а не молчаливый откат к `"full"`: это тот же класс ошибки, что «аргумент выброшен, ответ
успешен», против которого в репозитории уже заведено правило CB-15. Описания обоих
инструментов называют `"summary"` как вид для просмотра списков и отсылают к `get` за
полной карточкой.

**Решение, которое остаётся за куратором codebugs:** какое значение будет по умолчанию.
- Если по умолчанию `"full"`, ничего не ломается, но агенты могут просто не передавать
  параметр, и тогда выгрузки в файлы продолжатся. Это главный довод Codex против
  необязательного ключа.
- Если по умолчанию `"summary"`, выгрузки прекратятся сразу. Зато каждый, кто сейчас
  читает `meta` из `query`, молча получит меньше полей.

Предложение сессии autosorter-6d: сперва `"full"` по умолчанию, неделя замера (пункт 5), и
смена умолчания — отдельным решением по его итогам.

## 4. Что проверить — каждое свойство пробой порчей

Для каждого свойства нужен тест, и надо показать, что он краснеет, когда ломаешь именно это
свойство:
1. в виде `"summary"` нет `meta`;
2. описание длиннее 200 знаков обрезано, и `description_truncated` равен `true`;
   короткое описание не тронуто, флаг `false`;
3. ключи выдачи на месте в обоих видах;
4. ветка `deferred` сохраняет `blocker_count` в виде `"summary"`; это нужно проверить и
   на раннем пустом возврате, и на обычном пути;
5. неизвестное `view` вызывает отказ;
6. вид `"full"` совпадает с сегодняшней выдачей поле в поле;
7. `recent` ведёт себя так же, как `query`.

Отдельно — замер размера: одна и та же страница из 100 карточек в двух видах.

## 5. Как понять, что задача решена

Через неделю после выпуска повторить замер из раздела 1 по транскриптам: число файлов
`mcp-codebugs-query-*.txt` за неделю и долю вызовов `query` с `view="summary"`. Если
выгрузки не упали, вопрос об умолчании из раздела 3 возвращается к куратору с этими
числами.

## 6. Чего не делать

- Не вводить произвольный `fields=[...]`.
- Не менять `get`: он и есть способ получить полную карточку.
- Не менять форму ответов `group_by`.
