## FATAL

### F1. `reported_at_commit` и трекер разрешаются двумя НЕСВЯЗАННЫМИ механизмами, а обязательная сверка Р5 структурно слепа к этому

**Код.** Захват коммита:

- `src/codebugs/findings.py:2985-2988`
  ```python
  if reported_at_commit is None:
      reported_at_commit = db.git_rev_parse("HEAD", silent=True)
  with conn_factory() as conn:
  ```
- `src/codebugs/findings.py:3045-3049` — то же на batch-пути.
- `src/codebugs/db.py:582-620` — `git_rev_parse(ref, *, silent=False, cwd=None)`; оба вызова
  из `findings.py` **не передают `cwd`**, значит `cwd=None`, значит `subprocess` наследует
  **cwd процесса**.

Трекер при этом разрешается совершенно другим правилом (`db._db_path`: `project_dir`/`--repo` →
`--tracker-root` → `$CODEBUGS_ROOT` → обход вверх). **Ни строка, ни объект `loc` из Р2 не несут
идентичности репозитория.** `anchor_resolve` берёт `project_dir` от ЧИТАТЕЛЯ (Р5). То есть
координата, коммит и репозиторий разрешения приходят из трёх независимых источников, и ни один
не проверяется относительно остальных.

CLAUDE.md уже фиксирует, что MCP-сервер живёт дольше того дерева, в котором стартовал (CB-79),
и что `$CODEBUGS_ROOT` — ambient-канал, унаследованный посторонним подпроцессом (CB-48). Это не
гипотетическая конфигурация, это описанная в этом же репозитории.

**Воспроизведено** (`/tmp/bt7-fork`). Два проекта с общим предком (ровно та ситуация, что
описана в CLAUDE.md: `tools/worktree-*.sh` — «scaled-down port of autosorter's»).
Карточка заведена процессом, стоявшим в `proj_a`; `reported_at_commit` = общий коммит `SHARED`.
Трекер — в `proj_b`. Разрешение идёт в `proj_b`:

```
git blame --reverse -p -C -L 3,5 <SHARED>..HEAD -- tools/worktree-finish.sh   # выполнено в proj_b
df37954a8f473ec21958b4bf490548f3c3939279 4 3 3     <- sha == HEAD(proj_b) => "жива"
filename tools/worktree-finish.sh
	_guard_branch_type "$BRANCH" || exit $?
	_guard_main_clean || exit $?
	git merge --no-ff "$BRANCH"
```

Р5 шаг 2, сверка: сохранённый текст (строки 3-5 из `SHARED`) против `HEAD:<path>` строк 4-6 в
`proj_b` — **совпал байт в байт**, `diff` пуст. Ответ: `status=current`, `channel="git"`,
`line=4`. Высокая уверенность.

А в `proj_a` — том проекте, о котором карточка, — эта строка сегодня выглядит так:

```
git merge --no-ff --no-verify "$BRANCH"
```

то есть код изменился, и якорь обязан был это показать. Вместо этого он уверенно показал
чужой файл в чужом проекте как неизменившийся.

**Почему сверка это НИКОГДА не поймает.** Она перечитывает тот же репозиторий, по которому
только что шёл blame. А blame по построению гарантирует, что строка не менялась с `<commit>`
**в этом репозитории**. Значит **всякий раз, когда канал A отвечает, сверка проходит
автоматически**. Р5 шаг 2 сверяет git с git, а не ответ с реальностью. Раздел §7.5 продаёт
сверку как то, что «делает уверенно неверный ответ невозможным» — против класса F1 она не
делает ничего и не может.

Файл замеров об этом **молчит целиком** (проверено полным чтением: ни одного упоминания
кросс-репозиторного случая).

**Что нужно до передачи владельцу:** `loc` обязан нести идентичность репозитория
(`git rev-list --max-parents=0`, корневой коммит — дешевле и стабильнее URL), захват обязан
идти в том же `project_dir`, которым разрешён трекер, а не в cwd процесса, и при
неразрешимости — `skipped: no_root` (fail-closed уже объявлен в Р3, но он объявлен для
КОРНЯ, а не для коммита). Иначе ядро отдаёт уверенно неверный ответ по классу, который
объявленный гейт не видит.

### F2. Единственный опыт, ратифицирующий `-C` и дающий владельцу тезис №2, использует якорь, который сам дизайн запрещает

**Что говорит документ.** §1б: «`-C` в одиночку ловит split, `-M -C` — нет ⇒ флаг
ратифицируется». §2.1 и §8 тезис №2: «rename + сдвиг + вынос кода в другой файл — якорь
доехал». Замеры (строки 130-155): ОДИН одноразовый репозиторий `/tmp/bt7rn`, ОДИН якорь,
`a.py` строки **4–7**, вывод показан стилизованной таблицей, сырой porcelain не приведён ни разу.

**Р6 задаёт `MAX_ANCHOR_LINES = 3`.**

Якорь на 4 строки в этой системе не существует.

**Воспроизведено** (`/tmp/bt7rn2`) — построение документа повторено дословно: `a.py`→`b.py`,
вставка трёх строк выше, вынос `target_function` в `split_out.py`.

```
span   флаги   вердикт      filename
L4,7   -C      ALIVE@HEAD   split_out.py     <- результат документа воспроизводится
L4,7   -M -C   DEAD         b.py             <- немонотонность тоже воспроизводится
L4,6   -C      DEAD         b.py
L5,7   -C      DEAD         b.py
L4,5   -C      DEAD         b.py
L5,6   -C      DEAD         b.py
L4,4   -C      DEAD         b.py
L5,5   -C      DEAD         b.py
L6,6   -C      DEAD         b.py
L7,7   -C      DEAD         b.py
```

(`-M -C` даёт `DEAD b.py` на всех перечисленных спанах.)

**Split прослеживается ровно на одном спане — полном четырёхстрочном блоке. На КАЖДОМ спане
длиной ≤3, то есть на каждом якоре, который дизайн способен сохранить, ни один флаг split не
ловит.**

Сверх того, шесть независимых построений «код переехал в другой файл» (тело функции 3 / 10 /
30 строк; новый целевой файл; уже существующий целевой файл; 16 идентичных строк, вынесенных
коммитом, который больше ничего не трогает) — `bare`, `-M`, `-C`, `-M -C`, `-C -C`,
`-C -C -C`: **0 из 6 прослежено ни одним флагом** (`/tmp/bt7-sp3`, `-sp10`, `-sp30`, `-v1`,
`-v2`, `-split`).

Три следствия, все несущие:

1. **Ратификация `-C` не имеет продемонстрированной пользы.** «Бесплатная страховка с
   продемонстрированной пользой» — польза продемонстрирована на спане, которого не бывает.
2. **У статуса `moved_file` нет ни одного показанного производителя.** Замеры сами говорят:
   «ноль карточек переехали в другой файл ни при одном флаге». Единственное свидетельство —
   тот же 4-строчный якорь.
3. **Тезис №2 владельцу неверен в той форме, в какой он написан.** «Вынос кода в другой файл —
   якорь доехал» истинно для якоря в 4 строки и ложно для якоря в 1–3 строки. Владелец
   ратифицирует ядро, глядя на демонстрацию, которую это ядро не умеет повторить.

Отдельно: rename — то, что реально работает, — работает **без всяких флагов**
(`/tmp/bt7-ren`: bare, `-M`, `-C` все три дают `ALIVE@HEAD`, `filename new.py`). То есть
единственная воспроизводимая на любых спанах польза приходит бесплатно и `-C` не обосновывает.

**Что нужно:** либо поднять `MAX_ANCHOR_LINES` до размера, на котором split реально ловится
(и перемерить, на каком именно — 4 это порог этого конкретного блока, а не общая константа),
либо снять тезис №2 и `moved_file` до уровня «не продемонстрировано», либо и то и другое.
В нынешнем виде §6 замеров — не эмпирика механизма, а эмпирика одного спана.

### F3. Заглавные цифры покрытия измерены БЕЗ обязательной сверки и включают частично живые пролёты — то есть описывают не тот алгоритм, который ратифицируется

Замеры, §3, строки 62-69:

```
| разрешено (≥1 живая строка) | 27 / 37 (73.0%) | 189 / 312 (60.6%) |
```

Предикат — «≥1 живая строка», где «жива» определено (строки 26-28) исключительно как
`<sha> == HEAD`. **Сверка текста в этот предикат не входит.** Она живёт отдельно, в §5, над
ДРУГИМ знаменателем — 58 и 479 **строк**, а не карточек. Сам файл замеров формулирует сверку
как требование к будущему дизайну (строки 116-119: «разрешение ОБЯЗАНО сверить…»), а не как
то, что уже применено к §3.

И арифметика подтверждает, что **частично живые пролёты засчитаны как разрешённые**:
20 + 7 = 27, 162 + 27 = 189 (строки 66-69). Это 7/37 = 18.9% и 27/312 = 8.7% популяции.

Теперь Р2 требует `text` длиной ровно `end-line+1`, а Р5 шаг 2 говорит «сравнить содержимое
**выведенных строк** с `text`». Для частично живого пролёта это не определено:

- строгое чтение (сверять весь пролёт) — все частичные становятся `verify_mismatch`,
  и цифра падает до **20/37 = 54.1%** и **162/312 = 51.9%**;
- мягкое чтение (сверять только живые) — 73%/61% выживает.

Документ не говорит, какое. **Разница — 19 и 9 процентных пунктов на цифре, которую владелец
ратифицирует**, и она же переносится в сквозную оценку §8 («~21–29% codebugs, ~15%
autosorter»).

Это прямое нарушение собственного правила §1б: «цифра, уходящая владельцу, живёт здесь со
своим предикатом; цифра в прозе, которой здесь нет, — дефект». Предикат за 73% — это предикат
БЕЗ Р5, и в таблице он назван честно («≥1 живая строка»), а в §8 подан как результат ядра
целиком.

**Что нужно:** доспецифицировать Р5 шаг 2 для частично живого пролёта явно, и перевыпустить
две цифры под ратифицируемым алгоритмом. Это правка текста, а не механизма, но она обязана
случиться до владельца.

## SERIOUS

### S1. Карточка, заведённая на НЕ ВЛИТОЙ ветке, разрешается в тихий ложный `lost` — rc=0, пустой stderr, без отличимого токена

Рабочий процесс этого репозитория (CLAUDE.md, «main is never edited directly»): **каждая**
карточка заводится из worktree, то есть `reported_at_commit` = вершина ветки. Пока ветка не
влита, этот коммит не предок HEAD у main.

Воспроизведено (`/tmp/bt7-unm`):

```
reported_at_commit=b8a86d76   git merge-base --is-ancestor <commit> HEAD  ->  NO
git blame --reverse -p -C -L 4,4 b8a86d76..HEAD -- f.py
rc=0        stderr: []
b8a86d762247ea9bcf4783b1ba8dd2652bb8fa68 4 4 1
	BUGGY
HEAD=13b64f1b...
```

sha == `reported_at_commit` ≠ HEAD ⇒ по Р5 шагу 1 строка «не жива» ⇒ канал A отвечает
«потеряно». Файл и строка при этом целы и не тронуты.

Словарь §4.3 закрыт и токена для «диапазон не связан предком» в нём нет: ни `unreachable_commit`
(коммит достижим), ни `commit_unreachable`, ни `shallow_history` сюда не подходят. Ответ —
голый `lost`, неотличимый от «код действительно удалён». Для локатора это ровно та пара, которую
путать нельзя.

Стоимость закрытия — одна команда перед blame: `git merge-base --is-ancestor <commit> HEAD`
и новый токен. Но её нет ни в Р5, ни в §4.3, ни в Р8.

Тот же случай — типичный момент чтения: агент работает над карточкой, ветка ещё не влита, он
зовёт `anchor_resolve` из main и получает «код потерян».

### S2. Delete-then-restore (revert / повторное добавление) → ложный `lost` при байт-идентичной живой строке

Воспроизведено (`/tmp/bt7-rev`): `TARGET_R` удалена коммитом, затем `git revert --no-edit`
её возвращает. На HEAD она стоит на строке 3, байт в байт как в `reported_at_commit`.

```
verdict: DEAD (sha=5d2097f6, != HEAD)
blame text at reported line: TARGET_R
ACTUAL line 3 at HEAD:       TARGET_R
```

Канал A говорит «потеряно». Обратите внимание на порядок: porcelain-текст этой записи
СОВПАДАЕТ с сохранённым текстом — но Р5 шаг 1 отбрасывает её раньше, чем шаг 2 вообще
запускается. **Сверка стоит после теста живости, поэтому она умеет только отвергать ответы и
не умеет ни одного спасти.**

Класс реален: revert и повторное добавление — штатные операции, и CLAUDE.md отдельно
описывает работу этого репозитория с `git revert`. Канал B этот случай вытягивает — что
является конкретным аргументом против того, насколько «вторичен» канал B: таблица «только B =
0 и 10/250» измерена на двух корпусах, в которых revert-ов над заякоренными строками просто не
случилось, и +0 п.п. — свойство выборки, а не механизма.

### S3. Поле `filename` в porcelain по умолчанию C-квотируется — ровно тот дефект, который этот репозиторий уже закрывал трижды

Воспроизведено (`/tmp/bt7-q`, путь `src/héllo wörld.py`):

```
$ git blame --reverse -p -C -L 2,2 <B>..HEAD -- 'src/héllo wörld.py' | cat -A
filename "src/h\303\251llo w\303\266rld.py"$

$ git -c core.quotePath=false blame --reverse ... | cat -A
filename src/hM-CM-)llo wM-CM-6rld.py$
```

Р5 шаг 1: «путь берётся из записи `filename` вывода». Этот путь идёт в ответ как
`anchor.path`, он же — тот самый путь, которым отчитывается `moved_file`, и он же уходит в
Р5 шаг 2 на чтение `HEAD:<разрешённый путь>`. Использованный как путь, литерал с кавычками и
восьмеричными escape-ами не существует ⇒ ложный `lost`/`unknown`; показанный человеку —
нечитаем; и инвариант Р2 «`path` — относительный, без `..`» будет применён к строке с
обратными слэшами.

CLAUDE.md фиксирует этот же дефолт трижды (allowlist в pre-commit, `_guard_conflict_markers`,
вывод basename в commit-msg) и оба раза лечит его `-c core.quotePath=false`. Файл замеров о
`core.quotePath` **молчит полностью**; в шаблоне команды (строка 23) флага нет.

Лечение — `git -c core.quotePath=false` на КАЖДОМ вызове blame и show, плюс тест с
не-ASCII путём. Стоит одну строку и должно быть в Р5, а не найдено при реализации.

### S4. Бюджет `max_capture_ms` обещан, но API, на котором его придётся строить, зашивает 10 с — вдвое больше `busy_timeout`

§7.3 обещает: «Бюджет стенных часов (`max_capture_ms`, калибрует Т-a) всё равно обязателен…
исчерпание → `skipped: timeout`», и честно называет последствие: конкурирующий писатель
отваливается по `busy_timeout=5000`, а `SQLITE_BUSY` = 5 не входит в `{8,10,13,14}`, значит
выйдет сырым traceback.

Это **верно** — измерено (`/tmp/bt7_lock.py`): удержание `BEGIN IMMEDIATE` 6 с, конкурент с
`busy_timeout=5000`:

```
competitor RAISED OperationalError: database is locked
  sqlite_errorcode=5  masked=5
  in db._ENVIRONMENTAL_CODES {8,10,13,14}? False
  in db.is_contention {5,6}?               True
  waited 5.00s
```

Проблема в том, что бюджет негде взять. Все существующие подпроцессы зашивают `timeout=10`:

- `src/codebugs/db.py:605` — `git_rev_parse`
- `src/codebugs/provenance.py:234, 361, 403, 524, 724` — все пять вызовов

`src/codebugs/db.py:1261` — `PRAGMA busy_timeout=5000`;
`src/codebugs/db.py:483` — `_ENVIRONMENTAL_CODES = frozenset({8, 10, 13, 14})`.

То есть **дефолтный потолок ровно вдвое выше того, при котором конкурент уже упал сырым
traceback**. Р3 маршрутизирует разрешение корня через публичный API Т-0 (`provenance`), у
которого этот 10 зашит. Документ нигде не называет число для `max_capture_ms` и нигде не
говорит, что оно обязано быть меньше 5000 мс. «Т-a обязан иметь тест на конкуренцию» — это
обязательство поймать, а не обязательство не допустить.

**Второй, неучтённый подпроцесс под локом.** Таблица цен §1б начисляет под лок ОДИН `git show`
(0.95 мс). Но Р3 требует ещё разрешить корень рабочего дерева публичным API Т-0 — это
`git rev-parse --show-toplevel` (`provenance._repo_root`, `provenance.py:71`), то есть второй
подпроцесс, и он тоже под локом. Строка таблицы «`git rev-parse HEAD` — уже платится сегодня»
верна, но вводит в заблуждение: сегодня он платится **вне** лока — `findings.py:2986` его
вызывает, и только `findings.py:2988` открывает соединение. Новый вызов встанет внутрь.

**Чего я НЕ подтвердил и не утверждаю:** зависание подпроцесса мимо `timeout` на этом хосте не
воспроизвелось — см. «Что удержалось».

## WEAKNESS

**W1. §7.1 переоценивает, какую границу держит git.** `git show <commit>:<path>` ограничивает
чтение **закоммиченным содержимым**, а не **безопасным**. Все примеры П5 (`.git/config`,
`.env`, `/etc/passwd`, `../../etc/passwd`, `.codebugs/findings.db`) — неверсионируемые, поэтому
они доказывают containment и ничего не говорят о репозитории, который коммитит `.env`, ключ
или фикстуру с секретами: такой файл читается полностью и попадает вербатим в
`meta.loc.text` и в каждый MCP-ответ. Раздел v4 был про выход за пределы дерева, и git его
действительно заменяет; фраза «весь раздел границы чтения становится не нужен» шире улики.
`MAX_TEXT_BYTES` назван границей размера — верно; но ничто не ограничивает, КАКОЙ
закоммиченный файл может быть процитирован обратно.

**W2. Инвариант пути в Р2 разрешает `./`, а `./` резолвится от cwd процесса, не от корня
репозитория.** Воспроизведено: из подкаталога `sub/` команда `git show HEAD:./normal.py` даёт
`fatal: path 'sub/normal.py' does not exist in 'HEAD'`. Р2 запрещает только `..`. Безвредно
ровно пока cwd захвата и разрешения совпадает с корнем репозитория — что нигде не заявлено как
инвариант, при том что Р3 отдельно запрещает опираться на ambient cwd.

**W3. У `anchor_recapture` нет аналога сверки, и §10 об этом не говорит.** Т-b перечисляет
«сверяется ли с версией строки» среди четырёх точек, которые надо специфицировать, — то есть
это открытый вопрос в одежде решения. S2 показывает, зачем это важно конкретно: после
delete-and-restore ре-захват прочитает ТЕКУЩИЙ текст по СОХРАНЁННЫМ номерам строк и примет его
без сравнения с тем текстом, который он заменяет; якорь тихо перенацелится, а единственный
гейт, которым дизайн гордится (Р5 шаг 2), стоит только на пути ЧТЕНИЯ. Р7 говорит, что отказ
персистируется объектом, Т-b — что неудача не заменяет валидный якорь; но успешный на вид
ре-захват на неверные строки не является неудачей. §10 перечисляет восемь вещей, которых v5 не
делает, и этой среди них нет.

**W4. «126/126 согласия» — не независимое свидетельство про тот случай, ради которого
существует ядро.** Канал B ищет в `HEAD:<ЗАПИСАННЫЙ путь>` (Р5 шаг 3), а канал A может
ответить ДРУГИМ путём. Значит статистика согласия посчитана только по подпопуляции, где путь
не менялся, — ровно там, где оба канала смотрят в один файл. Как свидетельство «оба правы там,
где отвечают» это годится; как аргумент в пользу ядра против канала B — нет, потому что
разделяющий случай в неё структурно не попадает.

**W5. Цена разрешения на большом файле в 7–14 раз выше медианы таблицы, и §7.4 считает по
медиане.** Измерено на autosorter (10 724 коммита), самый большой отслеживаемый Python-файл
`tests/test_architecture.py`, 10 674 строки, глубина истории файла 426 коммитов, диапазон
10 269 коммитов, спан 3 строки: **0.15 с** — и одинаково для `bare`, `-M`, `-C`, `-M -C`,
`-C -C`, `-C -C -C`. Таблица §1б даёт медиану 21.5 мс и max 95 мс для autosorter; 150 мс выше
её max. §7.4 оценивает `anchor_resolve` по всему трекеру в «~7 с (autosorter, 325 карточек)»
исходя из 11–23 мс на карточку; при 150 мс это 49 с. Оценка, уходящая владельцу, не ограничена
худшим случаем — а якорь по определению чаще указывает в большие файлы.

## Что удержалось

Честный список направлений, которые НЕ дали находок — это тоже результат.

**Нелинейная история / мержи — держится, и это стоит знать явно.** Направление 2 не дало ни
одной находки. Проверено исполнением:

- `/tmp/bt7-wf` — реалистичный сценарий этого репозитория: карточка заведена на ветке
  `fix/cb-1` в worktree (`reported_at_commit` = вершина ветки), ветка влита `--no-ff`, затем на
  main приземлились ещё три `--no-ff` мержа. Первопарентная линия — сплошные мержи.
  `blame --reverse -C` даёт **`ALIVE@HEAD`**, строка 4, текст верный.
- `/tmp/bt7-cf` — НАСТОЯЩИЙ конфликтный `--no-ff` мерж (rc=1), разрешённый рукой с сохранением
  целевой строки — то есть та самая «evil»-по-содержанию резолюция, которую git не вычислял
  сам. **`ALIVE@HEAD`**, верно.
- `/tmp/bt7-s1` — обычный `--no-ff` мерж, строка не тронута: верно.
- `/tmp/bt7-s2` — строка законно удалена на влитой ветке: корректно `DEAD`.

Ложный `lost` появляется не от топологии мержей, а от **удаления с последующим
восстановлением** (S2). Формулировать находку как «мержи ломают ядро» было бы неверно.

**П3 подтверждена.** Записи `filename` при `--reverse` действительно несут путь в ПОСЛЕДНЕЙ
ревизии, а не в ревизии названного sha: rename дал `filename new.py`, split дал
`filename split_out.py`. Механика `moved_file` на этом стоит корректно (её проблема — квотирование, S3, и отсутствие продемонстрированного производителя, F2).

**Magic pathspec не эксплуатируется.** `git blame --reverse ... -- ':(glob)normal.py'` и
`-- ':/normal.py'` оба дают `fatal: no such path …`, и `--literal-pathspecs` ничего не меняет:
форма blame с `-L` принимает буквальный путь, а не pathspec. Это реальное отличие от
`provenance.py`, где `--literal-pathspecs` нужен для `git log`/`ls-tree`, и отсутствие флага в
Р5 дефектом НЕ является. Отказ при этом громкий и попадает в `path_absent_at_commit`.

**Выход за пределы репозитория через `moved_file` не получен.** Ни абсолютного пути, ни `..`,
ни пути в подмодуль из поля `filename` получить не удалось — оно репо-относительно по
построению. Единственный дефект этого поля — квотирование (S3).

**Зависание подпроцесса мимо `timeout` не воспроизвелось на этом хосте.** Python 3.14.4:
и `subprocess.run(capture_output=True, timeout=1.0)`, и
`subprocess.check_output(timeout=1.0)` вернулись ровно за 1.00 с даже когда внук держал
открытым pipe stdout (`sh -c 'python3 -c "time.sleep(25)" & exec true'`) — классическая форма,
в которой `communicate()` после `kill()` блокируется. Значит «нужен поток-надзиратель, иначе
бюджет нереализуем» я **не** подтверждаю. Названная в §7.3 угроза (подвисший носитель, D-state)
— случай, который SIGKILL не вытесняет; воспроизвести его в песочнице я не смог и не утверждаю.
Реальная находка по направлению 4 — не зависание, а зашитые 10 с против `busy_timeout` 5 с (S4).

**Цена `-C` не взрывается.** Направление «`-C` на большом файле и длинной истории» дало
отрицательный результат: 0.15 с одинаково для всех шести комбинаций флагов на 10 674-строчном
файле через 10 269 коммитов. `-C` бесплатен по времени. (Он при этом и бесполезен на
storable-спанах — F2; но не по цене.)

**Р8/резолверный шов держится по типам исключений.** `db.run_pre_add_resolvers`
(`db.py:449`) ловит `except Exception`, а `subprocess.TimeoutExpired` ⊂ `SubprocessError` ⊂
`Exception`, так что закрытая таблица Р8 действительно перехватывает исчерпание бюджета и не
уходит в `resolver_errors`. `_ResolverBrokeTransaction` (`db.py:433-443`) поднимается ВНЕ
перехвата, savepoint именуется nonce'ом — обход шва подпроцессом не строится.

**П9 держится.** `_derive_fingerprint` (`findings.py:946`) действительно раньше
`run_pre_add_resolvers` (`findings.py:1058`) внутри `_add_one`; якорь физически не может
повлиять на identity своей строки.

## Вердикт

**Ядро не выдерживает в текущей редакции** — но ломается не там, где документ ожидает.
Механизм reverse blame здравый и на мержах, ренеймах и длинных историях ведёт себя корректно.
Не выдерживают три вещи: (F1) он не знает, в каком он репозитории, и объявленный гейт этого
класса не видит по построению; (F2) единственная демонстрация его главного преимущества
использует якорь, запрещённый собственной константой дизайна; (F3) цифры покрытия, уходящие
владельцу, посчитаны по другому алгоритму, чем ратифицируемый.

Обязательно до передачи владельцу: F1 (идентичность репозитория в `loc` + захват в том же
`project_dir`, что и трекер), F2 (снять тезис №2 и ратификацию `-C` до уровня улики, либо
перемерить `MAX_ANCHOR_LINES`), F3 (доспецифицировать сверку частичного пролёта и
перевыпустить две цифры). S1 и S3 — по одной строке кода каждая, но обе дают тихий ложный
`lost`, поэтому должны попасть в Р5, а не в реализацию.
