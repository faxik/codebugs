# BT-8 — Merge policy дедуп-слияний (В-3 / CB-46): дизайн-док на ратификацию — v2

**Статус: ЗАКРЫТА РАТИФИКАЦИЕЙ ВЛАДЕЛЬЦА 2026-08-22** (реестр болей, коммит `c0e45e7`).
Ответы по §5: развилка — **ОСТАВИТЬ КАК ЕСТЬ + СЧИТАТЬ ОТКАЗЫ** (политика по замеренному
спросу — тот же приём, что с `moved_file` в BT-7); backfill отпечатков — **НЕ ВЫВОДИТЬ**;
статус слитой карточки — **`merged` как НАПРАВЛЕНИЕ**, строится только вместе с политикой.
Из документа вниз уходит РОВНО ОДИН механический юнит: счётчик отказов «отпечаток занят
живой CB-N», читаемый через `query`. Всё остальное ниже — обоснование этого решения и
варианты, которые владелец отклонил; текст сохраняется как запись выбора, а не как план.

**Итог для читателя, пришедшего сюда позже:** документ спрашивал три вещи и получил ответ
«не строить политику, пока не измерен спрос на неё». Это ратифицированный выбор, а не
отсутствие решения.

**Статус разработки документа:** v2, DIR-2, 2026-08-22. v1 прошла ревью в форме, назначенной куратором по
стоимости (узкий числовой аудит + одна структурная атака) и **не выдержала**: 4 FATAL,
10 чисел из 42 не воспроизвелись или несли не тот предикат. Отчёты:
`review-bt8-v1-numeric-audit.md`, `review-bt8-v1-structural-attack.md`.
**v2 = v1 + эти правки.** Что именно было неверно — приложение.

**Замеры (К-5/К-5б/К-5в):** `BT-8-MEASUREMENTS-2026-08-22.md` (`04603fb`, поправки
`14af9d7`) — со скриптами рядом как опровержимой уликой. Одна улика v1 не выполнилась

## 0. Постановка: не один вопрос, а три — и первый уже наступает сам

v1 утверждала: «популяция слияния не существует, она возникнет только при backfill, значит
первый вопрос — сливать ли вообще». **Это опровергнуто исполнением.** Аудит воспроизвёл во
временных трекерах два пути к развилке БЕЗ всякого backfill:

1. **Три обычные команды:** `add` → `update --status wont_fix` → `add` того же наблюдения.
   Второй `add` создаёт recurrence-форк с ТЕМ ЖЕ отпечатком; после этого попытка вернуть
   первую карточку в `open` отказывает: «its fingerprint is held by live finding CB-2
   (resolve or close that one first)».
2. **`restore-csv` в непустой трекер** падает на нарушении уникальности отпечатка.

Отсечены как НЕ ведущие к развилке сегодня: `import-csv` (срезает `auto:`-отпечатки),
`categories-normalize` (перевыводит хеш только у строк с хранимым `auto:v1`), вставка с
явным id (отпечаток остаётся пустым).

**Следствие: backfill — это ОБЪЁМ, а не причина.** Развилка уже доступна штатной работе,
по одной за раз; backfill предъявил бы 6 семей разом. Поэтому вопросов три (§5):
**(1)** что делать с развилкой, которая наступает сама; **(2)** выводить ли отпечатки
задним числом и для какой из трёх подпопуляций; **(3)** чем становится проигравшая строка.

## 1. Популяции: две по механизму и три по составу

### 1.1 По механизму

| | **A. ФОРСИРОВАННАЯ** | **B. СОВЕЩАТЕЛЬНАЯ** |
|---|---|---|
| кто принуждает | частичный уникальный индекс `ux_findings_fingerprint_live` | никто |
| autosorter | **6 живых семей, 36 живых строк**, 12/9/7/4/2/2 | **43 строки** в семьях (`collapse=35` — это сколько ИСЧЕЗНЕТ, а не размер) |
| codebugs | **0** | — |
| решение обязательно | ДА | нет |

**Пересечение полное, а не частичное: все 36 строк A лежат внутри B**; 13-членная
similarity-семья содержит форсированную семью A1 целиком, три семьи из шести совпадают
точно. (v1 писала «восемь id» — занижено.)

### 1.2 По составу — то, чего v1 не видела вовсе

Из 3204 строк autosorter без отпечатка:

| подпопуляция | строк | что с ней делает backfill |
|---|---|---|
| живые | ~1175 | создаёт 6 семей — единственное, о чём говорила v1 |
| **терминальные** (`fixed` 1659, `not_a_bug` 251, `wont_fix` 119) | **2029** | семей НЕ создаёт (индекс их не форсирует), но **вооружает ветку РЕОТКРЫТИЯ на 1659 закрытых карточках** и меняет семантику импорта для всех 3204 |
| с явным id | ~57 | отпечаток пуст by design |

**Владелец, читая v1, видел цену «36 строк» и получил бы изменение поведения на 2029.**
Это правится в §5 расщеплением вопроса №2 по подпопуляциям.

## 2. Природа популяции A — и почему различитель «машинное/авторское» НЕ СУЩЕСТВУЕТ

Все шесть семей — карточки `post_merge_gate_failure`, статус `stale`, описание
`Post-merge gate inconclusive on main @ <sha> (slug: …)`. По существу это машинный шум
одного филера.

**Но в данных этого не видно, и v1 построила на этом ★-рекомендацию, которой нельзя
следовать.** Измерено: у всех 36 строк (и у всех 118 строк категории) **`source = 'human'`**.
Причина в коде, а не совпадение: филер не передаёт `--source` вообще, а умолчание доменной
функции — литерал `"human"`; при этом MCP-тула `add` умолчанием ставит `"claude"`. **Поле
кодирует ПОВЕРХНОСТЬ ВЫЗОВА, а не происхождение, и инвертировано на обоих концах.**
Починить нельзя: `source` ратифицированно неизменяем (BT-4, «первый репортёр»).

Вывод, который приходится принять: **машинность популяции видна человеку и не видна
запросу.** Любое правило, опирающееся на «источник», сегодня отбирает пустое множество.

## 3. Решения — варианты С ЦЕНОЙ

### Р1. К чему применяется политика

| вариант | цена |
|---|---|
| **(а) ★ только популяция A** (форсированная индексом) | минимальный объём; не трогает то, что индекс не принуждает |
| (б) A + B | популяция растёт с 36 до 43 строк — **на семь строк, а не «до сотен», как утверждала v1**; но слияние B есть СУЖДЕНИЕ, а CB-45 намеренно сделал `min_pair_score` диаметром именно чтобы членство в семье НЕ управляло слиянием |
| (в) ~~только машинные источники~~ | **СНЯТ: неисполним** (§2) — различителя в схеме нет |

### Р2. Кто выживает

**Поправка к v1: «расходятся все четыре правила на всех шести семьях» — неверно.**
`occurrence_count = 1` у всех 36 строк, то есть правило «чаще наблюдаемая» вырождено ТАК ЖЕ,
как «по тяжести» (severity везде `low`). Среди НЕвырожденных правил:
**расхождение 5 семей из 6; семья 6 единодушна.**

| правило | цена |
|---|---|
| **(а) ★ старейшая** | сохраняет id, который дольше всех мог попасть в чужие ссылки; но в 5 семьях из 6 самая содержательная карточка — другая |
| (б) богатейшая | сохраняет максимум текста; ломает «первый репортёр» и меняет самый старый id |
| ~~(в) чаще наблюдаемая~~, ~~(г) по тяжести~~ | **вырождены на данных**, не предлагаются |

### Р3. Что происходит с проигравшей — и что слияние ВООБЩЕ ЗАПИСЫВАЕТ

**v1 не определяла слияние как ЗАПИСЬ, и это был её четвёртый FATAL.** Определяю здесь,
по полям выжившей, потому что ратифицированные заморозки BT-4 делают «просто слить»
невыразимым:

| поле выжившей | что с ним | почему |
|---|---|---|
| `source`, `reported_at_commit` | НЕ трогается | ратифицированно заморожено (BT-4) |
| `severity` | НЕ трогается | на данных однороден; общий случай эскалации уже живёт в `_bump_row` |
| `occurrence_count`, `last_seen_at` | **НЕ трогается** | объявлены IMMUTABLE со словами «a manual write would falsify the count» |
| `meta.occurrences` (кольцо) | **НЕ переезжает** | кольцо недостижимо любым пишущим API — то же, что закрыло ринг-хранение в BT-7 |
| `meta.merged_from` | добавляется список id | единственная запись, которую слияние делает на выжившей |

**То есть «слияние» здесь — это НЕ перенос содержимого, а ЗАКРЫТИЕ проигравших со ссылкой.**
Замер ёмкости кольца (максимум семьи 12 при ёмкости 20) в v1 стоял зря: он осмыслен только
при переезде наблюдений, которого не будет.

Чем становится проигравшая:

| вариант | цена |
|---|---|
| **(а) новый терминальный статус `merged`** | честен; но это **не «миграция»**, как писала v1, а **перестройка боевой таблицы**: ограничение CHECK в этой СУБД не изменяется на месте, а существующий мигратор статусов на заполненных базах выходит сразу; плюс две развилки — классификация в ветвящей таблице CB-43 и отображение нового статуса в терминальный исход milestone-элементов |
| (б) `wont_fix` + `meta.merged_into` | ноль миграции; **ложь в статусе**, и ложь дорогая: попадание в `wont_fix` ратифицированно ФОРКАЕТ новую строку при следующем наблюдении (CB-43) — то есть слитые карточки начнут порождать близнецов |
| (в) удалить | необратимо; `.codebugs/` в `.gitignore`, истории у трекера нет |
| (г) не сливать | это ответ на вопрос №2, а не вариант этого решения — вынесен в §5 |

### Р4. Ссылки на id проигравших — цена ВОССТАНОВЛЕНА, v1 её занизила

v1: «3 из 36 (8%)». **Неверно: не измерялся канал milestone items — тот, который CB-46
называет ПЕРВЫМ.** Измерено лично, после того как первый прогон обрезал выдачу
(`--limit 400`): очередь триажа содержит 1114 строк, и **36 из 36 наших id там**.

**Значит при любом правиле выживания 30 элементов очереди триажа будут указывать на слитые
id.** Опасение CB-46 восстановлено в полном объёме.

| вариант | цена |
|---|---|
| **(а) ★ реконсилировать очередь в той же транзакции** | требует, чтобы слияние шло через путь, ВЫЗЫВАЮЩИЙ status-change хуки — иначе живые claim-ы и открытые элементы очереди останутся висеть, а это форма CB-26 (неремонтируемое состояние) |
| (б) оставить висеть | 30 строк очереди указывают в никуда; очередь и есть главный потребитель |
| (в) не сливать те строки, на которые ссылаются | отбирает 36 из 36 — то есть запрещает слияние целиком |

**Разрешимость по id вариантом НЕ является:** `get_finding` — голый `SELECT … WHERE id = ?`
без предиката по статусу, то есть проигравшая карточка отвечает уже сегодня и решения не
требует. Настоящий остаток — что нефильтрованный `query` вернёт архивных близнецов; он
назван в §4, а не выдан за решение.

### Р5. Дисциплина применения — это ЗАПРОС ИСКЛЮЧЕНИЯ, а не наследование

**v1 объявила дисциплину «не требующей ратификации». Это был третий FATAL.** CB-61
ратифицирована владельцем 2026-08-20 и говорит дословно: коллизии **REPORTED AND STOP,
never auto-merged** — если состояние после свёртки поставило бы **две ЖИВЫЕ строки на один
отпечаток**, прогон не пишет ничего. **Это буквально определение популяции A.**

Значит любая политика слияния — **исключение из действующей ратификации**, и просить его
надо вслух, а не прятать в разделе «ратификация не нужна».

И второе: **инструмента dry-run для популяции A НЕ СУЩЕСТВУЕТ.** `similarity-report` —
инструмент популяции B; доказательство в самом замере, где для A пришлось писать
одноразовый скрипт. Его создание — часть цены любого «да».

## 4. Чего документ НЕ решает

1. Не решает за владельца ни один из трёх вопросов §5.
2. Не проектирует переадресацию id.
3. Не отвечает, что делать с нефильтрованным `query`, возвращающим архивных близнецов.
4. Не проверяем на codebugs — там ноль по всем осям; всё опирается на один трекер.
5. Не оценивает популяцию B как кандидата на слияние — только называет её размер.

## 5. Вопросы владельцу (через куратора, каждый собран с нуля)

**№1. Развилка уже наступает сама — что делать, когда она наступит?**
Сегодня три обычные команды (`add` → закрыть как «не чиним» → снова `add` того же) приводят
к состоянию, где вернуть первую карточку в работу нельзя: трекер отвечает «её отпечаток
занят живой карточкой CB-N, закройте сначала ту». Это не гипотеза — воспроизведено.
**Цена «оставить как есть»:** отказ честный и громкий, человек разбирается руками; частота
неизвестна, но путь открыт штатной работе.
**Цена «сделать политику»:** см. вопросы №2 и №3 — она стоит перестройки таблицы либо лжи
в статусе.
— оставить как есть / сделать политику.

**№2. Выводить ли отпечатки задним числом — и для каких карточек?**
Это ОБЪЁМ, а не причина: он предъявит разом то, что иначе приходит по одной.
Три разные подпопуляции с разной ценой:
- **живые (~1175)** → появятся 6 семей, 36 карточек, из них 30 придётся закрыть;
- **терминальные (2029, из них 1659 «исправлено»)** → семей не создадут, но **включат
  ветку реоткрытия**: повторная подача того же наблюдения начнёт ВОСКРЕШАТЬ закрытые
  карточки вместо заведения новых;
- **с явным id (~57)** → не затрагиваются by design.
— не выводить / только живым / живым и терминальным.

**№3. Чем становится карточка, которую слили?**
Честного статуса нет: `fixed`, `not_a_bug`, `wont_fix` — все три лгут о том, что произошло.
**Цена нового статуса `merged`:** это не правка словаря, а перестройка боевой таблицы
(ограничение в этой СУБД не изменяется на месте) плюс два решения о том, как новый статус
считать в очередях.
**Цена `wont_fix` с пометкой:** ноль работы — но `wont_fix` в этом трекере ратифицированно
означает «решение принято», и следующая подача того же наблюдения породит НОВУЮ карточку,
то есть слитые близнецы начнут размножаться заново.
— новый статус / `wont_fix` с пометкой / удалять.

## 6. Честные пределы

1. **Один трекер.** codebugs даёт ноль по всем осям.
2. **Популяция A гипотетична как МАССОВОЕ явление** (сегодня живых коллизий нет), но
   развилка по одной — реальна и воспроизведена.
3. **Частота пути №1 не измерена** — известно, что он открыт, не известно, как часто
   случается.
4. **Числа `2029 / 1659 / 251 / 119 / ~1175 / ~57`** взяты из отчёта аудита и мной
   перепроверены не были — в отличие от 36/36 по очереди триажа, `source='human'` и
   `occurrence_count=1`, которые я проверил лично. Названо, чтобы не выдавать чужой замер
   за свой.
5. **`threshold=0.7`** откалиброван под CB-45, а не под слияние.
6. **Цена «не делать»** в v1 опиралась на «36 близнецов за месяц»; на деле 115 из 118 строк
   категории созданы ДО того, как заработала функция идентичности, а все 3 созданные после
   несут отпечаток и дали связанный `recurrence_of`, а не безымянный дубль. **То есть
   цифра описывала до-идентичный режим и в аргументе «что будет дальше» неприменима.**

## Приложение: правки v1 → v2

| правка | что её вынудило |
|---|---|
| «популяция возникнет только при backfill» → **развилка наступает сама** | воспроизведено тремя обычными командами и `restore-csv` |
| один вопрос владельцу → **три** | backfill накрывал три подпопуляции, а цену называл для одной |
| ★ «политика только для машинных источников» → **вариант снят** | `source='human'` у всех 36 и у всех 118 строк категории; поле кодирует поверхность вызова, а не происхождение, и ратифицированно неизменяемо |
| «расходятся 4 правила на 6 семьях» → **5 из 6 среди невырожденных** | `occurrence_count=1` у всех 36 — правило «чаще наблюдаемая» вырождено так же, как «по тяжести» |
| «3 из 36 висячих ссылок» → **36 из 36** | не измерялся канал milestone items, который CB-46 называет первым; первый прогон вдобавок обрезал выдачу |
| «0 в истории git» → **0 в сообщениях коммитов, ≥6 по дереву** | предикат был уже утверждения |
| Р5 «ратификация не нужна» → **запрос исключения из CB-61** | CB-61 ратифицирована и запрещает авто-слияние ровно этой популяции |
| «dry-run уже существует» → **для A не существует** | `similarity-report` обслуживает популяцию B; для A пришлось писать одноразовый скрипт |
| слияние не определено → **определено по полям, как ЗАКРЫТИЕ со ссылкой** | заморозки BT-4 делают перенос содержимого невыразимым; замер кольца оказался ненужным |
| «популяция B — сотни» → **43** | завышено на порядок, а это была единственная причина отвергнуть вариант (б) |
| Р4(а) «оставить разрешимыми» как решение → **снято** | `get_finding` не фильтрует по статусу, разрешимость есть уже сегодня |
| «новый статус = миграция» → **перестройка боевой таблицы + две развилки** | ограничение CHECK не изменяется на месте, мигратор на заполненных базах выходит сразу |
| улика «0 в relations» → **команда не выполнялась** | у верба флаг `--entity-id`, а не `--id`; К-5в поймал это в первом же применении |
