# BT-5 — Attention-блок в ответе дедупа (дизайн-скетч)

Большая задача направления DIR-2 «Identity находок». Заведена 2026-08-20 держателем DIR-2.
**Статус процесса: дизайн-скетч — на adversarial-review-x2, затем владельцу.**
**Рамка РАТИФИЦИРОВАНА владельцем 2026-08-20** (вместе с ратификацией BT-4): поля
расхождения — структурированные, из УЖЕ ЗАПИСАННЫХ фактов; порог — только серьёзные
сигналы (эскалация / категорийное расхождение / dismissed-близнец); **никакого LLM внутри
трекера**; текст-инструкция — вторым шагом по замеренному спросу. Скетч решает форму
внутри этой рамки, не рамку.

## Замысел

Дедуп молчалив: `add`, попавший в живую карту, возвращает `was_new: false` и строку — и
филер (агентная сессия) обычно не смотрит дальше. Серьёзное расхождение наблюдения с
хранимой картой — то, что наблюдение УЖЕ изменило или должно было изменить прочтение
карты — тонет в теле ответа. Attention-блок делает серьёзный сигнал структурным: его не
надо вычитывать из diff'а полей, он назван.

## Нерешённое решение (одно)

Форма attention-блока: состав полей на сигнал, имя и место в ответе, какие пути `add` его
несут, и точная граница «серьёзного» внутри ратифицированного порога.

## Предпосылки (добыты DIR-2 2026-08-20 лично; строки могут уехать с посадкой Т-8/Т-9 — сверять по символам)

- Ответ `add` сегодня: строка карты + `was_new` + `dedup_action`
  (`created|bumped|reopened`) — наблюдалось в живых вызовах MCP этой сессии (CB-113..115).
- Эскалация severity вычисляется в `_escalated_severity` (`findings.py:505-518`, читал
  сам) и пишется бампом (CB-52); ОБА значения — хранимое и наблюдённое — в руках
  `_bump_row` в момент ответа. Факт «эскалировало» сегодня растворён: виден только как
  изменившееся поле строки.
- Категория наблюдения и категория строки обе известны `_add_one` в момент бампа
  (наблюдённая — параметр, хранимая — в `row`); расхождение возможно только при
  caller-supplied fingerprint (иначе категория — вход дериватного хеша и совпадает).
  Сегодня расхождение бесследно (CB-113, кросс-чека нет); после посадки строки `category`
  контракта BT-4 (юнит Т-10) ring понесёт категорию наблюдения.
- Dismissed-близнец: fingerprint-hit на `wont_fix`/`not_a_bug` заводит НОВУЮ строку с
  `meta.recurrence_of` (CB-43, ветка 3). Факт записан, но в ответе не выделен: клиент
  должен сам заметить ключ в meta.
- Рамка «из записанных фактов» выполнима для всех трёх сигналов без новых записей: все
  три факта либо уже в ответе растворены, либо вычисляются из пары (наблюдение, строка),
  которая в руках кода в момент ответа.

## Предлагаемая форма (рекомендация; варианты с ценой — ниже)

Поле `attention: [...]` в ответе `add`/`batch_add` (и только там — это сигнал ФИЛЕРУ в
момент наблюдения, не состояние карты): список структурированных записей, ПУСТОЙ список
опускается (нет поля — нет сигнала; falsey-ловушек у отсутствующего ключа меньше, чем у
`[]` против CB-25-шейпа на клиентах).

Три типа записей (закрытый словарь; расширение = новое решение):
1. `{"signal": "severity_escalated", "from": "low", "to": "critical"}` — бамп поднял
   severity (CB-52-эскалация реально сработала, не просто «наблюдение было серьёзнее»).
2. `{"signal": "category_divergence", "observed": "silent_failure", "stored":
   "missing_validation"}` — только при caller-supplied fingerprint и только при
   неравенстве ПОСЛЕ нормализации (Т-3): расхождение написаний — не сигнал, расхождение
   имён — сигнал.
3. `{"signal": "dismissed_twin", "recurrence_of": "CB-N", "prior_status": "wont_fix"}` —
   на recurrence-ветке: новая строка заведена, потому что близнец был решён «не чинить»;
   филер должен знать, что решение уже принималось.

Порог — ровно эти три; НЕ сигналы (названо, чтобы не расползлось): обычный бамп, новый
тег, изменившийся файл/описание, reopen как таковой (он уже виден `dedup_action:
"reopened"`), similarity-аннотации (`meta.similar_to` — annotate-only контракт CB-45).

## Варианты и цена

- **(а) Рекомендую: `attention` в ответе `add`/`batch_add`, отсутствует при пустоте.**
  Цена: изменение формы ответа двух инструментов (wire golden; MCP-клиенты, читающие
  ответ строго, получают новый ключ — аддитивно, но задокументировать в CHANGELOG);
  `batch_add` несёт блок per-row.
- **(б) Стакать сигналы в `meta` карты.** Отвергаю: это состояние КАРТЫ, а сигнал —
  момент НАБЛЮДЕНИЯ; в meta он гниёт (кто снимает?), плодит write-объём и повторяет
  CB-26-шейп (производное состояние без снимающего).
- **(в) Отдельный инструмент «what needs attention».** Отвергаю как первый шаг: это
  очередь со своим жизненным циклом — тяжелее рамки; по замеренному спросу может стать
  вторым шагом вместе с текст-инструкцией.

## Не-цели (рамка владельца, повторено чтобы x2 атаковал форму, а не рамку)

Никакого LLM в трекере; никакой текст-инструкции в этом шаге; никакой новой таблицы или
очереди; никакого сигнала ниже порога «серьёзное».

## Процесс

1. adversarial-review-x2 этого скетча (атаковать против кода: форма ответа `add`,
   доступность всех трёх фактов в момент ответа, `batch_add`-угол, импортный угол —
   импорт не наблюдение: несёт ли импортный бамп attention? предложение: НЕТ, симметрично
   `escalate=False`/`promote_tags=False`; голден/CHANGELOG-обязательства).
   Учесть in-flight: Т-9 (tags union) меняет `_bump_row` — сверять по символам.
2. Владельцу — форма (а) с ценой, батч-канал.
3. После ратификации — один юнит посадки; зависимость от Т-10 только у сигнала №2
   (категорийное расхождение сегодня вычислимо и без ринга — из пары в руках, — так что
   жёсткой зависимости нет; порядок юнитов решит менеджер).
