# BT-5 — Attention-блок в ответе дедупа (v2, после x2-ревью)

Большая задача направления DIR-2 «Identity находок». v1 (скетч 2026-08-20) провалила
adversarial-review-x2 — судья: **4/10, две из пяти предпосылок фактически неверны, одна
треть сигнального словаря мертва по собственному правилу исключения** — и перестроена по
девяти обязательным правкам тем же днём. Отчёты: `review-x2-bt5-{opus-attack,codex-attack,
defender,judge-verdict}.md`. **Статус: v2 — на ратификацию владельцу** (батч-канал).
Рамка ратифицирована ранее и не менялась: структурированные поля из уже записанных фактов;
порог — только серьёзные сигналы; никакого LLM в трекере; текст-инструкция — вторым шагом
по замеренному спросу.

## Замысел (не изменился)

Дедуп молчалив: серьёзное расхождение наблюдения с хранимой картой тонет в теле ответа.
Attention-блок делает серьёзный сигнал структурным и top-level — его не надо вычитывать
из глубины ответа.

## Предпосылки v2 (из branch-таблицы, не из наблюдённых вызовов; верифицированы тремя агентами ревью и судьёй лично)

- `dedup_action` имеет **четыре** значения: `created | bumped | reopened |
  recurrence_of_closed`; recurrence-ветка возвращает **`was_new: True`** (insert-путь) с
  `meta.recurrence_of` — v1 знала три значения и ошибалась о `was_new`.
- Ответ `add` — целиком сконвертированная строка + два response-only ключа (`was_new`,
  `dedup_action`), безусловных; `batch_add` — список таких словарей (на проводе — две
  формы: unstructured flatten и `{result: [...]}`).
- Pre-эскалационная severity умирает локалом внутри `_bump_row` (`RETURNING *` возвращает
  пост-строку); `_finalize_add` — единственный конструктор ответа над позиционным
  4-кортежем (splat в `batch_add`). «Оба значения в руках в момент ответа» v1 — ложь;
  подъём факта требует нового внутреннего outcome-канала.
- Изначально файленная severity НЕ пишется в ring (insert-путь не пишет occurrence-запись),
  колонка держит max — эскалацию ЭТОГО наблюдения из ответа восстановить нельзя. Это
  единственный подлинно растворённый факт из трёх ратифицированных сигналов.
- Импорт структурно не достигает `_finalize_add` (возвращает счётчики) — опт-аут-флаг не
  нужен ПО ПОСТРОЕНИЮ; пиновать тестом, не флагом.
- Wire golden НЕ гейтит форму ответа (нет outputSchema; на проводе
  `additionalProperties: True`) — единственный реальный гейт: поведенческий MCP-result
  тест, авторится с нуля.

## Форма v2 (вопрос владельцу — два пункта)

### Ядро (рекомендую ратифицировать): один сигнал `severity_escalated`

`attention: []` — **всегда присутствует** в ответе `add`/`batch_add` (прецедент:
`claims._response()` несёт все 15 ключей безусловно; два существующих response-only ключа
рядом — безусловны; отсутствующий ключ схлопывает «оценили, ничего не сработало» с «канала
нет»). Пустой список — норма. Аудитория — MCP-only (CLI ответ не сериализует; заявлено).

Единственная запись ядра: `{"signal": "severity_escalated", "from": "low", "to":
"critical"}` — фиксирует, что ЭТОТ бамп поднял severity (решение `_bump_row`, не повторное
сравнение). Допустима ровно на ветках `bumped` и `reopened`; матрица
допустимости сигнал×ветка ДЕРИВИРУЕТСЯ из branch-таблицы и пинуется totality-тестом формы
`TestBranchTotality`; порядок в списке детерминирован, каждый сигнал — не более раза.

**Транспорт (реальная цена ядра):** замороженный `AddOutcome` вместо 4-кортежа (и его
splat в `batch_add`), `BumpOutcome` из `_bump_row`, несущий его же решение `escalated` —
один предикат, второго сравнения severity не существует (правило CB-41/CB-52). Сигналы
захватываются ВНУТРИ транзакции; `_finalize_add` остаётся механическим (пост-коммитный
коррапт-путь не приобретает новых отказов). Это осознанный разворот решения
`_import_would_reopen` («не давать `_add_one` новый outcome») — его реальное содержание
«не менять форму ОТВЕТА» соблюдено (кортеж module-private: 3 внутренних вызова + 1
тестовый monkeypatch); докстринг обновляется тем же юнитом с цитатой разворота.

**Гарды юнита:** поведенческий MCP-result тест (обе wire-формы batch); ратчет
«response-only ключи ∩ колонки findings = ∅» (задним числом покрывает
`was_new`/`dedup_action` — CB-119); пин «хуки до мутации ответного словаря» (CB-119); пин
«импорт не несёт attention» (по построению); CHANGELOG. Wire golden движется только
докстрингами — НЕ заявлять его гейтом формы.

### Условное дополнение (владелец выбирает: да/нет): сигнал `category_divergence`

`{"signal": "category_divergence", "observed": ..., "stored": ...}` — **жёсткая
зависимость: только ПОСЛЕ посадки Т-10** (category в ring; до неё сигнал утверждал бы
факт, не записанный нигде — нарушение рамки «из записанных фактов», кросс-модельно
подтверждено). Обоснование ЧЕСТНОЕ и более слабое, чем у ядра: после Т-10 расхождение
выводимо из двух полей одного ответа (колонка vs `meta.occurrences[-1].category`) — сигнал
не создаёт факт, а ИМЕНУЕТ top-level факт, зарытый в ринге, который филеры доказуемо не
читают. Популяция ограничена гейтом CB-60 (только между категориями, которые гейт
пропустил); сравнение — normalize-обе-стороны, non-string хранимое — skip (политика
`_existing_categories`); provenance-булево снимается на входе наблюдения (после деривации
`fingerprint` non-None в обоих случаях; live-экспозиция — restore и explicit-id строки).
Если владелец говорит «нет» — ядро самодостаточно.

### Сигнал №3 (`dismissed_twin`) — УДАЛЁН; letter-fix, признан судьёй честным

Ратифицированный замысел «филер узнаёт, что решение уже принималось» УЖЕ несут три
структурных носителя: top-level `dedup_action: "recurrence_of_closed"` (то самое поле,
которым рамка исключает reopen), `meta.recurrence_of` (всегда) и `meta.similar_to`
c `{id, score, status}` (доминантный путь, score 1.0 по построению на дериватном
fingerprint). Владелец ратифицировал ПОРОГ, не носитель; форма — мандат этого скетча.
Замена — **опция (г), карта CB-118**: докстрочные строки `add`/`batch_add`, именующие
`recurrence_of_closed` (golden движется описаниями) — обязана лечь ВМЕСТЕ с посадкой ядра,
иначе недокументированный носитель тихо регрессирует замысел. **Остаток назван честно:**
на путях supplied-fingerprint-с-непохожим-текстом и sub-40-символьных описаний статус
близнеца в ответе отсутствует — он в одном `get` по `meta.recurrence_of`.
