# L3-BRIEF DIR-1 / Т-27 — CB-135: `.python-version` как единый источник + fail-closed отказ finish'а при расхождении

Автор брифа: держатель DIR-1 (уровень (2)), 2026-08-22. Исполнитель: менеджер (3), модель opus.
Карта: **CB-135** (`uv run codebugs get CB-135` — читать целиком). Родня: CB-121 (та же семья
«протестированное состояние ≠ приземлённое»), CB-134 (красный на 3.14).
Пакет куратора DIR-1 сессии 5, пункт 1б. **Диспетчеризуется после посадки Т-26** — версию пина
выбирает измерение Т-26, а не этот бриф.

## §1. Замысел (ратифицировано куратором как решение по Э-13 — форма не пересматривается)

Гейт интеграции прогоняет сьют **под интерпретатором worktree**, а работа приземляется в **main**.
Это два разных утверждения, и 2026-08-22 они разошлись: менеджер Т-25 отчитался «1943 passed»
(worktree, 3.13.3), а тот же сьют на приземлённом main под документированной командой дал
«1 failed, 1942 passed» (3.14.4). Красное существовало на main **до** мерджа и было невидимо
**каждому** finish'у. Это Н1: гард, докладывающий «чисто», потому что смотрел не туда.

**Форма фикса ратифицирована куратором и не подлежит замене:** сделать расходящееся состояние
непредставимым (**пин интерпретатора в `.python-version`** — один источник для main, каждого
worktree и CI) **плюс fail-closed отказ `worktree-finish.sh` при расхождении версий** worktree и
main — **отказ, а не предупреждение**, в форме `_guard_enforcement_armed`.
**Отвергнуто куратором, не переоткрывать:** «алярм после мержа» (гейт, описанный лучше, чем ведёт
себя) и «записать в CLAUDE.md, что зелёное worktree не есть зелёное main» (проза не энфорсит
прозу — урок CB-50).

## §2. Измеренные факты, от которых отталкиваешься (перепроверь, не наследуй)

Держатель измерил лично 2026-08-22 на main `11628cd`:

- `.python-version` в репозитории **отсутствует**; `pyproject.toml` несёт
  `requires-python = ">=3.11"` — то есть допущено всё от 3.11 до 3.15b.
- main: `uv run python -V` = **3.14.4**; `.venv/bin/python -> /usr/bin/python3.14`,
  `pyvenv.cfg: version_info = 3.14.4`.
- Свежий worktree (`tools/worktree-setup.sh`, шаг `[3/5] uv sync --extra dev`) = **3.13.3**
  (uv-managed `~/.local/share/uv/python/cpython-3.13.3-…`).
- **CI — третье непинованное дерево**: `.github/workflows/ci.yml` использует
  `astral-sh/setup-uv@v5` и **не задаёт версию python** вообще.
- `.gitignore` пинует только `.venv/` — `.python-version` коммитится нормально.

## §3. Гипотеза (преflight вправе предложить лучшую — и обязан назвать, если предлагает)

**(а) Пин.** `.python-version` в корне репозитория даёт `uv` один источник для main, каждого
worktree и CI. Версия — **та, на которой сьют зелёный на ОБОИХ деревьях по измерению Т-26**.
Если после Т-26 зелены обе — пинуй **3.14** (системный интерпретатор, на котором сегодня стоит
main; минимум сюрприза и минимум переустановок), и **запиши это решение с причиной**, чтобы
следующая сессия не передобывала. Гранулярность (`3.14` против `3.14.4`) — твой выбор, но
**назови цену обеих**: `MAJOR.MINOR` допускает разные patch между машинами и переживает
обновление системного python; полный pin ловит 3.13.3 против 3.13.14, но требует, чтобы этот
patch был доступен uv в CI.

**(б) Гард.** Новый `_guard_*` в `tools/_guards.sh`, вызываемый из `worktree-finish.sh` через
`|| exit $?`, сравнивает интерпретатор, **которым реально гоняется сьют**, в worktree и в main, и
**отказывает** при расхождении новым кодом выхода, называя в тексте отказа команду починки.

## §4. Ловушки — каждая названа потому, что мимо неё легко пройти

1. **Пин НЕ перестраивает существующие `.venv`.** После посадки main продолжит нести
   3.14.4-окружение, пока кто-то не выполнит `uv sync --extra dev` в main. Значит: (i) отказ
   гарда обязан **называть эту команду дословно**, иначе гард превращается в стену, а не в
   диагностику; (ii) **этому юниту разрешено** выполнить `uv sync --extra dev` в main после
   мерджа — это единственное разрешение на пересборку окружения в репозитории, и оно обязано
   быть названо в возврате вместе с тем, что стало с версией.
2. **Гард обязан быть fail-closed в форме `_guard_enforcement_armed`.** Невозможность узнать
   версию (нет `.venv`, `uv` недоступен, пустой вывод, ненулевой rc) — **отказ**, а не «версии
   совпали». «Гард, доложивший чисто, потому что не смог посмотреть» — ровно тот дефект, который
   этот юнит чинит; воспроизвести обе стороны в тесте.
3. **Сравнивай то, что гоняет сьют.** Финиш гоняет `uv run --extra dev python -m pytest` в
   worktree; значит сравниваемое значение берётся тем же путём (`uv run --extra dev python -V`
   или эквивалент), а не `python3 -V` с PATH. `pyvenv.cfg` допустим как **второй** источник, но
   не как единственный: он описывает окружение, а не то, что `uv` выберет при следующем запуске.
4. **Фаза вызова — тонкая и решающая.** Сверка обязана идти **после форвард-мержа main в
   worktree** (иначе она не увидит `.python-version`, только что пришедший из main) и **до
   дорогого прогона сьюта** (отказ должен стоить секунды, а не ~110 с). Назови выбранную точку
   явно и закрепи структурным тестом на фазу, как это сделано для остальных гардов.
5. **`--skip-checks` не должен отключать гард.** Скрипт уже разделяет «проверки» (ruff, pytest) и
   «гарды безопасности»; это гард. Пин тестом.
6. **Не сузить `requires-python`.** Пин — про среду разработки и гейта, а не про поддерживаемый
   диапазон пакета. `">=3.11"` остаётся, если Т-26 не даст обратного основания; если даёт — это
   отдельное решение, и оно эскалируется мне, а не принимается попутно.
7. **CI связывается пином тоже** — это выигрыш, но проверь, что выбранная версия скачиваема
   `setup-uv` (или что `uv python install` её достанет). Молча покрасневший CI после посадки —
   провал приёмки.
8. **`_guard_enforcement_armed` — образец формы, а не место для правки.** Не расширяй его;
   новый гард — свой.
9. **`CLAUDE.md`**: раздел Workflow обязан назвать `.python-version` единственным источником, а
   таблица энфорсмента — получить строку с **честной** колонкой «refuses with» (это гард, он
   действительно отказывает — в отличие от алярма из Т-28, который в таблицу не попадает).
10. **Мутационная проба** — в точку дефекта, с подтверждением применения мутанта
    (`PYTHONDONTWRITEBYTECODE=1`, чистый `__pycache__`, `grep -c`).

## §5. Приёмка (проверяемо, не «отчитано»)

1. **Свежий worktree и main дают один `uv run python -V`** — проба выполнена реально: создать
   worktree через `tools/worktree-setup.sh`, снять обе версии, показать их в возврате.
2. **Finish с намеренно подменённой версией в worktree отказывает** новым кодом выхода, и текст
   отказа называет команду починки. Проба выполнена, а не рассуждена.
3. **Fail-closed проба**: сделать версию неопределимой (снести `.venv` worktree / убрать `uv` из
   PATH для вызова) → **отказ**, не пропуск.
4. **Структурный тест**: `worktree-finish.sh` вызывает гард с `|| exit $?`, в объявленной фазе; и
   тест, что `--skip-checks` его не отключает.
5. **Полный сьют зелёный на main ПОСЛЕ мерджа** под документированной командой
   `uv run --extra dev python -m pytest tests/ -q` — это и есть смысл юнита; число в возврате.
   (Если Т-26 сел, красного CB-134 там быть не должно.)
6. `ruff check src/ tests/` чисто; `CLAUDE.md` обновлён (Workflow + таблица).

## §6. Границы

- Не трогать `src/` (это была работа Т-26).
- Не переоткрывать отвергнутые куратором формы (алярм-после-мержа как **замена** отказу; запись
  в прозу как единственный механизм).
- Карту CB-135 не закрывать — статус в трекере пишет держатель (2) после приёмки.
