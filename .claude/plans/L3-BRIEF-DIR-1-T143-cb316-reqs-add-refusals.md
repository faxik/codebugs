### Половина (а) — повторный идентификатор требования падает аварией

```
uv run codebugs --tracker-root <пустой каталог> init
uv run codebugs --tracker-root <тот же каталог> reqs-add FR-1 -d "first"    # Added: FR-1
uv run codebugs --tracker-root <тот же каталог> reqs-add FR-1 -d "second"   # ← дефект
```

Второй вызов печатает **полную аварийную трассировку**, заканчивающуюся строкой
`sqlite3.IntegrityError: UNIQUE constraint failed: requirements.id`.

Механизм, целиком: функция `add_requirement` (`src/codebugs/reqs.py:107-161`) — единственная точка
записи требования, общая для обеих поверхностей, — не проверяет существование идентификатора и
ничем не защищает вставку. Единственная защита от дубликата — ограничение `PRIMARY KEY` на колонке
`id` в схеме таблицы (`reqs.py:26`). Нарушение этого ограничения библиотека доступа к базе SQLite
поднимает как исключение класса `sqlite3.IntegrityError`, и оно уходит вызывающему как есть.

**Почему это хуже, чем «некрасивый текст», и почему карта заведена как `high`.** Класс
`sqlite3.IntegrityError` — чужой для пакета: его объявляет стандартная библиотека, а не этот проект.
Единый источник `refusals.CLASSIFICATION` называет его? Нет. Значит по правилу таблицы («класс, не
названный в таблице, — авария, что бы он ни наследовал») он классифицируется как авария. Проверено
вызовом:

```
uv run python -c "import sqlite3; from codebugs import refusals; print(refusals.kind_of(sqlite3.IntegrityError))"
→ crash
```

Адаптер регистрации инструментов `server._RefusalsReachTheClient` переводит в читаемое клиентом
исключение `ToolError` **только** классы, названные отказами. Авария уходит клиенту обезличенной.
А по собственному замеру проекта, записанному в шапке `refusals.py` (строки 11–15), под библиотекой
`mcp` версии 2.1.1 авария доходит до клиента **вовсе без текста**, тогда как под 2.0.0 SDK
приписывает текст исключения к своему сообщению. В окружении разработки установлена 2.0.0, у
владельца — 2.1.1.

**Следствие, которое ты обязан перепроверить экспериментом, а не принять на веру:** то, что корпус
транскриптов за полгода записал как «сырой текст SQLite», на реальной установке владельца, скорее
всего, уже превратилось в полную потерю текста — то есть в тот самый вред, ради которого заводилась
карта CB-310, но на пути, которого её починка принципиально не достаёт: починка несёт текст только
для классов, названных в таблице.

**Улика важности — замер, а не оценка.** Реестр болей `.claude/plans/PAIN-REGISTRY-codebugs.md`,
§1б: в корпусе реальных вызовов за полгода с 2026-03-06 текст
`reqs_add: UNIQUE constraint failed: requirements.id` встретился **38 раз** — второй по частоте
текст отказа после потери текста как таковой.

### Половина (б) — обработчик создания выпал из общего помощника обработки ошибок

```
uv run codebugs --tracker-root <каталог> reqs-add FR-2 -d "x" --priority bogus
```

Печатает полную трассировку, заканчивающуюся `ValueError: Invalid priority: 'bogus'`.

Механизм: обработчик командной строки `_cmd_reqs_add` (`reqs.py:1001-1011`) не обёрнут в общий
помощник `cli.domain_errors`, тогда как соседи по файлу — `_cmd_reqs_update`, `_cmd_reqs_query`,
`_cmd_reqs_get`, `_cmd_reqs_verify` — обёрнуты. Помощник делает ровно две вещи в строго заданном
порядке: сперва пропускает без изменений аварии, которые наследуют от отказов (сегодня это ровно
`json.JSONDecodeError` — падение уже ПОСЛЕ коммита записи, при сериализации ответа), и только затем
ловит отказы по вводу, печатает одну строку в поток ошибок и завершает процесс кодом 1. Оба кортежа
с версии CB-311 выводятся из таблицы `refusals.CLASSIFICATION`, а не пишутся руками.

### Поправка к диагнозу документа ревизии — держатель проверил и опроверг

Документ ревизии и реестр болей называют вторым симптомом текст
`reqs_add: CHECK constraint failed: priority IN (…)` (31 раз за полгода). **Сегодня этот текст
данным путём не воспроизводится.** Резолвер `types.resolve_priority` вызывается в `add_requirement`
первой же строкой тела (`reqs.py:144`) и отбивает недопустимое значение раньше, чем что-либо
доходит до SQL, а кортеж `types.PRIORITIES` (`must`, `should`, `could`) совпадает с ограничением
`CHECK` в схеме (`reqs.py:30`) слово в слово. Эти 31 случай — исторические, из времени до того, как
резолвер встал на путь записи.

**Что из этого следует для тебя.** Требование ревизии «неверное значение из закрытого словаря даёт
одну строку, а не аварийную распечатку» остаётся живым и невыполненным — но его механизм — это
половина (б), отсутствующая обёртка, а вовсе не ограничение схемы. Не ищи ограничение `CHECK` и не
чини его. Это ровно тот класс ошибки, который направление ведёт третью смену подряд и который смена
23 назвала точнее всех: **прибор смотрит на написание и находит написание, а не предмет.**

## 2. Задание

Довести обе половины до состояния, когда отказ на поверхности создания требования — это **отказ со
словами, классифицированный через единый источник**, а не авария; на обеих поверхностях.

Форма решения не продиктована — ниже развилка, которую решаешь ты, и запреты, которые не обсуждаются.

### 2.1. Ратифицированное держателем решение по слою: конвертировать в домене

Отказ доводится до вызывающего **конверсией в доменном слое** — то есть `add_requirement` сама
превращает нарушение ограничения таблицы в исключение, которое таблица классификации уже называет
отказом (контракт модулей записан в `src/codebugs/CLAUDE.md`: «доменные функции поднимают
`ValueError` при негодном вводе и `KeyError` при отсутствии сущности»).

**Строку `sqlite3.IntegrityError` в `refusals.CLASSIFICATION` добавлять ЗАПРЕЩЕНО, и это не вкусовое
предпочтение.** Причина: таблица классифицирует по точному имени класса, но обе границы применяют её
как `except <кортеж>`, а `except` в Python сопоставляет **по наследованию**. Назвав чужой класс
отказом, ты объявишь отказом всякое нарушение всякого ограничения во всём пакете — а в этом дереве
таких мест много, и в большинстве из них сырая строка SQLite человеку — заведомо неверный ответ
(`findings.py` документирует это в восьми местах, например `findings.py:2109` и `:2660`). Это была бы
та самая дыра молчаливого наследования, ради закрытия которой таблица и построена, только этажом
выше. Конверсия в домене даёт то же наблюдаемое поведение и не расширяет ничью границу.

Побочная выгода, ради которой слой выбран именно этот: `add_requirement` — общая точка для обеих
поверхностей, поэтому одна правка закрывает и командную строку, и протокол, что прямо требуется
пунктом 3 критерия приёмки.

### 2.2. Развилка, которую решаешь и защищаешь ты

**Как отказ узнаёт, ЧТО именно нарушено, и как он говорит об этом, не соврав.**

`PRIMARY KEY` — не единственное ограничение, которое может нарушить эта вставка. Колонка
`description` объявлена `NOT NULL`; выясни замером, достижимо ли её нарушение с каждой из двух
поверхностей (и учти, что промежуточный слой `server.install_strict_arguments` проверяет имена
аргументов, но не обязательно их значения). Сообщение «требование FR-1 уже существует», выданное на
нарушение `NOT NULL`, — это ложь, выданная за отказ, и приёмка её не пропустит.

Известные держателю пути, каждый со своей ценой; выбери один или предложи четвёртый, но **выбор
запиши вслух с ценой**:

1. **Различать по коду ошибки библиотеки.** У исключения есть атрибут `sqlite_errorname`
   (`SQLITE_CONSTRAINT_PRIMARYKEY`, `SQLITE_CONSTRAINT_NOTNULL` и так далее). Точно и дёшево. Цена и
   предупреждение: в этом же файле, на строках 678–680, уже записано ратифицированное решение
   CB-99 — не перечислять коды, потому что ревью дважды измерило такой список неверным в обе
   стороны. Тот запрет вынесен про *классификацию* строки как негодной; здесь речь про *выбор
   сообщения*, и в проекте есть прецедент ровно такого разделения (`db.py`, CB-86: неоднозначный код
   разрешается проверкой «for message selection only»). Если идёшь этим путём — объясни в коде, чем
   твой случай отличается от того, что CB-99 запретила, иначе следующий читатель прочтёт это как
   нарушение.
2. **Различать перечитыванием.** Поймать нарушение, затем спросить у базы, есть ли строка с таким
   идентификатором. Транзакция к этому моменту уже откачена, так что чтение безопасно. Цена: лишний
   запрос на пути отказа и check-then-act, который в принципе может дать неверный ответ при
   параллельном писателе (правило CB-24 в `src/codebugs/CLAUDE.md`).
3. **Не различать вовсе.** Одно сообщение, называющее идентификатор и говорящее правду о том, что
   строка отвергнута ограничениями таблицы, без утверждения, каким именно. Цена: человеку с
   опечаткой в дубликате помогает хуже, чем прямое «уже существует».

Что бы ты ни выбрал — **сообщение не имеет права утверждать больше, чем известно**, и тест обязан
это различать: то есть должен существовать случай, где сообщение о дубликате было бы ложью, и тест
обязан краснеть, если код всё-таки его выдаёт.

### 2.4. Требование S-11: единый источник обязан сохранить различие областей

В `refusals.py` три производных кортежа отвечают на разные вопросы: `INPUT_REFUSALS` — то, что ловит
`cli.domain_errors` вокруг одного доменного вызова; `TRACKER_REFUSALS` — то, что ловит внешняя арка
`cli.main`, потому что оно поднимается при ОТКРЫТИИ трекера, вне области действия помощника;
`EXPECTED_REFUSALS` — их объединение, потому что у поверхности MCP граница одна. **Свести их в один
кортеж — регресс, а не упрощение.** Это требование, а не пожелание; оно записано здесь потому, что
проход упрощения — законная часть твоей работы и естественно тянется именно к такому «упрощению».

## 3. Критерий приёмки — дословно из §5 П-1, с проверяющей командой на каждый пункт

Пункты 1 и 2 — это **приёмка того, что уже приземлилось**: их надо подтвердить, а не строить.

1. **Полнота.** Каждый класс, названный в таблице `refusals.CLASSIFICATION`, достижим хотя бы из
   одного инструмента протокола, и намеренное изъятие любого члена краснит проверку.
   Команда: `uv run --extra dev python -m pytest tests/test_refusal_classification.py -q` — вывод
   «N passed». **Мутант обязателен:** удали одну строку таблицы, повтори команду; вывод обязан стать
   красным с именем изъятого класса. Верни строку на место. Запиши в отчёт обе выдачи.

2. **Названный предел, а не обещание.** В документации модуля записано, что классификация идёт по
   точному имени класса, а перехват на границах — по наследованию, поэтому гарантия держится над
   классами, объявленными этим пакетом, и не держится над классом стандартной библиотеки,
   унаследованным от уже классифицированного. Проверяется чтением шапки `refusals.py` — вывод:
   соответствующий абзац присутствует. (Держатель прочитал: абзац на строках 42–54. Твоя задача —
   убедиться, что твоя правка его не сделала ложным.)

3. **Повторный идентификатор требования даёт человекочитаемый отказ на обеих поверхностях.**
   Проверяется: `codebugs reqs-add FR-1 -d x` дважды подряд — вывод второго вызова обязан быть одной
   строкой текста проекта и ненулевым кодом возврата, а не трассировкой; и тот же сценарий через
   инструмент протокола — вывод обязан нести текст, а не обезличенное «ошибка при выполнении
   инструмента».

4. **Неверное значение из закрытого словаря даёт одну строку, а не аварийную распечатку, и на
   командной строке тоже.** Проверяется тем же способом: команда с недопустимым приоритетом, вывод —
   одна строка. (Помни поправку из §1: механизм здесь — половина (б).)

5. **Наблюдаемый клиентом договор об ошибках зафиксирован ДО правки и сверен ПОСЛЕ** (правка судьи
   S-17). Перед началом работы запиши в файл на ветке перечень кодов возврата и форм ответа, которые
   видит клиент на обеих поверхностях; после работы запиши второй и сверь командой сравнения файлов.
   Вывод: либо пусто, либо список расхождений, **каждое из которых объявлено намеренным с причиной
   на строку**.

   **Основание, из-за которого этот пункт обязателен, а не бюрократия:** файл правил подсистемы
   `src/codebugs/CLAUDE.md` сам признаёт, что эталонный снимок схемы протокола не является гейтом на
   форму ответа — «никакой `outputSchema` не снимается, а живая схема несёт
   `additionalProperties: True`, так что расширение было бы гейтом, который не может сработать».
   Значит внутренние тесты могут остаться зелёными при изменении того, что видит клиент.

   Минимальный набор сценариев для обоих снимков (расширь, если найдёшь ещё): удачное создание;
   повторный идентификатор; недопустимый приоритет; недопустимый статус; отсутствующий трекер;
   незаявленное имя аргумента (только протокол). Для каждого — код возврата процесса и форма ответа
   (одна строка текста / трассировка / `ToolError` с текстом / обезличенная ошибка).

6. **Эксперимент на обеих версиях библиотеки протокола.** Пункт 3 в его половине про протокол
   выполняется и записывается **дважды** — под `mcp` 2.0.0 (стоит в окружении) и под 2.1.1 (стоит у
   владельца); если поведение различается, различие записано. Это перенесено сюда из соседнего
   пакета П-2, потому что именно здесь оно решает вопрос: под 2.0.0 текст аварии клиенту приписывает
   SDK, и без прогона на 2.1.1 ты не отличишь настоящую починку от совпадения.
