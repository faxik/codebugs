# BT-7 — Локационный якорь находки (CB-95): дизайн-док на ратификацию владельцу — v2

**Статус:** v2, DIR-2, 2026-08-22 — перестроен после adversarial-review-x2 тем же днём
(v1: вердикт судьи **4/10, REBUILD**; 69 находок, 55 CONCEDE, **16 корроборированы обеими
модельными семьями** — все в четырёх секциях, претендовавших на «измерено»). Направление
судья признал здравым по всем трём осям: контентный якорь как ядро, resolve-on-read,
якорь ≠ вход identity. Отчёты: `review-x2-bt7-{opus-attack,codex-attack,defender,judge-verdict}.md`.
**Итог BT — документ, не код**: ни один юнит вниз до ратификации.
**Карта:** CB-95 (вербатим владельца 2026-08-18: «can we have some more stable and robust
fingerprint of location than just a line in a file? Ideally, with auto-resolution of the
new line»). **Боль:** Б-8.

## 0. Что решается и что НЕТ

**Решается:** что есть локация находки, где она хранится, кто и в какой фазе её
захватывает, кто разрешает её в текущую строку, и где она относительно identity.

**НЕ решается** (ревью в это не тянем): merge policy (В-3/CB-46 — следующая BT); система
координат `file` (CB-93 ратифицирована: от корня worktree); мутабельность
`file`/`description` (CB-21); relations-леджер (**уже приземлён** — `relations.py`, режим
`coderelations`; связь карта↔карта и карта↔код — разные графы). **И названный предел
(C-R12):** `file` — вход `auto:v1`, поэтому переезд находки в другой файл меняет identity
независимо от якоря; якорь стабилизирует ПОИСК внутри карты, а не узнавание карты через
переезд (re-key — отдельный контракт, CB-43 п.6).

## 1. Предпосылки (v1-предпосылки, пережившие проверку двух атакующих, помечены ✓)

П1 ✓. Локация сегодня = `file` (свободный TEXT; координаты от корня worktree с CB-93,
мердж `f0b4010`) + неструктурированные meta-ключи. В `src/` два писателя литерального
`lines` (CSV-импорт; CLI `add -l`) и ноль читателей; но докстринг MCP `add` прямо
приглашает клиентов писать `lines` в meta — писателей системно столько, сколько клиентов,
что и объясняет ≥9 грамматик (§1а).

П2. Реальный набор локационных ключей — **семь**, не три: `lines`, `line`, `sites`,
`site`, `function`, `location` (+ `anchor`, который в autosorter-корпусе ЗАНЯТ под id
карт — см. Р4-rename). v1 пропустила `sites`/`site` (61 строка, самые однозначно
локационные значения) — перевывод §1а сделан по ФОРМЕ значения, не по списку имён.

П3 (исправлена). `provenance.file_status` возвращает `{file_status, reason}`:
`file_status ∈ {current, modified, renamed, deleted, unknown}`; `reason` — закрытый
словарь токенов для `unknown` и СВОБОДНАЯ ПРОЗА для `renamed`/`deleted` (путь назначения
живёт только внутри английской фразы — см. Т-0). Якорь наследует закрытый словарь причин;
«новейшее наблюдение» — НЕ предрешено этой предпосылкой, это решение Р3/в2 (v1 здесь
противоречила собственной рекомендации — FATAL-6).

П4 (исправлена). `auto:v1` = hash(category, file, normalized description); `meta.lines`
не вход. RFC identity graph **D5 объявляет вопрос иммутабельности fingerprint ВНЕ скоупа,
а не решает его** — v1 приписывала D5 «границу». Р1 высказывается только про `auto:v1`.

П5 ✓. BT-4: `file`/`description` observation-frozen; top-level meta — авторское
состояние; «promoted keys — future allowlist by measured demand». Ринг
(`meta.occurrences[*]`) несёт `at, severity, category, file, description, source, tags,
reported_at_commit, reported_at_ref` + `meta` наблюдения; читатель «новейший пригодный с
хвоста» уже ратифицирован и реализован — `provenance._effective_commit` (CB-53).

П6 (усилена исполнением). Резолверный шов CB-45: **регистрация ЕСТЬ резервирование** —
`db.resolver_reserved_meta_keys()` = объединение `meta_keys` всех зарегистрированных
резолверов, и `add(meta={<ключ>: …})` ОТКАЗЫВАЕТ (проверено защитником исполнением, не
чтением); `updatable_keys=(<ключ>,)` открывает ТОЛЬКО update-путь (`similar_to` —
прецедент с причиной CB-26). Патч резолвера — правая сторона `dict.update`, т.е.
резолвер побеждает вызывающего, а не наоборот. Резолверы исполняются под write-lock
(`db.txn` → `run_pre_add_resolvers`, отказ вне транзакции) и ТОЛЬКО на пути вставки —
bump/reopen возвращаются раньше.

П7 ✓. Прецедент авто-захвата: `reported_at_commit = git_rev_parse("HEAD")` если не
передан.

П8 (перевёрнута). «Ловушка `_VOLATILE_KEY_TOKENS`» для вложенного dict НЕ активна: цикл
нормализации обходит только верхний уровень и только `str`-значения. Реальная ловушка —
ОБРАТНАЯ: будущий, кто УПЛОЩИТ якорь (`meta.<key>_commit = "abc…"`), сделает значение
вырезаемым и сменит identity всех несущих строк. Фиксируется запретом на уплощение с
тестом. Плюс структурный факт, на котором держится Р1: `_derive_fingerprint` вызывается
ДО резолверов, так что захваченный якорь физически не может повлиять на отпечаток
собственной строки.

П9 ✓. `file` бывает вне репозитория (каталоги, глобы, абсолютные кросс-репо пути, проза —
в сознательном использовании; CB-88/89/91).

## 3. Решения (строки ратификации; ★ — рекомендация)

**Р1 ★. Якорь НЕ входит в `auto:v1`.** Про `auto:v2` BT-7 не высказывается — версия
отпечатка есть отдельный контракт (CB-43 п.6), D5 оставлен RFC открытым. Гарантия
держится структурно (П8): отпечаток дериваируется до резолверов.

**Р2 ★. Хранение по 2.2(b), ключ — `loc` (НЕ `anchor`: имя занято в живом peer-трекере
под id карт; импорт-strip уронил бы 16 чужих строк молча).** Объект версионирован:
`{v:1, line, end, hash, context_hash, context_before, context_after, text,
captured_at_commit, sites_dropped}` — с блоком ИНВАРИАНТОВ: `v∈{1}` (незнакомая →
`unknown(unsupported_anchor_version)` на чтении, никогда не исключение — restore
сохраняет meta дословно, значит валидация обязана жить на чтении); `line>=1` int-не-bool;
`end>=line`, `end-line+1 <= MAX_ANCHOR_LINES`; хеши — hex фиксированной длины;
`len(text) <= MAX_TEXT_BYTES`; `captured_at_commit` — None|40-hex. Тумбстоун:
`loc: null` легален = «не перезахватывать», читается как `unknown(retracted)`.
Импорт вырезает `loc` (чужой якорь указывает на чужое дерево); restore сохраняет дословно
— обе асимметрии названы, вторая покрыта read-side валидацией.

**Р3 ★. Захват — ДВУХФАЗНЫЙ, вне лока, на КАЖДОМ наблюдении.** Прецедент — ратифицированный
RFC S2: `add`/`batch_add` ДО открытия `db.txn` читают и хешируют (батч — каждый различный
путь ОДИН раз), готовый объект едет в observation; под локом — только валидация и штамп.
TOCTOU-остаток назван и приемлем: якорь — снимок, разрешаемый на чтении, не гейт.
Раскладка: первозахват → top-level `meta.loc` через pre-add-резолвер (модуль `loc.py`,
второе zero-SQL расширение — с оговоркой N-3: прецедент similarity переносится только
при выносе I/O из лока, иначе переносится буква без причины); ре-наблюдение → якорь в
occurrence-entry (`meta.occurrences[*].loc`) через **носитель-шов**: generic pre-lock
«observation enricher» — НОВЫЙ шов, его цена входит в вопрос №2 и в Т-a. Читатель —
новейший пригодный с хвоста, фолбэк на `meta.loc` (= `_effective_commit` дословно).
Ринг-запись несёт `loc` под ОТДЕЛЬНЫМ байтовым капом в духе `_OCC_DESC_CAP` (ринг хранит
до ~20 записей; текст+хеши ×20 без капа раздули бы каждую карту — цена J-1, названная
судьёй); бонус ринга, сказанный вслух: он АВТОМАТИЧЕСКИ наследует import-strip /
restore-verbatim семантику — контракты не изобретаются заново (C-M6).
Ручное ре-якорение: `update_finding(meta_update={"loc": …})` работает благодаря
`updatable_keys=("loc",)` — плюс серверный верб `anchor_recapture <id>` (Т-b), чтобы
никто не строил объект руками.

**Р4 ★. Резервирование — по контракту шва, как он есть:** регистрация резолвера С
`meta_keys=("loc",)` автоматически резервирует ключ на ADD — вызывающий НЕ может подать
`loc` в `add(meta=)`, и это правильно (caller-supplied координата = спуфинг);
`updatable_keys=("loc",)` открывает только update. Аналогия с caller-supplied
`fingerprint` из v1 УДАЛЕНА — она обратной формы (там ядро само обеспечивает caller-wins).

**Р5 ★. Разрешение — на чтении, без записи разрешённой строки.** Поверхности:
`anchor_resolve(finding_id|status|category|file, project_dir=)` — батч-контракт как у
`check_findings`; `staleness_check(anchor=True)` — каждая запись получает ВЛОЖЕННЫЙ ключ
`"anchor": {status: current|moved|lost|ambiguous|unknown, line, end, reason,
resolved_against: {head, path, mtime_ns, size}} | null` (null = якоря нет; вложенный —
чтобы `reason` не имел двух производителей). `confidence` УДАЛЁН (числовая точность без
калибровки поверх статусов — ложная). Биндинг: `project_dir` явный, дефолт через
`db.describe_root()`, НИКОГДА `_ambient_cwd()`; кеш `check_findings` `(file, effective)`
для якоря НЕ используется (рабочее дерево — не функция effective-коммита); свой кеш —
только по замеренной цене. `get` по умолчанию возвращает ХРАНИМЫЙ якорь (чистая БД);
`get(resolve_anchor=True)` — разрешённый; так вербатим-просьба владельца («auto-resolution»)
достижима, а `get`/`query` не приобретают файловый I/O молча.

**Р6 ★. Нормализатор и хеш v1 — специфицированы полностью:** sha256 поверх
`json.dumps([<нормализованные строки>])` (массив, не склейка — сепаратор неоднозначен,
урок `_derive_fingerprint`), усечение до 32 hex как у fingerprint; декод
`errors="replace"`; `\r\n`/`\r`→`\n` ДО хеша; **ведущий отступ → токен глубины, не
стирается** (отступ в Python семантичен; реиндент — это правка, `moved` честнее ложного
`current`); внутренние пробельные раны схлопываются; контекст = N строк до/после,
хешируется ОТДЕЛЬНЫМ массивом БЕЗ якорных строк, ширины записываются в объект;
`MIN_ANCHOR_CHARS` — КАЛИБРУЕТСЯ юнитом по корпусу (урок `MIN_TEXT_LEN=40` similarity),
не выбирается. `context_hash` обязателен при захвате (у границы файла — фактическая
ширина, не null).

## 4. Грамматика захвата (перевыведена по ФОРМЕ; каждая ветвь несёт источник)

Свип-предикат: значение любого meta-ключа, содержащее `NAME.ext:DIGITS`-токен или
int-подобную ссылку. Ветви:
- `line`: bare int / int-строка (98 строк) → одиночная строка.
- `lines` строка: int, `"a-b"`, `"N,M,K-L"` → ПЕРВОЕ место; остальные СЧИТАЮТСЯ в
  `sites_dropped` внутри объекта.
- `lines` список int (контракт libcheck, 206/206): **каждый элемент — ОТДЕЛЬНАЯ строка,
  диапазон НЕ выводится ни при какой длине** (v1 читала len-2 как [min,max] — 76 строк
  получили бы 51-строчные «якоря»); берётся первый элемент, остальные — в `sites_dropped`.
  `[0,0]` отсекается инвариантом `line>=1`.
- `sites`/`site` (61 строка, пропущены v1): та же обработка, что `lines`-строка/список.
- `file:N…`: захватывается ТОЛЬКО при однозначности — ровно один `NAME.ext:`-токен И
  `basename(колонка file) == NAME.ext` (точных совпадений полного пути 2/31 и 0/38 —
  диалект базовых имён); несколько разных имён файлов → пропуск с причиной
  `ambiguous_multisite`. Мера ветви — СОВПАДЕНИЯ, не токены.
- Проза, dict, `function` → пропуск.

**«Первое место — первичный якорь» — КОНВЕНЦИЯ с названной ценой** (полно отвечает 2/32
dogfood-карт), не измеренный факт; `sites_dropped` — счётчик в самом объекте, он же
триггер мульти-якоря/таблицы (2.2(c)). Отказ захвата НИКОГДА не исключение и не
`resolver_errors` (тот остаётся сигналом сломанного резолвера): закрытый словарь причин
`not_a_file | out_of_repo | unreadable | too_large | binary | no_grammar |
ambiguous_multisite`, счёт — через `lost`-rate `anchor_resolve` (вычислим, потому что
популяция = каждое наблюдение), а не через несуществующий канал в `stats`.
Структурные `line=`/`end=` на `add` — отложены (цена на клиентах, владелец не просил), но
честно: цена скрытого недозахвата уже платится, пересмотр — по `sites_dropped`.
Ловушка CLI `--meta` побеждает `-l` — карта класса CB-15, файлится при посадке Т-a.

## 7. Риски и граница

- **Батч:** двухфазность выносит I/O из лока; юнит Т-a обязан замерить 100-членный батч
  с холодным кешем ДО посадки (масштаб: чистый CPU-резолвер уже стоит ~2.4 s/100).
- **§7а. Граница чтения — РЕШЕНИЕ ВЛАДЕЛЬЦА, не унаследованный скоуп.** По умолчанию —
  containment `commonpath == root`, идентичный `file_status`; только `S_ISREG` (зеркало
  таксономии fsio/CB-76 — FIFO/устройство под локом блокирует навсегда); капы ЧИСЛАМИ в
  Т-a: `max_bytes_read` (последовательное чтение до строки — «построчного seek» не
  существует; реальный максимум в корпусе — строка 5708), `max_span_lines`,
  `max_text_bytes`; NUL-детект → `binary`; `errors="replace"`. Чтение ВНЕ worktree
  (кросс-репо абсолютные пути) — CB-89 ратифицировала отказ, CB-91 держит открытым как
  границу доверия «not blocked on code»: BT-7 это решение НЕ принимает — вопрос №4.
  До ответа A-преимущество «вне git» НЕ реализуется, и §2 это говорит.

## 8. Вопросы владельцу (через куратора, каждый собран с нуля)

1. **Пакет ядра ★:** локация = версионированный контентный якорь `meta.loc`
   (хеш+контекст+текст с капами), захватывается сервером при подаче из существующих
   форм `lines`/`line`/`sites` (клиентские контракты не меняются), разрешается на чтении
   отдельным вызовом (каскад: diff-remap → контентный поиск → честный `unknown`), identity
   не трогает. — да / нет / иначе. (Оговорка «обновляется наблюдением» из пакета УБРАНА —
   это вопрос 2.)
2. **Свежесть якоря — трёхвариантный:** (а) только первозахват + ручное ре-якорение —
   цена: якорь старых наблюдений гниёт до ручного вмешательства; (б) bump-шов для
   обновления top-level ключа — цена: новый резолверный контракт на bump-пути (CB-45
   стоила трёх раундов ревью) ИЛИ ядро узнаёт ключ расширения (запрещено CB-45); **(в) ★
   захват на каждом наблюдении в ринг, читатель «новейший пригодный»** — цена: место в
   ограниченном ринге + один новый generic pre-lock шов «обогатитель наблюдения»; зато ноль
   исключений из BT-4, старые карты получают якорь при следующем наблюдении, и все
   §5-триггеры становятся измеримыми. Рекомендация — (в).
3. **Символьный якорь для Python:** сейчас (первая парсерная зависимость пакета) или по
   замеренному `lost`-rate (★).
4. **Граница чтения (новый):** может ли трекер читать и СОХРАНЯТЬ байты файла по
   абсолютному пути вне worktree, названному в данных карты? CB-89 ратифицировала отказ,
   CB-91 держит вопрос открытым как границу доверия. По умолчанию v2 — НЕТ (containment
   как у `file_status`); «да» включает кросс-репо якоря и несёт риск утечки байтов в
   экспортируемую БД (в v1 это был бы arbitrary-file-read через MCP `add` — FATAL-5).

## 9. Нарезка после ратификации (эскиз)

**Т-0:** provenance — публичный path-API (`resolve_in_worktree`) + структурный `new_path`
в вердикте `renamed` (сегодня назначение живёт в прозе `reason`; парсер rename-пар уже

батча. **Т-b:** `anchor_resolve` + `staleness_check(anchor=)` + `anchor_recapture` +
golden. **Т-c:** backfill dry-run (`git show`), опционально.
