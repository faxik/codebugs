## 0. Что решается и что НЕТ

**Решается:** что есть локация находки, где она хранится, кто её захватывает и в какой фазе,
кто разрешает её в текущую строку, где она относительно identity, и где граница чтения.

**НЕ решается:** merge policy (В-3/CB-46); система координат `file` (CB-93 ратифицирована);
мутабельность `file`/`description` (CB-21); relations-леджер (приземлён).

**Названный предел:** `file` — вход `auto:v1`, поэтому переезд находки в другой файл меняет
identity независимо от якоря. Якорь стабилизирует ПОИСК внутри карточки, а не узнавание
карточки; ре-кей — отдельный контракт (CB-43 п.6). Заметьте асимметрию, которая теперь
возникла: **якорь умеет отследить переезд кода в другой файл, а identity карточки — нет.**
Это не дефект якоря, это ровно та граница, которую CB-43 провела сознательно.

## 1. Предпосылки

**✓** — пережила предыдущие раунды; **[исп.]** — проверена ИСПОЛНЕНИЕМ в этой сессии.

**П1 ✓.** Локация сегодня — колонка `file` (свободный TEXT, координаты от корня worktree,
CB-93) плюс неструктурированные meta-ключи семи написаний. Читателей ноль.

**П2 [исп.] — вход для нового ядра В ТРЕКЕРЕ УЖЕ ЕСТЬ.** `reported_at_commit` захватывается
при заведении карточки (`git_rev_parse("HEAD")`, если не передан) и **заморожен по BT-4**
(наблюдение его не двигает; CB-53). То есть «git version», о которой говорит владелец,
уже записана, и ядро не требует новых полей на строке.

**П3 [исп.] — `git blame --reverse` делает ровно то, что описал владелец.**
`git blame --reverse -p -C -L a,b <commit>..HEAD -- <path>`; porcelain при `--reverse`
инвертирован: `<sha> <строка_в_последней_ревизии> <строка_в_исходной>`. Строка жива, если
`<sha>` равен HEAD. Записи `filename` несут **путь в последней ревизии** — им и ловится
переезд. Git 2.53.0.

**П4 [исп., ИСПРАВЛЕНА] — git НЕ ошибается на измеренной популяции; ошибалась мерилка.**
v5 утверждала «0.21% неверных координат» на основании одного случая (CB-3055). Аудит
показал: blame отдал `ignore_rules.py:168`, и там **побайтно** ожидаемый текст — просто
файл ДРУГОЙ, а моя сверка читала записанный путь и игнорировала запись `filename`.
Исправленной сверкой: **58/58 и 479/479 = 100.00%, побайтно, ноль ошибок.**
Побочно это ЕДИНСТВЕННЫЙ реальный переезд в другой файл на живой истории — то есть тот
самый `moved_file`, ради которого вводится статус.
**Следствие для дизайна ОСТАЁТСЯ, но обоснование меняется:** сверка сохраняется не потому,
что git наблюдался неверным, а потому что «ноль из 537» — это отсутствие наблюдений, а не
доказательство невозможности, и цена сверки — одно чтение файла, который уже открыт.

**П4б [исп.] — а вот ТИХИЙ ложный отказ реален, и он бьёт по штатному процессу.**
Карточка, заведённая на НЕВЛИТОЙ ветке (а здесь так заводится каждая), даёт
`git blame --reverse <коммит ветки>..HEAD` с кодом возврата **0**, пустым stderr и
атрибуцией коммиту ветки — то есть тест «жива ⇔ sha == HEAD» отвечает «удалена», тогда как
строка на HEAD жива. Проверено лично. Лечится проверкой предка ДО трейса (Р5).

**П5 [исп.] — захват через хранилище объектов git структурно недостижим для
неверсионируемых файлов.** `git show HEAD:.git/config`, `:.env`, `:/etc/passwd`,
`:../../etc/passwd`, `:.codebugs/findings.db` — все отказывают. Захват v4 читал бы их с
диска: `.git/config` это обычный файл 546 байт, а `.codebugs/findings.db` — **1.5 МБ базы
самого трекера**.

**П6 ✓.** `auto:v1` = sha256 канонического JSON-массива `[category, file,
normalize(description, meta)]`, `ensure_ascii=False`, 32 hex. `meta.lines` не вход.

**П7 ✓ [исп.].** Резолверный шов CB-45: регистрация ЕСТЬ резервирование; `updatable_keys`
открывает только update-путь и **не валидирует ничего**; резолверы бегут под write-lock и
только на пути вставки; предикат `finding_id is None and annotate`.

**П8 [исп.].** Наблюдение, передаваемое резолверу, несёт `file`, `meta`, `description`,
`category`, `at`, `dedup_action` — но **НЕ несёт корня рабочего дерева и не несёт
`reported_at_commit`**. Первое — дефект, найденный третьим раундом; второе — новое
требование этого ядра. Оба закрываются одинаково (Р3).

**П9 [исп.].** Отпечаток дериваируется ДО резолверов (`_derive_fingerprint` раньше
`run_pre_add_resolvers` в `_add_one`), поэтому якорь физически не может повлиять на
identity собственной строки.

**П10 [исп.].** Кольцо наблюдений недостижимо ни одним пишущим API (`occurrences` — ключ
ядра). Поэтому хранение — top-level, как и в v4; per-occurrence отложено с триггером.

**П11 [исп.].** Ре-наблюдений в обоих трекерах ноль (0/129, 0/3300; 0 из 240 после посадки
CB-43), при исправном механизме. Хранение «на каждом наблюдении» обосновывать нечем.

**П12 [исп.].** Честный отказ детектируем: на `--depth 1` клоне `.git/shallow` существует,
и `git blame --reverse <старый>..HEAD` падает с `fatal: Invalid revision range`.

**П13 [исп.] — мержи ядро проходит.** Строка, удалённая в одной ветви `--no-ff` мержа,
атрибутируется не HEAD, то есть корректно читается как удалённая. Проверено мной и
независимо структурной атакой на реалистичной цепочке из четырёх мержей. Это направление
атаки находок НЕ дало, и сказано здесь, потому что первопарентная линия этого репозитория
состоит из мержей целиком.

**П14 [исп.] — репозиторий не самоидентифицируется.** `reported_at_commit` берётся
`git_rev_parse("HEAD")` от cwd процесса, а трекер разрешается своим правилом
(`--repo`/`--tracker-root`/`$CODEBUGS_ROOT`/обход вверх). Между НЕСВЯЗАННЫМИ репозиториями
это отказывает закрыто (проверено: полный и сокращённый SHA autosorter в codebugs не
разрешаются; коллизий 7–9-символьных префиксов на 13 751 коммите ноль). Между
репозиториями с ОБЩИМ ПРЕДКОМ — не отказывает, и сверка поймать это не может по построению,
потому что перечитывает тот же репозиторий, по которому шёл blame. Закрывается Р3.

## 2. Варианты

### 2.1 Каналы разрешения

| | как работает | переживает | ломается | цена | вердикт |
|---|---|---|---|---|---|
| **A. Reverse blame (git) ★ ЯДРО** | от замороженного `reported_at_commit` вперёд по истории до HEAD | переименование файла, сдвиг строк, **вынос кода в другой файл** (опыт §6 замеров), любую правку ВОКРУГ | нет git; shallow-клон; переписанную историю; удаление самих строк | 11–23 ms на чтении | **ядро** |
| **B. Контентный якорь (v4)** | нормализованный хеш строк ищется в текущем файле | правки вокруг, перемещение внутри файла | переезд в ДРУГОЙ файл (ищет в записанном); правку самих строк | 2 ms | **второй канал**, +0 и +4 п.п. |
| **C. Символьный (`ast`)** | (file, qualified symbol) | перемещения, большинство рефакторингов | rename; не-Python; первая парсерная зависимость | — | отложен (владелец: по замеру) |
| **D. History-walk / diff-remap** | `git log -L`, `git diff -U0` | — | — | — | **поглощён каналом A**: A и есть обход истории, но штатным инструментом |

**Что исчезло по сравнению с v4 и почему.** v4 держала C2 (diff-hunk remap) отдельной
строкой и исключала её, потому что переиспользуемого парсера не оказалось. В v5 этой
дилеммы нет: `blame --reverse` делает ту же работу штатной командой, без собственного
парсера hunk-заголовков. **Это прямая выгода от редиректа владельца** — механизм, который
я собирался писать руками и отверг по цене, в git уже есть.

### 2.2 Хранение

Остаётся решение v4: **top-level `meta.loc`** — потому что кольцо наблюдений недостижимо
ни одним пишущим API (П10), а ре-наблюдений в обоих трекерах ноль (П11). Per-occurrence и
таблица `finding_anchors` отложены с вычислимыми триггерами (§5).

## 3. Решения (строки ратификации; ★ — рекомендация)

**Р1 ★. Якорь НЕ входит в `auto:v1`.** Гарантия структурна: отпечаток дериваируется до
резолверов (П9). Значение якоря не живёт в top-level `meta` строкой ни под каким именем
(запрет на уплощение; точная формулировка — приложение).

**Р2 ★. Объект `meta.loc`, версия 2:**

```
{ "v": 2,
  "repo":   <SHA корневого коммита репозитория — идентичность дерева>,
  "commit": <40 hex — ревизия, к которой относятся координаты>,
  "path":   <путь от корня worktree В ТОЙ ревизии>,
  "line":   <int ≥1>, "end": <int ≥line>,
  "text":   [<строки ВЕРБАТИМ из той ревизии>],
  "norm":   "v1",
  "sites_dropped": <int ≥0> }
```

или объект отказа: `{ "v": 2, "skipped": <токен §4.3>, "sites_dropped": <int ≥0> }`.

**`repo` — новое поле v6, и оно закрывает единственный путь к УВЕРЕННО НЕВЕРНОМУ ответу.**
`reported_at_commit` берётся от cwd процесса, а трекер разрешается своим правилом, поэтому
карточка может нести коммит одного дерева, а разрешаться в другом (П14). Между несвязанными
репозиториями это отказывает закрыто, но между репозиториями с ОБЩИМ ПРЕДКОМ — нет, и
сверка поймать это не может, потому что перечитывает то же дерево, по которому шёл blame.
`repo` = SHA корневого коммита; на разрешении он сверяется, при несовпадении —
`unknown(repo_mismatch)`. Цена 8–10 ms, берётся ОДИН раз на процесс и кешируется, иначе
под локом она вдесятеро перекрыла бы сам захват. **Остаточный предел назван:** истинный
форк с той же историей неотличим — но там и код в захваченной ревизии тот же самый,
расхождение начинается только после точки ветвления.

**Три отличия от v4, каждое из замера.**
1. **`commit` и `path` образуют пару координат** — ядру нужна ревизия, а не только путь.
   По умолчанию `commit` = `reported_at_commit` строки; после ре-захвата — та ревизия, из
   которой взят текст.
2. **`text` ХРАНИТСЯ (ратифицировано владельцем) и хранится ВЕРБАТИМ, не нормализованным.**
   Обоснование уточнено замером: текст нужен не чтобы НАЙТИ код — находит git, — а чтобы
   **ПРОВЕРИТЬ ответ git'а** (П4: 0.21% координат уверенно неверны). Вербатим, потому что
   сверять надо с тем, что реально лежит в файле, и потому что человеку показывают его же.
3. **Хешей `hash`/`context_hash` в объекте НЕТ.** Раз текст хранится, хеш из него
   выводится, а два представления одного факта — это лишняя возможность разойтись.
   `norm` называет версию нормализатора, которой пользуется канал B на чтении.

Инварианты проверяются **на ЧТЕНИИ** (restore сохраняет meta дословно, а `updatable_keys`
не валидирует — П7): `v ∈ {1,2}` — незнакомая версия даёт `unknown(unsupported_anchor_version)`,
**никогда исключение**; `commit` — 7..40 hex; `path` — относительный, без `..`;
`line` int-не-bool ≥1; `end ≥ line`; `end-line+1 ≤ MAX_ANCHOR_LINES`; `text` — список строк,
длиной ровно `end-line+1`, суммарно ≤ `MAX_TEXT_BYTES` в UTF-8. Нарушение → `unknown(invalid_anchor)`.

Тумбстоун `loc: null` = «не перезахватывать», читается как `unknown(retracted)`; при
top-level хранении он действительно работает.

**Р3 ★. Захват — в существующем резолверном шве CB-45, из ХРАНИЛИЩА GIT, под локом.**
Модуль `loc.py` регистрируется резолвером с `meta_keys=("loc",)`, `updatable_keys=("loc",)`.
Он берёт путь и пролёт из наблюдения, ревизию — из `reported_at_commit`, и читает текст
через `git show <commit>:<path>`.

**Цена и почему она приемлема — измерено:** маржинальная цена якоря под локом это один
`git show` ≈ **0.95 ms**, при том что лок уже держит 8–16 ms работы резолвера similarity.
`reported_at_commit` уже захватывается сегодня. **Трейс истории под локом НЕ выполняется
вообще** — он живёт на чтении.

**Захват обязан идти в ТОМ ЖЕ дереве, что и трекер, иначе fail-closed.** Сегодня
`reported_at_commit` берётся от cwd процесса — то есть ничем не связан с репозиторием, к
которому относится карточка. В v6 ревизия и корень берутся из ОДНОГО источника —
разрешённого `project_dir`; если он не разрешается в git-дерево, якорь не захватывается
(`skipped: no_root`), а `reported_at_commit` остаётся как есть, потому что он не наша
собственность (BT-4 заморозил его).

**Правки сигнатур названы числом, лозунга «ноль» здесь нет:** наблюдение должно донести до
резолвера ревизию, корень и идентичность репозитория — это **один необязательный
параметр `project_dir` на `add_finding`/`batch_add_findings` и три ключа в литерале
наблюдения**. Корень разрешается публичным API Т-0 в worktree-корень, НИКОГДА через
`db.describe_root()` (в linked worktree он возвращает корень main — проверено) и НИКОГДА
через ambient cwd; при неразрешимости — `skipped: no_root`, fail-closed.

**Почему чтение именно из git, а не с диска — три причины, все измеренные.**
(i) Дерево может быть грязным, и тогда текст с диска не совпадает с текстом в коммите, от
которого ядро стартует, — трейс начался бы не с того. (ii) Неверсионируемые файлы
недостижимы по построению (П5), и **весь раздел границы чтения v4 — containment, `realpath`
полного пути, `S_ISREG`, отказ FIFO — становится не нужен: границу держит git**. (iii)
Цена 0.95 ms против 0.008 ms сырого чтения — на фоне 8–16 ms под локом это не различимо.

**Р4 ★. Резервирование — по контракту шва, как он есть.** `meta_keys=("loc",)` резервирует
ключ на ADD: caller-supplied координата есть спуфинг. `updatable_keys=("loc",)` открывает
только update. **Названный предел:** `updatable_keys` не валидирует ничего (П7), поэтому
вручную собранный `loc` может быть мусором и будет прочитан как `unknown(invalid_anchor)`,
а не отвергнут при записи. Санкционированный путь починки — верб, который строит объект сам.

**Р5 ★. Разрешение — каскад A → B → отказ, на чтении, с ОБЯЗАТЕЛЬНОЙ сверкой.**

Одна поверхность: `anchor_resolve(finding_id | status | category | file, project_dir=)`,
батч-контракт по образцу `check_findings`, плюс CLI-верб.

Алгоритм:
0. **ГЕЙТ ПРЕДКА — первым, до всякого трейса.** `git merge-base --is-ancestor <commit> HEAD`.
   Если коммит НЕ предок HEAD (карточка заведена на невлитой ветке — а здесь так заводится
   каждая), `blame --reverse` возвращает **код 0, пустой stderr** и атрибутирует строку
   коммиту ветки, из-за чего тест живости читает её как удалённую, хотя она жива.
   Проверено. Без этого гейта штатный процесс репозитория даёт ТИХИЙ ложный «потеряно».
   Ответ: `unknown(commit_not_ancestor)` — состояние временное, снимается мержем ветки.
1. **Канал A.** `git blame --reverse -p -C -C -L line,end <commit>..HEAD -- <path>`,
   с `-c core.quotePath=false`. Живые строки — те, чей sha равен HEAD; **путь берётся из
   записи `filename` вывода** и может отличаться от записанного. `core.quotePath` обязателен:
   по умолчанию git C-квотирует не-ASCII пути в porcelain, и этот же дефолт репозиторий уже
   лечил трижды (`_guard_conflict_markers`, allowlist плановых заметок, commit-msg гейт).
2. **СВЕРКА (не пропускаемая), и читается она по РАЗРЕШЁННОМУ пути, а не по записанному.**
   Прочитать `HEAD:<путь из записи filename>` и сравнить содержимое выведенных строк с
   `text`. Совпало — ответ; разошлось — канал A считается не ответившим.
   **Именно эта деталь была неверна в моей мерилке и дала фантомные «0.21% ошибок git»:**
   сверка по записанному пути объявляет переезд ошибкой. Измеренная цена сверки на
   исправленной реализации — ноль ложных отказов (537/537).
   **Частично выживший пролёт определён явно, чего v5 не делала:** сверяется каждая дожившая
   строка; ответ выдаётся, если сошлись ВСЕ дожившие, и несёт `survived: <n>/<m>`.
   Ни одной дожившей — `lost`. Часть сошлась, часть нет — `verify_mismatch`.
3. **Канал B** (если A не ответил): нормализовать `text` по `norm` и искать в
   `HEAD:<записанный путь>`; несколько кандидатов различать контекстом.
4. Ни один не ответил → `lost` либо `unknown(<причина>)`.

Ответ на запись:

```
"anchor": { "status": current | moved | moved_file | lost | ambiguous | unknown,
            "path": <путь на HEAD>, "line": <int|null>, "end": <int|null>,
            "channel": "git" | "content" | null,
            "reason": <токен|null>,
            "resolved_against": { "root", "head", "path", "mtime_ns", "size" } } | null
```

**`moved_file` — новый статус, и он появился из опыта, а не из вкуса:** якорь может
разрешиться в ДРУГОЙ файл (контролируемый split разрешился в `split_out.py`), и потребитель
обязан это видеть, а не получать номер строки в файле, о котором он не спрашивал.
`channel` присутствует всегда — читателю важно, каким механизмом получен ответ.

**Флаг `-C -C`, и обоснование в v6 переписано — v5 ратифицировала не то и на не том.**
v5 брала одиночный `-C` по контролируемому опыту и утверждала, что на живых историях
переездов нет вовсе. Оба утверждения поправлены:
(i) контролируемый split **не воспроизводится ни на одном пролёте ≤ 3 строк** — мой опыт
стоял на пролёте в 4 строки при ратифицированных тогда 3, то есть демонстрировал
способность, которой дизайн не имел (находка структурной атаки, проверено мной);
(ii) на ЖИВОЙ истории autosorter переезды есть: `-C` ловит 1, **`-C -C` ловит 2**,
`-M -C` — 1. Значит у статуса `moved_file` есть живой производитель, а лучший флаг —
`-C -C`. Цена измерена и не взрывается: 0.15 с на файле в 10 674 строки через 10 269
коммитов, одинаково для всех флагов.

`get(resolve_anchor=)` и `staleness_check(anchor=)` **не вводятся** (решение v4 сохранено):
первое заставило бы ядро знать имена ключей расширения, второе дало бы два разных корня в
одной записи ответа.

**Р6 ★. Нормализатор канала B (`norm: "v1"`) — числами.**
Декод `errors="replace"`; `\r\n`/`\r` → `\n`; ведущий отступ → токен глубины `indent // 4`
после замены табов на 4 пробела; внутренние пробельные раны схлопываются; хеш —
`sha256(json.dumps(<массив строк>, ensure_ascii=False).encode("utf-8")).hexdigest()[:32]`,
параметры взяты у `auto:v1` дословно. **`CONTEXT_LINES = 8`** (контекст бесплатен по месту:
в объекте его нет вовсе, он вычисляется на чтении из файла). **`MAX_ANCHOR_LINES = 5`** — поднято с 3 в v6 по измеренной причине: split не отслеживается
ни на одном пролёте ≤3 (контролируемый опыт), а на 4–5 отслеживается. Цена — две лишние
строки хранимого текста на карточку, что владелец уже принял («места не жалко»); выигрыш по
доле разрешения при этом почти нулевой (73.0/60.3% при 3 против 73.0/60.6% при 5), то есть
пролёт покупает НЕ процент разрешения, а способность видеть переезд.
**`MIN_ANCHOR_CHARS = 24`** — единственная константа, чьи числа взяты из загрязнённого
корпуса; направление вывода от состава не зависит, но **пересчёт вменён юниту Т-a**.
**`MAX_TEXT_BYTES = 2048`**, считается по `len("\n".join(text).encode("utf-8"))`.
Оговорка, которую v4 обещала неверно: `indent // 4` не различает 4 и 7 пробелов, а
схлопывание пробелов меняет строковые литералы — нормализатор МОЖЕТ назвать
семантически правленый код неизменившимся.

**Р7 ★. Отказ ПЕРСИСТИРУЕТСЯ объектом**, а не отсутствием ключа: иначе `null` неотличим от
«карточка старше якоря», а lost-rate и `sites_dropped` неисчислимы.

**Р8 ★. Закрытая таблица исключение→токен внутри `loc.py`.** Рантайм резолверов ловит любое
исключение, продолжает вставку и штампует `meta.resolver_errors`; более того,
`_validate_resolver_outcome` исполняется ВНУТРИ того же перехвата. Поэтому обещание «отказ
захвата никогда не `resolver_errors`» держится не словом, а таблицей: ненулевой код
возврата `git show`, отсутствие коммита, отсутствие пути в ревизии, ошибка декода,
превышение капов, исчерпание бюджета. Всё, что мимо таблицы, — настоящий сломанный резолвер,
и `resolver_errors` для него правильный канал. Т-a обязан иметь тест на каждый случай.

## 4. Грамматика захвата — общий потолок обоих каналов

Она не изменилась относительно v4, потому что от выбора механизма не зависит: это вопрос,
говорит ли карточка, где смотреть. Перемерена и воспроизведена обеими модельными семьями
третьего раунда.

**Файл — это ВСЕГДА колонка `file`** (609 из 709 строк autosorter не называют имени файла
в значении; когда называют ровно одно — согласие с колонкой 41/47 и 22/23).

Ветви по ФОРМЕ значения: **B1** голый int / int-строка; **B2** `list[int]` — каждый элемент
ОТДЕЛЬНАЯ строка, диапазон не выводится (контракт libcheck, 206/206); **B3** `path:N`
токен(ы) — строкой, списком строк или dict; **B4** голая спека `a-b`, `N,M,K-L`;
**B5** dict спек; **B6** проза → пропуск.

Приоритет между ключами одной строки: **`line` → `site` → `lines` → `sites` → `location`**;
`function` не источник никогда (28/28 проза). Singular-ключи однозначны по построению
(`line` 0% многоместных, `site` 15/15 гейта), plural — многозначны (`sites` 63%
многофайловых). Реально конкурирующих строк во всём корпусе **две** — таблица нужна, чтобы
захват не зависел от порядка обхода словаря, а не потому, что конфликт част.

### 4.3 Закрытый словарь причин

```
no_commit | commit_unreachable | commit_not_ancestor | repo_mismatch |
shallow_history | no_repo | path_absent_at_commit | not_a_file |
no_grammar | no_matching_site | out_of_range | too_short | too_large |
binary | timeout | no_root | verify_mismatch | internal_error |
unsupported_anchor_version | invalid_anchor | retracted
```

Статусы (`current | moved | moved_file | lost | ambiguous | unknown`) — **отдельная,
объявленная граница**: статус отвечает «где строка сейчас», причина — «почему ответа нет».
Три токена добавлены в v6, каждый закрывает найденный ТИХИЙ отказ:
**`commit_not_ancestor`** — карточка с невлитой ветки (иначе ложное «потеряно» при коде 0);
**`repo_mismatch`** — координата из другого дерева (единственный путь к уверенно неверному
ответу); **`verify_mismatch`** — git ответил, сверка не сошлась. Токен `unreachable_commit`
удалён как дубликат `commit_unreachable` — в v5 они стояли в одном «закрытом» словаре, что
и было замечено ревью.

**Известный остаток, названный, а не спрятанный:** `delete-then-restore` (строка удалена и
позже возвращена байт-в-байт, например ревертом) читается ядром как «потеряно», хотя строка
на HEAD жива. Сверка спасти не может — она стоит ПОСЛЕ теста живости и умеет только
отвергать. Спасает канал B, и это одна из причин, по которой он не избыточен.

## 7. Риски и граница — раздел СЖАЛСЯ, и это следствие редиректа

**§7.1. Границу чтения держит git, а не наш код.** Захват идёт через `git show
<commit>:<path>`; неверсионируемое недостижимо по построению (П5). Из v4 исчезают:
containment по `realpath` полного пути, `S_ISREG`, отказ FIFO/устройствам, разбор симлинков,
`max_bytes_read` как граница безопасности. Остаётся `MAX_TEXT_BYTES` как граница РАЗМЕРА
записи, а не доступа.

**§7.2. Чтение вне рабочего дерева — НЕТ**, ратифицировано владельцем. Кросс-репо карточки
получают честный отказ. Здесь это к тому же бесплатно: `git show` на путь вне репозитория
отказывает сам.

**§7.3. Лок.** Захват под локом = один `git show` ≈ 0.95 ms при 8–16 ms, уже удерживаемых;
идентичность репозитория кешируется на процесс и в маржинальную цену не входит.
Трейс истории под локом не выполняется. Бюджет стенных часов обязателен, **но v5 обещала
его неточно, и это поправлено:** «`max_capture_ms`» реализуется не новым механизмом, а
параметром `timeout=` у `subprocess`, который в пакете уже используется (`provenance` и
`db.git_rev_parse` зашивают `timeout=10`) — то есть значение надо согласовать, а не
изобретать. Согласовать его надо с `busy_timeout=5000`: измерено, что конкурирующий писатель
отваливается ровно на 5.00 с, **а `SQLITE_BUSY` = 5 не входит в `{8,10,13,14}` классификатора
`db._is_environmental`, то есть выйдет сырым traceback'ом.** Значит бюджет захвата обязан
быть заведомо меньше `busy_timeout`, и Т-a обязан иметь тест на конкуренцию. **И то, что при этом видит
конкурирующий писатель, названо прямо:** он отваливается по `busy_timeout=5000`, а
`SQLITE_BUSY` = 5 не входит в `{8,10,13,14}` классификатора `db._is_environmental`, то есть
выйдет сырым traceback'ом. Т-a обязан иметь тест на конкуренцию.

**§7.4. Цена разрешения на чтении.** N × 11–23 ms, дедуп по паре экономит 6–16%. Для
`anchor_resolve` над всем трекером это ~0.4 с (codebugs) и ~7 с (autosorter, 325 карточек) —
приемлемо для явного верба и неприемлемо внутри `get`/`query`, что и есть довод Р5.

**§7.5. TOCTOU и сверка.** Якорь — снимок, разрешаемый на чтении. `resolved_against` несёт
`head`, `mtime_ns`, `size` как свидетельство, а не доказательство. Сверка по тексту (Р5 шаг 2)
делает уверенно неверный ответ невозможным ценой ложных отказов при чистом реиндентe.

**§7.6. Предел, названный числом (перевыверен аудитом).** Ядро годно **28.7% / 9.5%**
карточек. **Канал B годен ровно столько же**, потому что питается тем же захватом
(строка «36.4% / 19.8%» из v5 считала предикат захвата v4, который v5 отменила). Потолок
обоих — грамматика: 63.6% / 79.2% карточек не говорят, где смотреть.

## 8. Что ратифицировано, что осталось владельцу

**Ратифицировано 2026-08-22 (`e306f5f`), исполнено:** №1 — ядро reverse blame (редирект
принят; механика v4 понижена до второго канала). №2 — текст хранится. №3 — вне дерева НЕТ.
№4 — символьный якорь по замеру.

**Оговорка к №2, которую я обязан сделать, потому что мой прежний довод рассыпался.**
v5 обосновывала хранение текста замером «git ошибается в 0.21%». Аудит показал, что
ошибалась мерилка: на исправленной сверке git прав 537 раз из 537. Решение владельца этим
не отменяется — у него были свои основания (другие VCS, «места не жалко»), — но **честное
основание теперь такое:** текст нужен каналу B, который без него не работает вовсе, и нужен
сверке как страховка от ненаблюдавшегося отказа. «Ноль из 537» — это отсутствие наблюдений,
а не доказательство невозможности.

### Три числа, по которым принимается решение, и все три в v5 были завышены

1. **Покрытие.** Локацию реально получат **~21% карточек codebugs (27 из 129)** и
   **~6% autosorter (209 из 3300)**. v5 называла «~21–29%» и «~15%»; аудит показал, что
   автосортерная цифра завышена в 2.4 раза — она переносила долю со смещённой выборки на
   популяцию, где канал B неприменим к половине строк. Верхний конец «29%» снят,
   нижний «21%» — измеренный пол и он верен.
   Потолок задаёт не механизм, а подача: **64% и 79% карточек не говорят, где смотреть.**
   Из тех, что говорят и захватываемы, разрешается 73% и 67%.
2. **Качество разрешения.** Строго (весь пролёт дожил) — 54% и 52%. Мягко (дожила хотя бы
   одна строка) — 73% и 60%. v5 давала владельцу только мягкое число, не назвав его мягким.
   Там, где отвечают оба канала, они согласны по номеру строки **133 раза из 133**.
3. **Верность.** На измеренной популяции ядро не ошиблось **ни разу (537/537 побайтно)**.

### Что стоило этого раунда — сказано прямо

Ревью нашло **один класс уверенно неверного ответа** (координата из другого дерева с общей
историей) и **два класса тихого ложного «потеряно»** (карточка с невлитой ветки — а здесь
так заводится каждая; и строка, удалённая и возвращённая ревертом). Первый закрыт полем
`repo`, второй — гейтом предка, третий — каналом B и назван остатком.

### Открытый вопрос — единственный, и он не про механизм

Якорь умеет сказать «код теперь в ДРУГОМ файле» (`moved_file`; на живой истории autosorter
таких переездов найдено 2). Карточка при этом остаётся привязанной к старому `file`, потому
что `file` — вход отпечатка, и его смена есть ре-кей identity (CB-43 п.6, отдельный
контракт, которого BT-7 не делает).

**Оставить ли расхождение видимым (★ — да, статусом `moved_file`), или карточка должна
следовать за кодом?**
Цена «оставить»: читатель видит, что карточка и код разошлись, и решает сам; трекер
остаётся честным, но карточка постепенно указывает на файл, где кода уже нет.
Цена «следовать»: это ре-кей identity — отдельная и большая работа, которая меняет
отпечаток карточки, то есть её тождество; BT-7 такую работу не делает и не должна.

## 10. Чего v5 НЕ делает — названо, а не оставлено на обнаружение

1. **Не покрывает большинство карточек** — 64% codebugs и 79% autosorter не говорят, где
   смотреть. Это граница подачи, а не механизма. Сквозное покрытие: ~21% и ~6%.
2. **Не работает без git** — нет репозитория, shallow-клон, переписанная история: честный
   отказ с причиной. Для этой популяции существует канал B, но её вклад **не измерен**:
   оба корпуса — репозитории с полной историей.
3. **Не следует за переездом карточки в другой файл** — `file` вход отпечатка; якорь лишь
   ПОКАЗЫВАЕТ расхождение статусом `moved_file`.
4. **Не отдаёт координату, которой не доверяет** — сверка по тексту, `verify_mismatch`.
   **Но и сверка слабее, чем кажется, и это измерено:** 29 из 58 (50%) и 168 из 479 (35%)
   верно разрешённых строк имеют текст, НЕ уникальный внутри своего файла на HEAD — то есть
   на таких строках сверка прошла бы и на неверном номере. Она отсекает грубую ошибку, а не
   доказывает правильность. (Слепота к отступу, которую я подозревал сам, стоит РОВНО НОЛЬ:
   побайтная сверка даёт те же 537/537.)
4б. **Не спасает строку, удалённую и возвращённую ревертом** — ядро читает её как
   «потеряно»; спасает канал B.
4в. **Не отличает форк с общей историей** — `repo` ловит другое дерево, но не дерево-близнец;
   там, впрочем, и код в захваченной ревизии тот же.
5. **Не валидирует `loc` на пути `update_finding(meta_update=)`** — `updatable_keys` не
   валидирует ничего; мусор будет принят на записи и прочитан как `unknown(invalid_anchor)`.
6. **Не даёт `WHERE hash = ?`** — хранение в `meta`. Триггер таблицы — §5.
7. **`MIN_ANCHOR_CHARS` не перемерен** на первопартийном коде — единственный долг калибровки,
   вменён Т-a.
8. **Вклад канала B вне git не измерен** — аргументируется (владелец назвал другие VCS),
   не измеряется.

## Приложение 2: правки v5 → v6 (узкий числовой аудит + одна структурная атака)

Форма ревью назначена куратором взамен четвёртого полного x2 — документ трижды проваливался
на шве «число → утверждение», а не на структуре. Форма себя оправдала: аудит проверил ~48
цифр, из них **не воспроизвелось 17**, а структурная атака нашла три FATAL, из которых один
я подтвердил лично в тот же час.

| правка | что её вынудило |
|---|---|
| «git ошибается в 0.21%» → **537/537 побайтно** | ошибалась МОЯ мерилка: сверяла по записанному пути и игнорировала запись `filename` — механизм, который сам документ объявляет ловцом переезда |
| **гейт предка** `merge-base --is-ancestor` перед трейсом | карточка с невлитой ветки даёт rc=0, пустой stderr и ТИХОЕ ложное «потеряно»; здесь так заводится каждая карточка |
| поле **`repo`** (SHA корневого коммита) + захват в дереве трекера | единственный путь к уверенно неверному ответу: коммит одного дерева, разрешение в другом с общей историей; сверка этот класс не видит по построению |
| `MAX_ANCHOR_LINES` 3 → **5** | split не отслеживается ни на одном пролёте ≤3; мой контролируемый опыт стоял на 4 строках при ратифицированных 3 |
| флаг `-C` → **`-C -C`** | на живой истории autosorter `-C` ловит 1 переезд, `-C -C` — 2; и у `moved_file` появился живой производитель, которого v5 считала отсутствующим |
| строка «канал B годен 36.4%/19.8%» **удалена** | считала предикат захвата v4, отменённый самой v5: B питается тем же `git show`, его популяция РАВНА ядровой |
| комплементарность 4.0 → **6.7 п.п.** | выборка 250 бралась с хвоста CSV и смещена по времени; на полной популяции 312 вклад канала B ВЫШЕ |
| покрытие «~15% autosorter» → **~6%** | доля со смещённой выборки, применённая к популяции, где канал B неприменим к половине строк; завышение в 2.4 раза |
| публикуются **обе** доли разрешения (строго 54/52, мягко 73/60) | v5 давала только мягкую, не назвав её мягкой; частично выживший пролёт теперь определён в Р5 |
| `-c core.quotePath=false` | porcelain C-квотирует не-ASCII пути по умолчанию — дефолт, который репозиторий лечил уже трижды |
| «62 и 1594 не говорят где смотреть» → **82 и 2615** | арифметика от неверного знаменателя |
| `max_capture_ms` — не новый механизм, а согласование `timeout=` с `busy_timeout` | обещан был механизм; в пакете он уже есть, а `SQLITE_BUSY`=5 не классифицируется и выйдет сырым traceback'ом |
| `unreachable_commit` удалён из словаря | дубликат `commit_unreachable` внутри «закрытого» словаря |
| `delete-then-restore` назван остатком | ядро читает как «потеряно»; сверка стоит после теста живости и спасти не может |
| §10: сверка слабее, чем кажется (50%/35% строк неуникальны в файле) | это и есть настоящая оптимистичность, а не подозревавшаяся слепота к отступу (её цена — ноль) |

**Что удержалось под атакой и потому названо явно:** мержи (реалистичная цепочка `--no-ff`
и конфликтный мерж с ручным разрешением — оба дают верный ответ); отсутствие выхода за
пределы репозитория через `moved_file`; невозможность эксплуатировать pathspec; цена `-C -C`
не взрывается на длинной истории (0.15 с на файле в 10 674 строки через 10 269 коммитов);
структурная гарантия Р1.
