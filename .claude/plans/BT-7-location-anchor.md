# BT-7 — Локационный якорь находки (CB-95): дизайн-док на ратификацию владельцу

**Статус:** черновик v1, DIR-2, 2026-08-22. До владельца — через куратора, после
adversarial-review-x2 (§8.3б). **Итог BT — документ, не код**: ни один юнит вниз не уходит
до ратификации.
**Карта:** CB-95 (`needs-design`, вербатим-запрос владельца 2026-08-18: «can we have some more
stable and robust fingerprint of location than just a line in a file? Ideally, with
auto-resolution of the new line»). Скоупится против CB-65 (RFC identity graph) — §6.
**Боль:** Б-8 — локация находки не должна гнить с первого редактирования.

## 0. Что здесь решается (одно решение) и что НЕ решается

**Решение:** какой ОБЪЕКТ является локацией находки, кто его ЗАХВАТЫВАЕТ при подаче, кто и
когда РАЗРЕШАЕТ его в текущую строку, и где он живёт относительно identity (fingerprint).

НЕ решается здесь (и сказано вслух, чтобы ревью не тянуло внутрь): merge policy дедуп-слияний
(В-3/CB-46 — следующая BT); система координат `file` (CB-93 — уже ратифицирована: путь
относительно корня worktree, см. §1); мутабельность `file`/`description` (CB-21 — объявлены
IMMUTABLE с причиной, вопрос открыт в точке изменения); relations-леджер (CB-65 S1).

## 1. Предпосылки (добыты из кода и трекера 2026-08-22; цитаты — грепаемым содержанием)

П1. **Локация сегодня = `file` (TEXT, свободный) + `meta.lines` (неразобранная строка без
грамматики).** `file` документирован «File path relative to project root» и с CB-93 (опция
(a), ратифицирована владельцем 2026-08-18, мердж `f0b4010`) все git/stat-операции staleness
исполняются от корня worktree, так что координатная система якоря ОПРЕДЕЛЕНА — это
предусловие, без которого CB-95 сама писала «an anchor is only stable if the path it hangs
on is». `meta.lines` не читает ни одна строка кода (CB-95 measured; подтверждено грепом
2026-08-22: в `src/` ровно два ПИСАТЕЛЯ и ноль читателей — CSV-импорт переносит колонку
`lines`/`Lines` в `meta["lines"]` (грепаемо: `row.get("lines") or row.get("Lines")`), и
CLI `add --lines` пишет `meta["lines"] = args.lines` как есть, без разбора).

П2. **Грамматики `meta.lines` в живых трекерах** — см. §1а (измерение агентом, числа
подставлены из его отчёта).

П3. **Staleness отвечает на гранулярности ФАЙЛА.** `provenance.file_status` возвращает один из
`current, modified, renamed, deleted, unknown` + `reason` (грепаемо: `"no_provenance"`,
`"no_cwd"`, `"empty_path"`, `"invalid_path"`, `relative_git_env`), и это уже «house style»:
неотвечаемый вопрос деградирует в `unknown` с причиной, а не в уверенную ложь. CB-53 научил
читателя staleness смотреть НОВЕЙШЕЕ наблюдение ринга (`_effective_commit`, «scanning from
the tail, the first entry carrying a usable commit wins»). Якорь ДОЛЖЕН наследовать обе
конвенции — словарь с `reason` и «новейшее наблюдение».

П4. **Identity.** `auto:v1` fingerprint хешится из category + file + normalized description
(CB-43 п.4); `meta.lines` — НЕ вход. Re-key identity — отдельный переговорный контракт
(CB-43 п.6; единственная санкционированная операция — `normalize_categories`, CB-61). RFC
identity graph, D5: граница иммутабельности fingerprint. Следствие, которое CB-95 назвала
сама: якорь — КАНДИДАТ в пятый вход, но ре-якорение не должно ре-кеить. Отсюда §3 Р1.

П5. **Контракт свежести (BT-4, ратифицирован):** `file`/`description` observation-frozen (входы
fingerprint), ринг несёт оба; top-level `meta` — АВТОРСКОЕ состояние строки, ре-наблюдение
пишет meta только в `meta.occurrences[*].meta`; «promoting specific keys into the row is a
future allowlist by measured demand» (CLAUDE.md, CB-43 п.10). Отсюда §3 Р3: якорь, если он
обновляется наблюдением, — ПЕРВЫЙ элемент этого allowlist'а и требует отдельной строки
ратификации.

П6. **Зарезервированные meta-ключи:** `_RESERVED_META_KEYS = {occurrences, occurrences_dropped,
regressed, recurrence_of}` (отказ на add и update), `_ADD_ONLY_RESERVED_META_KEYS =
{category_minted}`, плюс расширения (`similar_to`, `resolver_errors`) через реестр
резолверов. Якорь, вычисляемый сервером, войдёт в одну из этих категорий — §3 Р4.

П7. **Прецедент авто-захвата при подаче:** MCP `add` делает `reported_at_commit =
db.git_rev_parse("HEAD", silent=True)` если не передан. Якорь-захват — та же форма: сервер
дополняет наблюдение фактом о репозитории в момент подачи.

П8. **Ловушка нормализации:** `_VOLATILE_KEY_TOKENS = ("sha","commit","slug","branch","log",
"run","time","duration")` — строковые значения meta с такими именами ключей вырезаются из
описания при деривации fingerprint. Имя ключа якоря и его подполей не должно ломать это
(или должно сознательно на это опираться); фиксируется как ловушка для юнита.

П9. **Файл может не быть в этом репозитории** (CB-89/CB-91: абсолютные кросс-репо пути,
каталоги, глобы, проза — в сознательном использовании). Любой якорь, требующий git-истории
файла, не универсален по построению.

## 2. Варианты якоря с ценой (таблица порождена из П1–П9, не перечислена по памяти)

| | Что хранится | Разрешение на чтение | Переживает | Ломается на | Цена реализации | Цена владения |
|---|---|---|---|---|---|---|
| **A. Контентный** | нормализованный хеш якорных строк + хеш контекста (±N строк) + исходная строка + `captured_at_commit` | поиск хеша в текущем файле (сначала вблизи старой строки, потом весь файл); контекст — для дизамбигуации дублей | перемещение блока, правки вокруг, переименование файла (если `file_status=renamed` уже найден) | правку самих якорных строк; дубли блока без контекста → `ambiguous` | stdlib, ~200 строк + тесты; язык-агностичен; работает на любом читаемом файле, включая вне git | нет внешних зависимостей; версия нормализатора в ключе (`v`) — как `auto:v1` |
| **B. Символьный** | `(file, qualified symbol)` — `ast` для Python | парсинг текущего файла, поиск символа → строка def | любые перемещения внутри файла, большинство рефакторингов | rename символа; файл не-Python (per-language); проза/конфиги | stdlib для Python; каждый следующий язык — зависимость (tree-sitter) | таксономия языков — долг навсегда |
| **C. Git-walk** | `(file, line, commit)` | `git log -L`/`blame` от `captured_at_commit` до HEAD | любые правки, записанные git | файл вне репозитория (П9); squash/rebase история; стоимость O(история) на каждое чтение | обёртка над git, но самая медленная; MCP-сервер живёт долго — кеш по HEAD | зависит от формы истории, которую этот же репозиторий переписывать запрещает только на main |
| **D. Гибрид с `reason`** | A как ядро; B/C как опциональные уточнители | каскад: A → (B если Python и A `lost`) → `unknown(reason)` | объединение | сложность каскада; два ответа на один вопрос | A сейчас, B — по замеренному спросу (§5) | словарь `reason` растёт |

**Рекомендация: A сейчас, D как рамка (B — вторым шагом по спросу, C — отклонён).**
Обоснование через уже ратифицированные правила репозитория:
- A — единственный вариант, честно работающий на ВСЕЙ популяции `file` (П9): для файла вне
  git он всё ещё отвечает, для прозы/каталога отвечает `unknown(not_a_file)` — тот же
  деградационный стиль, что `file_status`.
- C противоречит CB-89/CB-91 по построению и дорог в долгоживущем MCP-процессе.
- B ценен, но per-language; включать его сейчас — строить таксономию без замеренного спроса
  (правило репозитория: «by measured demand»).

## 3. Решения внутри BT (каждое — строка для ратификации; рекомендация помечена ★)

**Р1. Якорь ≠ вход identity.** ★ Якорь НЕ входит в `auto:v1` (и не в `auto:v2`); ре-якорение не
ре-кеит. Альтернатива — сделать его пятым входом — отвергнута: одна и та же находка после
перемещения кода получила бы новый fingerprint, т.е. дедуп перестал бы узнавать ре-наблюдение
ровно в том случае, ради которого якорь строится. Согласуется с D5 RFC и CB-43 п.6.

**Р2. Где живёт.** ★ `meta.anchor` — структурированный, ВЕРСИОНИРОВАННЫЙ объект
`{v: 1, line: int, end: int|null, hash: str, context_hash: str|null, text: str,
captured_at_commit: str|null}`; `meta.lines` (свободный текст) НЕ мигрируется и не
трогается — остаётся авторской заметкой. Альтернатива «колонка» отвергнута: якорь — один
на строку, но его форма будет меняться (v), а колонка делает версию схемой; meta уже
несёт версионированные серверные структуры (ринг).

**Р3. Кто пишет.** ★ Три писателя, ровно: (i) ЗАХВАТ при подаче — сервер, если `lines`
парсится в строку/диапазон (грамматика §4) И файл читаем от корня worktree (CB-93); иначе
якоря нет и это не ошибка (как `reported_at_commit=None` при недоступном git); (ii)
РЕ-НАБЛЮДЕНИЕ — новейшее наблюдение ЗАМЕЩАЕТ `meta.anchor` (первый элемент allowlist'а
«promoted keys» из BT-4 — отдельная строка ратификации, потому что это первое исключение из
«top-level meta = авторское состояние»); (iii) `update_finding(meta_update={"anchor": …})` —
ручное ре-якорение, разрешено (неремонтируемый якорь — это форма CB-26). Захват (i) — через
`register_pre_add_resolver` (annotate-only seam, CB-45): ядро не знает про якорь, модуль
`anchor.py` — второе самореrистрирующееся расширение с нулём SQL.

**Р4. Резервирование.** ★ `anchor` — НЕ в `_RESERVED_META_KEYS` (ручное ре-якорение должно
быть возможно, Р3(iii)); резолвер не перезаписывает якорь, переданный вызывающим явно
(caller-supplied побеждает, как caller-supplied `fingerprint`).

**Р5. Разрешение — на чтение, без записи.** ★ Новая read-поверхность `anchor_resolve`
(MCP) / `anchor-resolve` (CLI) и расширение `staleness_check(..., anchor=True)`: возвращает
`{status: current|moved|lost|ambiguous|unknown, line, reason, confidence}`; `moved` несёт
новую строку; `lost` — якорный текст не найден; `ambiguous` — найден более одного раза и
контекст не разрешил. НИКАКОЙ записи «разрешённой строки» обратно в строку: это кеш,
гниющий с каждым коммитом (та же причина, по которой CB-53 чинился на стороне чтения).
`get`/`query` НЕ трогают файловую систему (чистая БД).

**Р6. Версия нормализатора.** ★ Хеш — от нормализованного текста (trim, схлопнуть
пробелы; без casefold — регистр значим в коде); алгоритм закреплён в `v`, как `auto:v1`;
смена нормализации = новая версия, старые якоря читаются старым нормализатором.

## 4. Грамматика `lines` для захвата (минимальная, по измеренным формам §1а)

Принимаются: `N`, `N-M`, `N,M,K-L` (берётся ПЕРВЫЙ диапазон как якорь, остальные — не
якорятся, заметка сохраняется как есть); `file:N (...)` — только если `file` совпадает с
колонкой `file`. Всё прочее — якоря нет, причина не пишется (это не ошибка подачи).
Альтернатива «структурированный аргумент `line=`/`end=` на `add`» — отложена до спроса:
сегодняшние писатели эмитят `lines` (§1а), и менять их контракт ради якоря — цена на
стороне клиентов, которую владелец не просил.

## 5. Что НЕ строится сейчас, с триггером

- Символьный якорь (B): триггер — измеренная доля `lost` на Python-файлах > порога, который
  назовёт первый замер `anchor_resolve` по живому трекеру.
- Бэкфилл якорей для существующих строк: читать старый `meta.lines` против текущего HEAD —
  это захват «задним числом» на уже сдвинутом коде; честно только с `captured_at_commit` из
  ринга/колонки и checkout'ом того коммита. Отдельная операция, dry-run по умолчанию (форма
  `normalize_categories`), если владелец захочет.
- Запись разрешённой строки обратно (кеш): триггер — замеренная стоимость чтения.
- Якорь в ринге per-occurrence: ринг уже несёт `file`; `anchor` per-occurrence — только если
  появится читатель «где это было на коммите X» (пара к Т-22).

## 6. Скоуп против CB-65 (RFC identity graph)

Пересечения ровно три, и все разведены: (1) D5 — Р1 подтверждает границу иммутабельности
fingerprint, якорь по ту сторону границы; (2) инструмент «shared locus» (same file + общие
символы), использованный в S0-адъюдикации RFC, — потенциальный потребитель символьного
якоря (B), отложен вместе с ним; (3) relations-леджер (S1) не знает о якоре — связь
карта↔карта и связь карта↔код — разные графы. BT-7 НЕ добавляет стадию в RFC и не
блокируется его нерешёнными D1/D2/D3.

## 7. Риски, названные до ревью

- Резолвер-захват читает файловую систему внутри `add` — ВНЕ транзакции? Нет: резолверы
  исполняются внутри `_add_one` под write-lock (CB-45). Чтение одного файла — десятки
  микросекунд; но файл по сетевому FS или огромный — держит лок. Смягчение: cap размера
  файла, захват только диапазона (seek по строкам), `silent` при любой ошибке I/O
  (`resolver_errors` — queryable). Это ЧИСЛО должно быть замерено юнитом до посадки.
- Хеш одной строки `return None` совпадает в сотнях мест → `ambiguous` без контекста;
  поэтому `context_hash` обязателен в захвате и первичен при поиске.
- Перенос между worktree/репозиториями: захват от корня worktree (CB-93) — якорь у карты
  кросс-репо (абсолютный `file`) захватывается, если путь читаем; разрешение — тоже по
  абсолютному пути. Говорится прямо, не прячется.

## 8. Вопросы владельцу (через куратора, в нулевом контексте)

1. Р1–Р6 пакетом: «якорь = контентный хеш строк в `meta.anchor`, захватывается сервером при
   подаче по `lines`, обновляется новейшим наблюдением, разрешается на чтение отдельным
   вызовом и не влияет на identity» — да/нет/иначе.
2. Отдельно Р3(ii): первое исключение из правила «верхнеуровневая meta — авторская»:
   согласны ли, что якорь обновляется наблюдением (иначе якорь тоже гниёт — но медленнее,
   чем строка).
3. Нужен ли символьный якорь (B) сразу для Python — или по измеренному спросу (§5).

## 9. Нарезка после ратификации (эскиз, не бриф)

Т-a: модуль `anchor.py` (захват-резолвер + грамматика + нормализатор v1) + тесты; Т-b:
`anchor_resolve` MCP/CLI + `staleness_check(anchor=)` + golden; Т-c (опционально):
backfill dry-run. Каждый — механический юнит с worktree-харнесом и §13.
