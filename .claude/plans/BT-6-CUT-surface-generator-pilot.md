## §0. Одно нерешённое решение, и почему оно сейчас нерешаемо

BT-3 измерила N — сколько строк поверхностного кода УБРАЛ бы слой экспозиции (одно описание на
поверхность, обе стороны генерируются): **587–1111 LOC из 3658** (диапазон устоял в двух
кросс-модельных проходах; **587 — это «LOW минус арм-ы, защищённые CB-86», 1111 — «HIGH минус
переезжающий `help=`», и арм-ы из него НЕ вычтены** — см. §6 про выравнивание операндов). BT-3
**не измерила M** — сколько строк такой слой САМ ДОБАВИТ. Без M «сокращает ли он код» неизвестно,
а это единственный критерий владельца («улучшает код И сокращает его размер одновременно»).

**BT-6 измеряет M на одном модуле.** Форма отчёта — **`G + D_per_surface + H_manual`**:
`G` — генератор (платится один раз), `D_per_surface` — декларация на одну поверхность (тул или
верб), `H_manual` — строки, которые остались рукописными, потому что генератор их не покрывает.
**Не `k·D_per_module`**: у модулей разное число поверхностей, и у `bench` 7 доменных функций
против 4 тулов и 4 вербов — «на модуль» не имеет знаменателя (находка Codex).

## §1. Что измеряется — и чем

Приёмка куратора дословно: *замер в трёх числах (строки генератора, строки снятой ручной обвязки,
время на второй модуль по оценке)*. Инструменты v1 (awk-диапазон, `git diff --stat`) **не могли
разделить то, что вычитали** (FATAL-2, подтверждено обеими моделями) — заменены.

| число | как считается | инструмент |
|---|---|---|
| **G, D** | декларации живут в **ОТДЕЛЬНОМ файле** (напр. `bench_surface.py`), генератор — в своём; `git diff --numstat 966f8f0..<tip>` по этим файлам даёт G и D раздельно. D делится на число поверхностей (8) → `D_per_surface`. Правила учёта: тесты генератора считаются отдельно (не в G); перемещённые строки (`--find-renames`/`-M`) считаются переездом, не добавлением; сгенерированные артефакты, если они материализуются в дерево, — в G-колонку с пометкой | `git diff --numstat`, пин базы `966f8f0` |
| **N_pilot, H_manual** | AST-разложение спанов `register_tools`/`register_cli` по `code / docstr / help / comment / blank` **до и после** (`module_surface.py --module bench`). Базовая линия на `966f8f0`: **span 320, код 189, докстринги 45, help 23, комментарии 34, пустые 29.** Заголовочное N_pilot = **колонка `code`** (189), не 320 и не 326 из v1: докстринги и `help=` ПЕРЕЕЗЖАЮТ в декларацию, комментарии и пустые — не обвязка. H_manual = `code`-строки, оставшиеся в модуле после пилота в рукописных хендлерах | `.claude/plans/exposure-scripts/module_surface.py` (артефакт этого разреза, AST-ключ, не файловый диапазон) |
| **T_second** | **по умолчанию — ИЗМЕРЯЕТСЯ**, не оценивается: исполнитель мигрирует `merge` на выбрасываемой ветке (без finish), засекает время, ветку удаляет; в отчёте — число с разбивкой «механическая часть / H_manual». Если измерение невозможно (названная причина) — оценка с явным интервалом погрешности, подписанная как оценка | секундомер исполнителя; протокол в §4.6 |

*Про 326 из v1:* awk-диапазон `^def register_tools … ^register_tool_provider` воспроизводится (127+199)
и **это верное число для неверного инструмента** — он считает файловый интервал, куда поместятся
декларации и откуда исчезнет функция. Сохранено как запись о v1, а не как базовая линия.

## §2. Кандидат: `bench.py` — выбор с ценой, по данным

Условия владельца: **не простейший модуль**; **не `findings`** (DIR-2). Таблица тиров —
**отдельный проход `module_surface.py` по `matrix.derivability_tier`** (сам `matrix.py` печатает
тиры только агрегатом — v1 приписала таблицу прогону `matrix.py`, это было неверно). На `966f8f0`,
все 14 модулей, без пропусков:

```
module        caps  MCP  T1 T2 T3  CLI   территория / причина
milestones       -   18  16  1  1    8   DIR-1; исключён по РАЗМЕРУ (пилот = миграция четверти поверхности)
findings        14   10   4  1  5   12   DIR-2; исключён владельцем
sweep            9    9   9  0  0    9   не назначен; все T1 — простейшая форма
reqs            10    8   5  0  3    9   не назначен (CB-117)
merge            9    6   6  0  0    4   DIR-1; все T1; 3 CLI-only + 3 MCP-only — АСИММЕТРИЧНАЯ поверхность
claims           5    5   4  1  0    4   не в списке файлов DIR-1; все T1/T2
bench            7    4   1  0  3    4   DIR-1  ← кандидат
blockers        12    4   4  0  0    4   DIR-1; все T1
embeddings       4    4   4  0  0    0   нет CLI — пилот на одной поверхности
relations        3    3   3  0  0    3   все T1, 3 поверхности — мал
similarity       2    2   1  1  0    2   DIR-2
provenance       2    1   1  0  0    1   DIR-2
grouping         3    0   -  -  -    0   поверхности нет (экспонируется DIR-2, CB-127)
db               4    0   -  -  -    0   инфраструктура, не домен
```

**Почему `bench`:**
1. **Единственный модуль DIR-1, где T3 ДОМИНИРУЕТ (3 из 4)** — `milestones` тоже смешанный
   (16/1/1), но исключён по размеру. Три из четырёх тулов несут логику: `codebench_import` —
   диспетч по ТОМУ, КАКОЙ аргумент передан (`csv_data is not None`; вывод по расширению живёт в
   CLI-хендлере, не в туле — v1 описала это неверно); `codebench_list`/`codebench_delete` — диспетч
   «run или benchmark». Генератор, который на `sweep`/`merge` выглядел бы всесильным, на `bench`
   обязан показать, **что остаётся рукам** — это и есть `H_manual`.
2. **Самый жёсткий констрейнт CLI-слоя лежит здесь, и он не тот, что назвала v1.** У `bench`
   четыре хендлера — **четыре разные формы `except`**: import — локальный `except OSError` на
   чтении + `except (ValueError, json.JSONDecodeError)` одним кортежем + печать результата
   **ВНЕ** арма; query — `except ValueError`; list — ничего; delete — `except (KeyError,
   ValueError)`, с комментарием в коде, почему упорядоченного `JSONDecodeError`-арма тут нет.
   `tests/test_bench.py` ратифицирует трассировку как дискриминатор пост-коммитного отказа
   (`assert "Traceback" in r.stderr` для записи, которая закоммитилась, а вывод упал). Генератор
   обязан воспроизвести **все четыре формы** и печать вне арма — если декларация вынуждена кодировать
   все четыре, **это и есть измерение**, а не провал.
3. **Размер средний:** 8 поверхностей, 189 строк кода обвязки (`merge` — 10 поверхностей/132,
   `sweep` — 18/288, `blockers` — 8/45, измерено тем же инструментом).
4. **Полоса A уже прошла здесь** (Т-19), тесты свежие.

**Цена выбора.** Выборка смещена в T3-сторону (в пакете 58 T1 из 74 тулов, у `bench` 1 из 4).
**Направление ошибки экстраполяции НЕИЗВЕСТНО**: если T3-хендлеры остаются рукописными вне
деклараций, `D` их не содержит и экстраполяция по `D` ЗАНИЖАЕТ (Codex); если декларация
вынуждена их кодировать — ЗАВЫШАЕТ. v1 утверждала «завышает» — не следовало из данных. Поэтому
T_second измеряется на `merge`: **противоположная форма по тирам (все T1), но АСИММЕТРИЧНАЯ
поверхность** (3 способности только в CLI, 3 только в MCP) — под правилом «ничего нового не
экспонировать» (§5) это не «лёгкий случай», а другая работа, и T_second покрывает и её.

## §3. Гипотеза формы — и что обязано устоять

**Гипотеза:** одна декларация на ПОВЕРХНОСТЬ (тул/верб) — Python-структура в отдельном файле
модуля, из которой строятся `@mcp.tool`-обёртка и `add_parser`/`add_argument` + хендлер.
Декларация называет доменные функции, к которым диспетчит. T3-логика либо остаётся рукописной и
**декларирует это** (поле «ручной хендлер» → `H_manual`), либо кодируется в декларации — выбор
исполнителя, оба считаются. Формат, требующий парсера (YAML/JSON-схемы), **в этом пилоте не
измеряется** — не запрет, а граница измерения; исполнитель вправе предложить другую форму в
возврате с обоснованием.

**Инварианты — и гейт, который МОЖЕТ сработать (v1 здесь провалилась):**

- **Форма регистрации — `__doc__`, НЕ `description=`.** Измерено: `server.py`
  `_NormalizedDescriptions` нормализует докстринг только при `kwargs.get("description") is None`,
  а коллектор golden (`tests/_mcp_schema.py`) регистрирует провайдер на **сыром** `MCPServer` и
  дедентит описание САМ. Сгенерированный тул с `description=` дал бы **golden байт-в-байт** и
  при этом клиентам — неотступленный текст: CB-73 воскрешён с зелёным гейтом, который для CB-73
  и построен. Поэтому генератор выставляет `fn.__doc__` (и `fn.__name__` — golden берёт
  `inputSchema.title` из него) и не передаёт `description=`. Альтернатива (если `description=`
  понадобится) — сперва обернуть коллектор golden в `_NormalizedDescriptions`; это правка
  `tests/_mcp_schema.py`, и её надо назвать в возврате как in-scope.
- **Независимый контроль, обязателен:** поведенческий тест, который строит сервер ЧЕРЕЗ реальный
  путь `server.py` (`_NormalizedDescriptions` + `install_strict_arguments`) и для всех четырёх
  тулов: `tools/list` описание == golden-запись; `tools/call` с валидными аргументами даёт тот же
  ответ, что до пилота; неизвестный аргумент ОТКАЗЫВАЕТСЯ. Сегодня `tests/test_bench.py` вызывает
  тулы как сырые функции через `FakeMCP`, отбрасывающий kwargs, и достигает только
  `codebench_import`/`codebench_delete` — **это пол, не доказательство.**
- **Golden `tests/golden/mcp_schema.json` не меняется** — гейт `tests/test_boundary.py::
  TestMcpWireSchema::test_schema_matches_golden`. Что он видит: `name`, `description`, `inputSchema`
  **включая вложенный `additionalProperties`** (11 вхождений). Чего не видит: `outputSchema` (в
  golden их 0) и **форму регистрации** (пункт выше).
- **CLI-контракт — снимок до/после для всех четырёх вербов:** `help`, `dest`, `nargs`, `choices`,
  defaults, stdout/stderr, exit code, граница коммита. Сегодня `bench-query` **не покрыт CLI-тестами
  вовсе** (import 14 / delete 3 / list 1 / query 0).
- **Четыре формы `except` и печать вне арма** — см. §2.2; `tests/test_bench.py` зелёный без
  ослабления (пол).
- **Имя провайдера остаётся `bench`** — `SERVER_NAMES` и `--mode` allowlist уже содержат его,
  правка `server.py`/`cli.py` не нужна. Плюс **тест `--mode bench`**: сегодня в `tests/` нет ни
  одного теста на `--mode` ни для какого модуля.
- Ноль нового SQL вне модуля — проверяется `grep -nE 'SELECT|INSERT|UPDATE|DELETE' <генератор>` = 0.
- Генератор импортируется модулем, не регистрируется сам — `_ensure_modules_loaded()` не трогать.

## §4. Ловушки

1. **Декларация длиннее обёртки** — честный ответ «нет», не провал; не ужимать ради числа.
2. **Перенос, а не удаление** — `docstr`/`help` колонки переезжают; считать их снятыми — ошибка
   BT-3 v2. Инструмент §1 разделяет по построению.
3. **Golden не видит форму регистрации** (§3, первый инвариант) — v1 назвала другое слепое пятно
   (`additionalProperties`) и ошиблась: golden его видит.
4. **Argparse dests** — снимок CLI-контракта (§3) ловит.
5. **Бюджет правок ≤4 на дерево:** генератор + файл деклараций + `bench.py` (снятие обвязки) +
   тесты (поведенческий MCP + CLI-снимок, один файл). `tests/test_bench.py` не правится (пол).
   Если выйдет пять — названная пятая, не молчаливая.
6. **T_second:** измерение на выбрасываемой ветке `merge` — по умолчанию (§1).
7. **Генерация в цикле по декларациям** — классическое место late-binding замыканий и двойной
   регистрации; тест на `tools/list` (ровно 4 тула, ровно 4 верба) обязателен.

## §5. Чего пилот НЕ делает

Не мигрирует второй модуль в main; не трогает `server.py`, `cli.py`, `types.py`, golden; не
экспонирует ничего нового; не решает про арку.

## §6. Что идёт наверх — вопрос владельцу, не решение

В нулевом контексте: «Слой экспозиции на одном модуле стоил **G** строк генератора (один раз) и
**D** строк описаний на поверхность, сняв **N** строк кода обвязки (докстринги/help переехали, не
исчезли); **H** строк остались рукописными. Второй модуль занял **T**. На 136 поверхностей
арифметика: **N_total − (G + 136·D)**, где N_total берётся как **1111** (верх BT-3, из которого
CB-86-арм-ы не вычтены — тот же учёт, что у M, который их оплачивает) — и второй раз против 587
с пометкой, что там арм-ы вычтены. Строить арку (В-5(а))? Цена «да»: миграция ~136 поверхностей,
четыре формы проводки унифицировать заранее (BT-3 §4). Цена «нет»: пилотный генератор удаляется,
либо остаётся на одном модуле.» Обе цены — без ранжирования.

## Приложение. Исправления по x2-ревью v1 (2026-08-22)

Сохранено как запись о том, что v1 утверждала, — числа v1 не переписаны сплошной заменой.

**Подтверждено обеими моделями независимо:** инструменты измерения не разделяют вычитаемое
(awk-диапазон + `--stat`); `JSONDecodeError`-инвариант для `bench` фиктивен (один кортеж, арм в
delete задокументирован как отсутствующий); `test_bench.py` не покрывает сгенерированную поверхность
(FakeMCP, `bench-query` 0); §6 предрешал («второе хуже первого»).
**Только Opus:** golden слеп к форме регистрации (`description=` обходит `_NormalizedDescriptions`,
коллектор дедентит сам) — FATAL, v1 при этом назвала ДРУГОЕ слепое пятно; 326 на 44 % состоит из
переезжающего текста; «единственный смешанный модуль DIR-1» ложно (`milestones`); таблица тиров
не из `matrix.py`; `codebench_import` диспетчит не по расширению.
**Только Codex:** единица `M_decl` не определена (7 функций / 4 тула / 4 верба); golden ВИДИТ
вложенный `additionalProperties`, слеп только к `outputSchema`; четыре формы `except` в четырёх
хендлерах; направление смещения выборки не следовало из данных.
**Отклонено судьёй:** два мини-пилота (владелец ратифицировал один модуль); «matrix.py не
запускается» (сэндбокс Codex, здесь rc=0); «`--mode` потребует правок `server.py`» (`bench` уже в
allowlist — но теста на `--mode` нет ни одного, добавлен в инварианты).
**Устояло:** 127+199 на `966f8f0`; 587–1111 из 3658; трассировка-дискриминатор в `test_bench.py`;
таблица тиров (числа верны, провенанс — нет).
