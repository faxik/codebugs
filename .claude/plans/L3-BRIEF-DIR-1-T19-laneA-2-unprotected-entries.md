## §1. Замысел — то, против чего будут принимать. Не задание.

**Функция не должна отчитываться успехом о записи, которая могла не произойти.**

Это ценность Н1 направления дословно (*success-shaped lie*). Все четыре сайта — один и тот же
отказ: между чтением, которое решает «делать ли запись», и самой записью **нет транзакции**,
поэтому в разрыв помещается конкурентный писатель, запись матчит ноль строк, а возвращаемое
значение всё равно утверждает, что всё случилось.

Приёмка будет читать дифф **против этого предложения**, а не против списка правок ниже.

## §2. Правило, которое здесь применяется, — уже РЕШЁННЫЙ закон, не предмет обсуждения

`CLAUDE.md`, раздел **Database**, правило CB-24: значение, вычисленное в Python из только что
прочитанной строки, записывается обратно **внутри ОДНОЙ транзакции**, и эта транзакция владеет
коммитом. Механизм — `db.txn(conn)`, который выдаёт `BEGIN IMMEDIATE`, т.е. берёт **write-lock
ДО чтения**. `busy_timeout` здесь не спасает: он сериализует записи и никогда не трогает
чтение, которое им предшествовало.

**Три следствия CB-24, каждое из которых стоило репозиторию реального отказа** — прочитай их в
`CLAUDE.md` целиком, здесь конспект:
1. **Удали собственный `conn.commit()` функции.** `db.txn` выдаёт `False` при уже открытой
   транзакции вызывающего, и коммит тогда закоммитит **чужую** работу.
2. **Конвертируй/сериализуй возвращаемую строку ПОСЛЕ блока.** Внутри блока `json.loads` на
   битом `meta` откатит запись, которую контракт обещал приземлить.
3. **Однооператорный read-modify-write — не этот случай** (`SET n = n + 1` уже атомарен).

И **следствие (4)**: читай строку **сырой** внутри блока, если хелпер парсит JSON, иначе
следствие (2) невыполнимо.

**Правило `RETURNING`** (`CLAUDE.md`, Database): оператор либо несёт `RETURNING` и читается
`fetch`-ем, либо не несёт и читается `cursor.rowcount`. **Никогда оба** — на `RETURNING`-операторе
`rowcount` равен `0`, пока курсор не исчерпан, т.е. отчитается «ничего не произошло» о
приземлившейся записи. Это строго хуже no-op.

## §3. ЧТО ИМЕННО ЧИНИТЬ — четыре сайта, ровно четыре

Список получен **прогоном** `python3 .claude/plans/bt1-scripts/population.py`, не чтением кода
и не из таблицы в документе. Все четыре в нём — `family=F1`, `dependence=proven`,
`with db.txn: NONE`. Я спот-чекнул каждый лично по исходнику.

**Цитирую ГРЕПАЕМОЕ СОДЕРЖАНИЕ, а не номера строк — номера не переживают форвард-мердж.**

### (1) `bench.delete_run` — `src/codebugs/bench.py`
Читает `SELECT run_id, benchmark FROM codebench_runs WHERE run_id = ?`, затем
`SELECT COUNT(*) as c FROM codebench_results WHERE run_id = ?`, затем удаляет
`DELETE FROM codebench_results WHERE run_id = ?` и `DELETE FROM codebench_runs WHERE run_id = ?`,
закрывает голым `conn.commit()`.
**Вред:** `result_count` прочитан ДО `DELETE` и возвращается уже неверным.

### (2) `bench.delete_benchmark` — `src/codebugs/bench.py`
Читает `SELECT run_id FROM codebench_runs WHERE benchmark = ?`, затем f-string
`SELECT COUNT(*) as c FROM codebench_results WHERE run_id IN (…)`, удаляет f-string
`DELETE FROM codebench_results WHERE run_id IN ( {} )` и
`DELETE FROM codebench_runs WHERE benchmark = ?`, голый `conn.commit()`.
**Вред — ХУЖЕ остальных, это порча данных, а не TOCTOU:** результаты удаляются по **снятому
списку** `run_ids`, а сами прогоны — **безусловно** `WHERE benchmark = ?`. Прогон, вставленный в
разрыв, теряет свою строку и **оставляет осиротевшие результаты**. Ставь мутационную пробу
именно сюда.
*(f-string в SQL здесь — существующая форма для `IN (...)`; она параметризована плейсхолдерами.
Не переписывай её и не трогай `# noqa`, если он там есть — это не твой скоуп.)*

### (3) `embeddings.store_embedding` — `src/codebugs/embeddings.py` (CB-125)
`SELECT * FROM requirements WHERE id = ?` → `KeyError` если нет →
`UPDATE requirements SET embedding = ?, updated_at = ? WHERE id = ?` → голый `conn.commit()` →
`return {..., "stored": True}` **безусловно**.
**Вред:** требование удалено в разрыве → UPDATE матчит 0 строк → `"stored": True`.

### (4) `sweep.archive_sweep` — `src/codebugs/sweep.py` (CB-126)
`sweep_id = _resolve_sweep(conn, sweep_ref)` →
`UPDATE codesweep_sweeps SET status = 'archived', updated_at = ? WHERE sweep_id = ?` → голый
`conn.commit()` → `return {..., "status": "archived"}` **безусловно**.
**Вред:** тот же. Чтение спрятано **за хелпером** — поэтому grep по `SELECT` этот сайт не видит;
это один из пяти helper-hidden чтений, найденных работой по популяции. Помни следствие (4).

## §4. Форма фикса

Для каждого: обернуть тело в `with db.txn(conn):`, **удалить собственный `conn.commit()`**, и
**сделать возвращаемое значение отражением того, что запись реально сделала**, а не утверждением.
Последнее — не косметика: именно оно закрывает Н1. Как именно (rowcount / `RETURNING` /
поднять `KeyError`) — **твоё решение по каждому сайту**, но оно должно быть одинаково
обосновано и не нарушать правило `RETURNING`.

**Изменение наблюдаемого контракта — назови его вслух в возврате.** Если `store_embedding`
начнёт поднимать `KeyError` там, где раньше возвращала `"stored": True`, это изменение
поведения: оно правильное, но оно должно быть в `CHANGELOG.md` и в возврате, а не всплыть у
приёмщика.

### Что сделано — по замыслу §1, не по списку §3

Все четыре функции: тело в `with db.txn(conn):`, собственный `conn.commit()` удалён, возврат
**читается из записи**, а не утверждается.

| Сайт | Чем теперь доказан возврат |
|---|---|
| `bench.delete_run` | `results_removed` = `rowcount` самого `DELETE` (был `COUNT(*)` до него) |
| `bench.delete_benchmark` | оба счётчика = `rowcount` соответствующих `DELETE` (были `COUNT(*)` и `len(run_ids)`) |
| `embeddings.store_embedding` | `UPDATE … RETURNING id`; нет строки → тот же `KeyError` |
| `sweep.archive_sweep` | `UPDATE … RETURNING sweep_id, status`; `status` — то, что в строке |

Обоснование единообразно: **`DELETE` доказывает себя `rowcount`-ом, `UPDATE` — `RETURNING`-ом.**
Правило `RETURNING` не нарушено ни в одном месте (подтверждено и кросс-модельным ревьюером):
где `RETURNING` — только `fetchone()`, где его нет — только `rowcount`. Возврат собирается
**после** блока (следствие 2). Следствие (4) для `archive_sweep` выполняется тривиально:
`_resolve_sweep` не парсит JSON, он отдаёт `row["sweep_id"]`.

### Изменения наблюдаемого контракта — названы вслух, оба в `CHANGELOG.md`

1. `store_embedding`: требование, удалённое в разрыве, теперь поднимает `KeyError` вместо
   `{"stored": True}`. Это и есть закрытие Н1 на этом сайте.
2. `store_embedding`, находка кросс-модельного ревью: существование теперь решает сам `UPDATE`,
   поэтому вызов, неверный **сразу двумя** аргументами (несуществующий `req_id` **и**
   нераспаковываемый вектор), поднимает `struct.error` там, где раньше был `KeyError`. Каждый
   аргумент по отдельности не затронут. Измерено, не выведено.

Счётчики `bench.*` на тихой базе совпадают со старыми значениями — эту половину «возврат =
квитанция» **не различает ни один тест, пока держится транзакция**; сказано так и в `CHANGELOG`,
вместо вакуозного теста.

### Доказательства

`ruff check src/ tests/` — `All checks passed!`; `pytest tests/ -q` — **1860 passed** (~85 s),

Мутационная проба — по одной на сайт, **в точку дефекта**: из функции убирается ровно

именно транзакция. Каждый мутант убит своей пробой, по одному тесту:

| Мутант | Проба, которая упала |
|---|---|
| `delete_run` | `test_a_result_inserted_in_the_window_cannot_falsify_results_removed` |
| `delete_benchmark` | `test_a_run_inserted_in_the_window_does_not_leave_orphaned_results` |
| `store_embedding` | `test_a_requirement_deleted_in_the_window_cannot_be_reported_as_stored` |
| `archive_sweep` | `test_a_sweep_deleted_in_the_window_cannot_be_reported_as_archived` |

Пробы одноклассные и **однопоточные**: подключение-инъектор (`InjectingConnection`) запускает
конкурентную запись с ДРУГОГО соединения непосредственно перед названным оператором, поэтому окно
между чтением и записью попадается детерминированно, без гонки планировщика. Различает
**кто из писателей отказан** (правило Testing (a) — конечное состояние на тихой базе по обе
стороны фикса одинаково); у конкурента `busy_timeout=150 ms`, потому что после фикса он не
получит блокировку **никогда** (правило Testing (b)). Хук на коммит не нужен: пробы цепляются за
оператор записи, а не за шов коммита.

### Методологическая заметка для следующего исполнителя — стоила отдельного разбора

**Первый прогон мутационных проб отчитался «`delete_benchmark`: 1 passed» — ложно.** Причина —
устаревший `__pycache__`: правка исходника и предшествующий `git checkout --` попали в одну
секунду, и pytest импортировал НЕ мутированный модуль. Симптом читался как «эквивалентный
мутант» (урок Т-6), а был инструментальным. Прогоняй мутационные пробы с
`PYTHONDONTWRITEBYTECODE=1` и чисткой `__pycache__`, и **проверяй, что мутант жив в момент
прогона** (`grep -c MUTANT <файл>`); иначе «мутант выжил» и «мутант не был применён» неразличимы —
ровно та же форма, что вакуозная проба.

### Кросс-модельное ревью — выполнено

`timeout 420 codex exec --sandbox read-only '<промпт с диффом ТЕКСТОМ>' < /dev/null`, модель по
умолчанию, явный запрет исследовать репозиторий, лимит 400 слов. Одна попытка потеряна на моём
собственном таймауте инструмента (2 мин < 420 с) — не таймаут codex; вторая прошла, exit 0.
Четыре находки: **(2) принята** (сдвиг приоритета исключений, объявлен); **(3) принята как
честная граница** (половину «квитанции» тест не различает — сказано вслух, а не закрыто
ратчетом: попутный энфорсмент запрещён §5); **(4)** подтверждает отсутствие нарушений `RETURNING`;
**(1) отклонена** — предлагалось проверять `rowcount` второго `DELETE` в `delete_run` из-за
гипотетического `BEFORE DELETE … RAISE(IGNORE)`: в этой схеме триггеров нет, а под write-lock'ом
строка прочитана в той же транзакции, так что ветка была бы недостижимой защитой.

Отдельно, для точности: ветка `row is None` в `archive_sweep` существующими тестами **не
покрыта** (`test_archive_not_found` отказывает раньше, в `_resolve_sweep`) — это обязательная
проверка перед чтением `RETURNING`-строки, а не гейт, и под блокировкой она недостижима.

### Пятый сайт — наблюдение, не диффу

`embeddings.batch_store_embeddings` (`src/codebugs/embeddings.py`, сразу под починенной
функцией): цикл `UPDATE`-ов, `rowcount` на каждом, затем **свой `conn.commit()`**. В популяции
BT-1 его **нет** и это верно — read-modify-write там отсутствует, счётчик честен. Но следствие (1)
CB-24 он нарушает: под чужой транзакцией эта функция закоммитит работу вызывающего. Не чинил —
пакет ≤4 и это другой класс дефекта (композируемость, не Н1).

### Границы пакета

Ровно четыре сайта. `findings.py` / `similarity.py` / `provenance.py` / `reqs.py` и приватные
сайты популяции не тронуты. `types.py`, `tests/golden/mcp_schema.json`, `CLAUDE.md` не тронуты:
докстринги MCP-тулов не менялись (правились докстринги доменных функций, а SDK берёт
`description` из докстрингов вложенных функций `register_tools`), значит golden не сдвигается —
и это проверено зелёным `tests/test_server.py` в полном прогоне. Попутного энфорсмента нет:
ни ратчета, ни AST-предиката, ни обёртки над `commit()`, ни линт-правила.
