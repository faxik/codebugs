**Набор — 546 различных имён:**

- все 128 кодов ASCII в **четырёх** позициях: одиночным символом, в начале, в середине и **в конце

- краевые имена брифа: пустое, `a.b`, `a[0]`, `a$b`, `a b`, `quo"te`, `back\slash`, `a\`, `\`,
  `a\"b`, `"`, `a"`, `"\`, `\\`, табуляция, перевод строки;
- комбинации, которых требует §3.2: `a".b`, `a\".b`, `a\\"b`;
- **имена, которых бриф не перечислял и которые я добавил намеренно** — литеральный текст того
  самого эскейпа, который правило порождает само (в четырёх позициях), чтобы проверить правило на
  устойчивость к собственному выводу, плюс `"a"`, `$.a`, `a\\`, `a\\\`.

**Каждое имя проверено двусторонне,** как требует §3.2:

- **(A) самонаходимость** — в документе `{имя: "SELF"}` путь обязан вернуть `SELF`;
- **(B) единственность в толпе** — в одном документе, содержащем **все** имена набора, путь имени
  обязан вернуть значение **именно этого** имени. Это и есть половина «не находится по пути соседа»,
  сделанная за один проход вместо попарного перебора;
- **(C) различение вложенности** — для имён с точкой строится вложенный документ, литеральный путь
  обязан вернуть `NULL`, и рядом проверяется, что наивный путь его **находит** (то есть дефект
  реален);
- **(D) различение индекса** — для `a[0]` строится документ с массивом, литеральный путь обязан
  вернуть `NULL`.

### Результат

| Набор | Имён | Отказов |
|---|---|---|
| Весь набор | 546 | **6** |
| Тот же набор без имён с нулевым байтом | 542 | **0** |
| Имена с нулевым байтом | 4 | все затронуты |

Проверок различения вложенности выполнено 7, различения индекса — 1; все прошли. Проверка (A)
**прошла на всех 546 именах без исключения** — включая имена с нулевым байтом. Именно это и есть
источник ошибки брифа: самонаходимость держится, а двусторонность нет.

Отказавшие имена, с байтами. В путях последовательность из шести знаков «обратный слеш, `u`, `0`,
`0`, `0`, `0`» записана как `<эскейп-нуля>` — намеренно, по причине, которую §2.2 брифа называет за
собой: такая последовательность в прозе дважды пережилась в живой байт при записи файла. В SQLite
уходят настоящие шесть знаков.

```
name='\x00z'   bytes=b'\x00z'    путь: $."<эскейп-нуля>z"   -> вернул значение ключа '\x00'
name='a\x00'   bytes=b'a\x00'    путь: $."a<эскейп-нуля>"   -> вернул значение ключа 'a\x00z'
name='a\x00b'  bytes=b'a\x00b'   путь: $."a<эскейп-нуля>b"  -> вернул значение ключа 'a\x00z'
name='a'       bytes=b'a'        путь: $."a"                -> вернул значение ключа 'a\x00z'
name=''        bytes=b''         путь: $.""                 -> вернул значение ключа '\x00'
```

Шестая строка отчёта прогона — `name='$."a"'`, проверка `C-nested-premise` — **моя собственная
ошибка пробы, а не отказ правила**: имя содержит точку, поэтому попало в проверку (C), но наивный
путь для него (`$.$."a"`) синтаксически бессмыслен, так что премиса «наивный путь обходит
вложенность» там неприменима. Само правило на этом имени отработало верно. Называю, чтобы число
«6» не читалось как шесть дефектов.

**Обратите внимание на две последние строки таблицы отказов.** Страдает не только диковинный ключ.
Страдают `a` и пустое имя — то есть **самые обычные ключи становятся недостижимыми**, если рядом в
том же документе лежит ключ с нулевым байтом и совпадающим началом.

## 4. Предъявленная фикстура и механизм

Просили состояние рядом с вердиктом. Вот оно, распечатано прогоном.

```
python dict : {'a\x00z': 'NUL_KEY_VALUE', 'a': 'ORDINARY_VALUE'}
doc bytes   : b'{"a\\u0000z": "NUL_KEY_VALUE", "a": "ORDINARY_VALUE"}'

ключи, которые видит сам SQLite (json_each):
    key='a\x00z' (bytes b'a\x00z') -> 'NUL_KEY_VALUE'
    key='a'      (bytes b'a')      -> 'ORDINARY_VALUE'

путь для 'a'      -> ('ok', 'NUL_KEY_VALUE')
путь для 'a\x00z' -> ('ok', 'NUL_KEY_VALUE')
```

Оба ключа в документе есть — `json_each` их перечисляет по отдельности и с разными байтами. Но
запрос **обычного** ключа `a` возвращает значение соседа.

**Механизм.** Я перебрал десять написаний пути для ключа `a\x00b` в документе, где рядом лежат `a`
и `a\x00c`, все три с разными значениями-маркерами:

| Написание | Результат |
|---|---|
| правило §2.2 (числовой эскейп нуля) | `TARGET` |
| сырой нулевой байт в пути | `OperationalError: bad JSON path` |
| наивное без кавычек, сырым байтом | `TARGET` |
| наивное экранированное, без кавычек | `None` |
| скобочное закавыченное `$["..."]` | `None` |
| скобочное сырое | `None` |
| прописная `U` в эскейпе | `None` |
| удвоенный обратный слеш перед эскейпом | `None` |
| JSON5-шестнадцатеричное (`\x` плюс два нуля) | `TARGET` |
| JSON5-восьмеричное (обратный слеш плюс три нуля) | `TARGET` |

Единственное объяснение, согласующееся со всеми десятью строками: **SQLite сначала раскрывает
эскейпы в метке пути и в ключе документа, а затем сравнивает их как C-строки, обрывая на первом
нулевом байте.** Отсюда и то, что шестнадцатеричная и восьмеричная формы — вовсе не эскейпы JSON, а
расширения JSON5 — дают тот же `TARGET`; и то, что удвоенный слеш не даёт ничего (обратный слеш
сохраняется, нулевого байта не возникает); и, главное, то, что метка `a` совпала с ключом `a\0z`.

Практический вывод: **ключ с нулевым байтом неотличим от своего начала до этого байта — в обе
стороны и при любом написании.** Это свойство чужого разборщика, а не наше решение.

## 5. Достижимость: дефект живой, а не умозрительный

Проверено сквозным прогоном через настоящий путь записи пакета, а не сырым SQL.

```
add_finding(..., meta={"a\x00b": "NUL_VALUE", "a": "ORDINARY_VALUE"}) -> CB-1

RAW STORED meta (сырая мета карточки, как она легла в столбец):
  {"a<эскейп-нуля>b": "NUL_VALUE", "a": "ORDINARY_VALUE",
   "category_minted": true, "loc": {...}}

ключи, которые видит SQLite:
    key='a\x00b' -> 'NUL_VALUE'
    key='a'      -> 'ORDINARY_VALUE'

наивный путь $.a       (сегодняшний код)  count=1  value='NUL_VALUE'
путь правила для 'a'                      count=1  value='NUL_VALUE'
путь правила для 'a\x00b'                 count=1  value='NUL_VALUE'
```

Ключ с нулевым байтом **пишется штатно** и попадает в столбец. Запись его не отвергает.

**Честная граница утверждения, которую важно не потерять:** сегодняшний наивный код ведёт себя на
этом ключе **точно так же плохо** (`$.a` тоже возвращает `NUL_VALUE`). То есть правило §2.2 —
**не регрессия** здесь; оно просто не чинит этот класс. Это существенно для решения: цена выбора
«оставить правило как есть» равна нулю относительно сегодняшнего дня, а не отрицательна.

## 6. Последствие для §4.3, которое меняет предписание

§4.3 велит **удалить** константу `_META_PATH_METACHARS` целиком. Измерено, что сегодня ось
группировки нулевой байт **отвергает** — через условие `ord(c) < 0x20` в `_resolve_group_axis`:

```
group_by 'meta:a\x00b' -> refused (A meta key containing '\x00' ...)
group_by 'meta:a.b'    -> refused (A meta key containing '.' ...)
```

Если константу удалить целиком, ось группировки **начнёт принимать** ключ с нулевым байтом и молча
сгруппирует его под именем его начала. То есть буквальное исполнение §4.3 **вносит новый тихий
неверный ответ** на поверхности, которая сегодня от него защищена. Это ровно та форма, которую
направление ловит: починка, открывающая вторую тихую очередь внутри себя.

Я это **не решил и не обошёл** — решение уровня (2). Отмечаю только, что «удалить, а не сузить» и
непустая область отказа несовместимы в одном предложении.

## 7. Форма, которая выражает всё, — предлагаю, но не выбираю

§4.1 разрешает предложить правило лучше при условии, что перебор §3.2 показан для обоих. Показываю.

Это **не другое написание пути, а другой механизм**: сравнивать имя ключа не меткой пути, а
значением столбца `key` в `json_each`.

```sql
EXISTS (SELECT 1 FROM json_each(meta) WHERE key = ?)                -- существование
EXISTS (SELECT 1 FROM json_each(meta) WHERE key = ? AND value = ?)  -- со значением
```

| Форма | Набор | Отказов |
|---|---|---|
| правило §2.2 (путь) | 542 без нулевого байта | 0 |
| правило §2.2 (путь) | **546, весь** | **6** |
| `json_each(meta) WHERE key = ?` | **546, весь** | **0** |

Имена с нулевым байтом при этой форме находятся по отдельности и не путаются:

```
'\x00'    -> 'SELF'      'a\x00z'  -> 'SELF'
'\x00z'   -> 'SELF'      'a\x00'   -> 'SELF'
```

Причина, по которой это работает: параметр связывается как значение SQL `TEXT`, и нулевой байт
внутри него — **данные, а не терминатор**; сравнение идёт по всей длине. Побочно эта форма точнее
выражает и само обещание тула: `json_each` перечисляет **непосредственных детей** документа, то есть
верхнеуровневые ключи, — тогда как путь есть путь, которому верхнеуровневость надо навязывать
грамматикой.

**Чего я НЕ проверял и что обязано войти в решение, если форма приглянётся:** поведение на
испорченной и на не-объектной `meta` (у `json_each` тут своя семантика, и в этом файле рядом уже
стоят стражи `json_valid` и `json_type = 'object'` для кольца наблюдений); стоимость на плане
запроса; и совместимость с ветвью `meta_value`, которая всё равно упирается в приведение типов
(CB-276). Всё это — работа, а не наблюдение, и я её не делал.

## 8. Расхождения брифа с деревом

Перечисляю всё, что нашёл, включая мелкое, — §6 брифа требует именно этого.

1. **§2.2 и §2.3.1 — несущая ошибка, третья по счёту.** Утверждение «область отказа пуста» и
   строка таблицы «нулевой байт → экранированная форма → литерал» **неверны в двустороннем
   смысле**. Экранированная форма действительно **находит** ключ (моя проверка (A) это
   подтверждает), но она же находит и соседа, а соседский путь находит её. §3.2 требует
   двусторонности прямым текстом, и по этому критерию имя не выражается.
   **Форма ошибки — ровно та, которую §2.3.1 записывает за собой сам:** утверждение шире замера.
   Померено одно свойство (находится ли ключ), высказано другое (выразимо ли имя). Направление
   ловит эту форму шестую смену подряд, и здесь она совершена в том же абзаце, который её называет.
2. **§2.1 — «сайтов ровно три», построений «четыре».** Держательница уже поправила себя сама:
   построений пять, чинимых три. **Подтверждаю независимо собственным обходом синтаксического
   дерева** (`ast`, все `.py` под `src/`, `tests/`, `tools/`; грепом здесь считать нельзя —
   локальный `grep` есть `ugrep` и молча теряет попадания). Обход дал **16** мест, где строка
   содержит `$.`, из них построений пути **пять**: `findings.py:3181` (ось группировки), `:3534` и
   `:3538` (две ветви фильтра) питаются вводом вызывающего; `:491` и литерал `'$.occurrences'`
   внутри SQL-строки, начинающейся на `:3557`, захардкожены и неуязвимы. Остальные одиннадцать —
   текст сообщений об ошибке и прозаические строки в тестах.

   **Нюанс, который стоит знать при повторе обхода:** механический признак «f-строка с подстановкой»
   помечает `:491` как питаемую переменной, потому что там действительно стоит
   `f"$.{REFUSAL_COUNT_META_KEY}"`. Но подставляется **модульная константа**, а не ввод вызывающего,
   — это видно только чтением, не признаком. То есть счётчик даёт четыре «динамических» построения,
   а чинимых по существу три; расхождение брифа с деревом здесь ровно такого происхождения.

   **Метод назван честно:** объёмный обход я поручил отдельному агенту на `sonnet`, как предписано
   каскадом, но его возврат до меня не дошёл, и обход я выполнил сам. Числа выше — мои.
3. **§4.3 — «отказ снимается целиком» несовместимо с непустой областью.** См. §6 выше: буквальное
   исполнение открывает новый тихий неверный ответ на оси группировки.
4. **Номер строки константы.** §4.3 называет `findings.py:3138` местом `_META_PATH_METACHARS`.

## 14. Замеры-условия §4.1 — выполнены ДО починки

**(а) Испорченная и не-объектная `meta`.** Фикстура из десяти форм: объект, `NULL`, обрыв `{"a": `,
массив, число, строка, `true`, объект с `NaN`, пустая строка, объект без искомого ключа.

```
TODAY  json_extract(meta,?) IS NOT NULL      -> OperationalError: malformed JSON
NEW    голый json_each                       -> OperationalError: malformed JSON
NEW    + json_valid(meta)   [голый]          -> OK, но потерял строку с NaN
NEW    + json_valid(meta,6) [JSON5]          -> OK: ['good-object', 'nan-inside']
NEW    + json_valid(meta,6) AND json_type(meta)='object' -> то же самое
```

Три вывода, и первый меняет оценку риска. **Сегодняшний код роняет запрос на той же строке.**
Значит страж — это **починка**, а не защита от регрессии, которую я бы внёс: после неё фильтр
строго устойчивее того кода, который он заменяет. **Флаг JSON5 обязателен**: голый `json_valid`
отвергает `NaN`, который пишет сам пакет, и молча выбросил бы такую строку из каждого мета-фильтра
— ровно ловушка CB-82, уже описанная в этом файле. **`json_type(meta) = 'object'`** результата ни на
одной измеренной форме не меняет (у массива ключи целые, у скаляра `NULL`, ни то ни другое не равно
связанному тексту), поэтому он есть защита по построению, а не по вере; цена измерена — **+5.2%** на
5000 строк.

**(б) Стоимость.** Мерил на копии боевого трекера и на синтетическом крупном.

одна копия ещё и без псевдонима `je`. Это ровно та форма, о которой предупреждает правило дерева про
перечисления, и — что хуже — **мой собственный комментарий уже утверждал, что дефиниция одна**.
