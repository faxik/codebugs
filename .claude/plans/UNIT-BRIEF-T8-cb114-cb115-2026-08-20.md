**Задание.**

1. **CB-114** — докстринг `import_findings` (`src/codebugs/findings.py:1049-1051`)
   утверждает «a fingerprint hit on a `fixed`/`stale` row would normally REOPEN it as a
   regression»; исполняемое множество `_REOPEN_STATUSES = ("fixed",)` (`findings.py:61`),
   а `stale` входит в `LIVE_STATUSES` — stale-хит БАМПАЕТ, не reopen'ит. Согласовать прозу
   с исполняемыми множествами (упомянуть, что stale — live и бампает; reopen — только
   `fixed`). Только этот докстринг: соседние упоминания REOPEN (`:878`, `:962`, `:1394`)
   корректны, не трогать. Пин-тест: если дешёвый тест сверки прозы с `_REOPEN_STATUSES`
   возможен (например, докстринг не называет `stale` в reopen-контексте) — напиши; если
   структурно нечем пинить — скажи это явно в отчёте.
2. **CB-115** — `idx_findings_reported_at_ref` не существует на свежих базах: оба места
   создания (`findings.py:141` — внутри условного ребилда `_migrate_statuses`; `:156-160` —
   под `if "reported_at_ref" not in cols`, ложным на свежей базе, т.к. SCHEMA несёт
   колонку) живут в миграционных путях, которые свежая база не проходит. Добавить
   `CREATE INDEX IF NOT EXISTS idx_findings_reported_at_ref ON findings(reported_at_ref)`
   в **`_POST_MIGRATION_INDEXES`** (`findings.py:75`) — НЕ в индексный блок SCHEMA.
   TDD: сначала тест «свежая in-memory база несёт индекс» (по `sqlite_master`,
   `type='index' AND name='idx_findings_reported_at_ref'`) — обязан быть красным до
   правки; затем правка; мутационная проба — тест красный на откате правки.

**Критерий приёмки.** Докстринг согласован с `_REOPEN_STATUSES`/`LIVE_STATUSES`; свежая
база получает индекс (тест по `sqlite_master`); мигрированная не ломается (CREATE INDEX
идемпотентен, выполняется после миграций); wire golden регенерирован ТОЛЬКО если diff
показал изменение (см. ниже — ожидается, что не изменится); полный прогон
`uv run --extra dev python -m pytest tests/ -q` и `uv run --extra dev ruff check src/ tests/`
из worktree зелёные.

   в SCHEMA-блоке индекса нет (grep `idx_findings_reported_at_ref` даёт ровно две

2. **Предпосылки против схемы — держатся, но БУКВА фикса CB-115 из L3-брифа опровергнута
   эмпирически.** L3-бриф предписывал «в индексный блок SCHEMA». Порядок в
   `ensure_schema` (`findings.py:83-96`): SCHEMA выполняется ДО миграций, поэтому на
   pre-provenance базе (таблица findings без колонки `reported_at_ref`) индекс в SCHEMA

   Комментарий у `_POST_MIGRATION_INDEXES` (`:70-74`) прямо запрещает: «Applied AFTER
   every migration, never inside SCHEMA». `_POST_MIGRATION_INDEXES` выполняется после
   всех миграций на ЛЮБОЙ базе, включая свежую, — замысел («свежая база несёт индекс,
   мигрированная не ломается») выполняется именно там. Риск ребилда (`_migrate_statuses`
   пересоздаёт только свой hardcoded список индексов) не бьёт: `:141` уже несёт этот
   индекс, и `_POST_MIGRATION_INDEXES` выполняется после ребилда в любом случае.
   Отклонение от буквы L3-брифа ратифицировано менеджером Т-8 по правилу «сохрани смысл,
   а не букву»; доложено вверх.
