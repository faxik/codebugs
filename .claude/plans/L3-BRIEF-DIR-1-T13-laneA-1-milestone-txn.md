## §2. Тройка (П-Б)

**Замысел.** Вызов, записавший строку, обязан вернуть ту строку, которую записал, и решение о
записи обязано приниматься под тем же замком, что и запись. Сегодня ни то, ни другое: три
функции коммитят вне транзакции и затем перечитывают результат отдельным запросом.

**Задание-гипотеза.** Единая трансформация на все три: тело в `db.txn(conn)`, собственный
`conn.commit()` удалить, возвращаемое значение строить из `INSERT/UPDATE … RETURNING *`, а не
из перечитывания.

**Критерий приёмки.**
1. Возвращаемое значение каждой из трёх функций — строка, которую записал **этот** вызов.
2. Ни одного `conn.commit()` в этих трёх функциях не осталось.
3. Внешняя транзакция вызывающего переживает свой `ROLLBACK` (функции перестают её коммитить).
4. `update_milestone`: строка `milestone_audit` описывает **фактический** переход, а не
   прочитанный до записи.
5. `add_milestone_item`: возвращается вложение, созданное этим вызовом (см. §3.2).
6. Полный сьют и `ruff` зелёные; мутационная проба на каждый новый/изменённый тест.

## §3. Ловушки — четыре, и три из них уже стоили времени на предыдущих юнитах

**3.1 `RETURNING` и `rowcount` несовместимы.** Как только оператор несёт `RETURNING`, его
`rowcount` равен 0, пока курсор не исчерпан. Любая существующая проверка `rowcount` на этих
операторах обязана стать «курсор не выдал строки». Измерено на CB-111: наивный вариант даёт
отказ на **каждом успешном** вызове.

**3.2 `add_milestone_item` — F2 здесь возвращает не ту строку, и `RETURNING` чинит это даром.**
INSERT ключуется на тройке `(milestone_id, item_kind, item_ref)`, а перечитывание идёт через
`_get_item_by_ref` → `_spine._get_item_row_by_ref`, чей запрос —
`SELECT * FROM milestone_items WHERE item_ref = ? ORDER BY id DESC LIMIT 1` (`_spine.py:100-103`),
то есть по `item_ref` **одному** с разрешением неоднозначности «самый новый id». Множественные
вложения на один `item_ref` легальны по схеме (это CB-33), поэтому функция может вернуть
вложение к ДРУГОЙ вехе. `RETURNING` отдаёт вставленную строку и запрос по `item_ref` просто
исчезает.
**НЕ чинить `_get_item_row_by_ref`, перекладывая его на тройку** — у хелпера есть другие
вызывающие, и его семантика — решение CB-33, не этого юнита.

**3.3 `_audit` обязан оказаться в ТОЙ ЖЕ транзакции**, что и строка, которую он описывает
(`_spine.py:64-79`). Обёртка это даёт сама. Не давать `_audit` собственную транзакцию.

**3.4 `fetchone()` — ВНУТРИ блока `db.txn`.** Вынесешь наружу — умрёт с
`cannot commit transaction - SQL statements in progress` (измерено на CB-111).

И ещё одно, не ловушка, а факт для теста: у `update_milestone` есть no-op-путь
(`:78-80`, `if not updates: return current`), возвращающий значение, прочитанное ДО любой
записи. Под `db.txn` он будет держать write-lock ради одного SELECT — CB-24 эту цену уже
ратифицировала, менять не нужно, но тест не должен на этом спотыкаться.
