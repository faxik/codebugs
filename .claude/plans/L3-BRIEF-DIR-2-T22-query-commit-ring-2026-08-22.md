## Тройка П-Б

**Замысел.** Вопрос читателя «что наблюдалось на коммите X» должен отвечаться по ВСЕМ
наблюдениям карты, а не только по первому. Колонка `reported_at_commit` заморожена на
первом репорте намеренно (CB-53, вариант (b), ратифицировано через CB-63), ре-наблюдения
лежат в ринге `meta.occurrences[*].reported_at_commit` (CB-43). CB-53 научил этому ОДНОГО
из двух читателей (`check_findings` через `_effective_commit`); x2-ревью BT-4 назвало
`query(commit=)` «вторым ring-blind читателем» (judge verdict п.4). Колонка остаётся
заморожённой — юнит строго read-side.

**Гипотеза.** Фильтр `commit` в `query_findings` расширяется дизъюнкцией: совпадение
по замороженной колонке ИЛИ по любому элементу ринга — в SQL, через `json_each` над
`json_extract(meta, '$.occurrences')`, с тем же префиксным `LIKE ? || '%'` и тем же
hex-валидатором. Семантика «любое наблюдение» (а не «новейшее», как у staleness): вопрос
`query(commit=X)` — «что видели на X», для него все наблюдения равноправны; `_effective_commit`
ищет новейшее, потому что отвечает на другой вопрос (насколько карта устарела). Это
расхождение двух читателей ОСОЗНАННОЕ, записать его в докстринге обоих мест.

**Критерий приёмки (ратифицированный, дословно по смыслу):** запрос по коммиту
ре-наблюдения находит карту, чья первозапись была на другом коммите. Плюс:
- по коммиту ПЕРВОЙ записи карта по-прежнему находится (первый репорт — тоже наблюдение;
  заодно дорожный пин: пред-дедуп строки без ринга ведут себя ровно как раньше);
- префиксный матч работает на обеих ветвях (короткий префикс коммита ре-наблюдения);
- hex-валидация не ослаблена (`commit="zz"` по-прежнему `ValueError`);
- ни одна карта не возвращается ДВАЖДЫ, если совпали и колонка, и ринг (EXISTS, не JOIN);
- `LIMIT`/`OFFSET`/`group_by` не ломаются — **параметры сплайсятся в текстовой позиции
  фрагмента** (CB-20: `rank_case_sql`-параметры идут ПОСЛЕ WHERE-параметров, ДО LIMIT;
  новая ветвь добавляет второй `?` того же значения — оба в `params` в момент добавления
  условия, не «в конец»);
- golden регенерирован из worktree (`PYTHONPATH=src …`), дифф — только описание `commit:`
  в `query` (+ CLI help `--commit`, если есть такой флаг; если нет — это дыра CB-6, НЕ
  закрывать в этом юните, записать в эскалацию).

## Предписания (2) — это ПРЕДПОСЫЛКИ; добывай из кода и опровергай

1. **Форма ринга.** `_effective_commit` (provenance.py) читает `meta["occurrences"]` как
   список dict'ов с ключом `reported_at_commit`; пишущая сторона — `_bump_row` в
   findings.py. Подтверди ключ и форму из ПИШУЩЕЙ стороны (`grep -n occurrences
   src/codebugs/findings.py`), не из читающей: читатель может быть толерантен к форме,
   которой никто не пишет.
2. **Malformed meta.** `query_findings` уже применяет `json_extract(meta, ?)` в фильтре
   `meta_key` — выясни ИЗМЕРЕНИЕМ, что делает SQLite на строке с невалидным `meta` при
   `json_each`/`json_extract` в WHERE (ошибка `malformed JSON` на всю выборку? пропуск?),
   и сделай новую ветвь НЕ ХУЖЕ существующей `meta_key`-ветви: если та падает на
   malformed-строке — допустимо то же; если нет — оберни `json_valid(meta)` так, чтобы
   короткое замыкание было гарантировано (`CASE WHEN json_valid(meta) THEN EXISTS(...) END`
   — проверить, что `AND` в SQLite его не гарантирует, прежде чем на него опираться).
   Результат измерения — в юнит-бриф.
3. **`NULL` в ринге.** Наблюдение без коммита пишет `reported_at_commit: null` (авто-захват
   недоступен) — `json_extract(value,'$.reported_at_commit') LIKE …` на NULL даёт NULL →
   строка не матчится, это правильно; пин-тест на это.
4. **Регистр.** Колонка хранит SHA как пришёл; фильтр сегодня делает `commit.lower()` и
   `LIKE` (регистронезависимый для ASCII по умолчанию) — ринг должен вести себя так же;
   не вводи `lower()` в SQL без нужды.
5. **Описания.** Докстринг `query` (MCP) и `--commit` (CLI, если есть): «matches the
   first-report column OR any occurrence in the ring; `staleness_check` uses the NEWEST
   ring entry instead — a different question» — по смыслу.
